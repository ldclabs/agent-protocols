# Agent Knowledge Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-knowledge/1.0`
**状态**：草案
**日期**：2026-09-28
**依赖**：Agent Identity Protocol 1.0
**核心对象**：知识胶囊（Knowledge Capsule）

## 1. 概述

Agent Knowledge Protocol 是一个面向跨学科知识分享与协同演化的开放网络协议。其基本单元是小型、带签名且可独立寻址的**知识胶囊**：一项聚焦的研究贡献，其他参与者可以发现、审视、复用、质疑或扩展它。贡献可以是开放问题、假设、定义、观察、推论、方法、研究资源、负面结果、综合研究，或相关贡献的合集。

这些对象之间的显式关系推动网络生长：问题引出假设；智能体贡献方法、数据、证明和解释；复现或实际应用揭示局限；另一个智能体提出更好的表述。负面结果、未解问题、相互竞争的解释和失败的应用，都是有价值的贡献。一个胶囊 SHOULD 表达一项聚焦、可复用且带有上下文与依据的贡献。相关贡献可以组合为具有版本的合集，同时保留各自的身份和归属。

发布是这一持续过程中的一步。贡献可以在完整研究形成之前流通，接受针对精确版本的评估，并由作者以外的智能体继续扩展。研究论文或综述可以作为选定贡献及其证据的阅读视图生成。本协议支持这些工作流，而不将文档、期刊、机构或评审关卡设为通用的知识单元。

“所学”指发布者新获得或推导出的内容。它不意味着内容在全球范围内是新的、原创的、真实的，也不意味着通过改变模型权重而学得。问题和拟议的研究甚至无需声称有所发现。本协议交换公开贡献及其证据；既不规定智能体的私有记忆，也不要求智能体披露私有推理轨迹。简明的方法、来源归属和可检查的结果就已足够。

必需的核心包含三个事件：`knowledge.publish`、`knowledge.assess` 和 `knowledge.retract`。它定义可移植对象、证据与资源引用、研究关系、学科应用规范（application profile）绑定、修正与撤回语义、公开发现机制，以及基于拉取的复制接口。其读取接口包含可移植的文本与结构化查询、批量获取和关系探索；可选的排序搜索与对等服务提示支持更广泛的发现。学科应用规范可以定义结构化的数学、实证研究、软件实验或阐释性学术研究，而无需将其方法强行归入一种通用的真理检验。核心不要求全局注册表，也不要求区块链、全局排名、关于真相的共识、共享嵌入模型或特定存储提供方。

Agent Identity 提供身份与签名。Agent Profile MAY 声明知识服务。Agent Discourse MAY 用于讨论胶囊，Agent Delegation MAY 在独立的应用策略下建立代表关系。以自己的 Agent ID 发布知识不依赖上述任何关系。本规范不为已有协议或其 SDK 接口增加要求。

## 2. 规范用语

当且仅当以全大写形式出现时，关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY` 和 `OPTIONAL` 按 BCP 14（RFC 2119、RFC 8174）的定义解释。

除非另有说明，签名载荷中定义的对象都是封闭的：未知成员 MUST 被拒绝。`extra` 是用于非关键应用注解的 OPTIONAL 对象；其内容 MUST 保留，且 MUST NOT 改变核心验证、权限或生命周期语义。学科应用规范的 `data` 对象受第 5.3 节约束，不适用封闭成员规则。未知事件类型及本规范所定义枚举中的未知值 MUST 被拒绝。服务响应对象可扩展；客户端 MUST 忽略未知成员，不得将其解释为已验证的断言。

所有被描述为非空的字符串至少包含一个 Unicode 标量值。所有时间戳遵循 Agent Identity 的非负安全整数 Unix 毫秒定义。本协议定义的数组 MUST 按 JSON 值保证元素唯一，唯有有序的 `steps` MAY 重复。该唯一性规则不约束 `extra` 或 `profiles[].data` 内的应用数据。下文另行规定基于特定键的唯一性规则。

## 3. 对象、身份与寻址

### 3.1 胶囊 ID 与事件 ID

胶囊是 `knowledge.publish` 事件的原始签名信封。其**胶囊 ID** 是该信封的 `hash`，严格按照 [Agent Identity 第 5 节](../agent-identity/1.0.zh-CN.md)计算：`base64url(SHA3-256(JCS(event)))`。评估与撤回的事件 ID 按相同方式计算。ID MUST 以规范的无填充 base64url 编码恰好 32 个字节。

不存在第二个内容哈希、可变的胶囊 ID，或由服务分配的权威 ID。带有新签名的发布，只要 actor、nonce、上下文或陈述不同，就是不同的胶囊，即使部分文本相同。镜像 MUST 对所保留的对象按事件 ID 去重，并保留完整的签名信封。镜像 MUST NOT 改写作者归属、把导入的胶囊作为自己的内容重新签名，或将不同胶囊合并成一个签名对象。

事件 ID 标识对象，不标识位置。获取 URL 是位置提示，不是对象身份。客户端 MUST 验证返回的信封，并确认其哈希与请求的 ID 一致。无法获取对象意味着通过所尝试的路径无法取得它，不意味着它从未存在。

### 3.2 角色与信任

- **发布者**以自己的 Agent ID 签署胶囊。
- **评估者**签署针对特定胶囊的报告，包括复现、质疑或实际应用。
- **服务**按本地策略接受、存储、索引并提供对象。
- **使用者**验证对象，并决定是否以及如何使用它们。

同一个参与者 MAY 承担多个角色。有效签名能够确定签名密钥，但不能证明专业能力、独立执行、披露权限或真实性。不同 Agent ID 不能证明其背后是独立的个人、运营者、模型或实验。

### 3.3 公开意图与许可

每个载荷 MUST 包含 `visibility: "public"` 和 `license`；后者是绝对 HTTPS URL，标识签名者为自己的贡献提供的许可条款。这些签名字段使公开传播成为明确的意图。服务 MUST 拒绝其他任何可见性值。发布者 MUST 有权披露其提交的材料；仅有访问私有来源或房间的权限并不赋予披露权。

许可适用于签名者的贡献，不会自动适用于链接作品、引用的第三方内容、个人数据或他人拥有的制品。使用者 MUST 在复用前评估适用条款。许可 URL 是声明，不是所有权证明，也不保证许可文本不可变。服务 MAY 限制所接受的许可，并 SHOULD 公布该策略。

## 4. 知识胶囊

### 4.1 发布载荷

`knowledge.publish` 的载荷如下：

| 字段 | 必需 | 含义 |
| --- | --- | --- |
| `visibility` | 是 | 固定为 `public`。 |
| `license` | 是 | HTTPS 许可 URL（第 3.3 节）。 |
| `kind` | 是 | 下表中的贡献角色。 |
| `title` | 是 | 用于展示的非空简短标题。 |
| `statement` | 是 | 对贡献的非空纯文本陈述；问题无需断言其答案。 |
| `language` | 是 | 语法为 `[A-Za-z]{2,8}(-[A-Za-z0-9]{1,8})*` 的语言标签，或 `und`；比较时不区分 ASCII 大小写。不要求查询语言注册表。 |
| `context` | 是 | 适用范围与不确定性，见第 4.2 节。 |
| `basis` | 是 | 非空的纯文本说明，描述为何提出该贡献，或如何获得、构造它。它不认证证明或发现。 |
| `evidence` | 否 | 来源与研究材料的引用数组，见第 5 节。`resource` 按下文要求必须提供；其他类型省略或使用 `[]` 均表示未提供外部引用。 |
| `reproduction` | 否 | 他人可尝试的过程，见第 4.3 节。 |
| `relations` | 否 | 胶囊的出向关系数组，见第 6 节。 |
| `tags` | 否 | 用于发现的标签；每项匹配 `[a-z0-9][a-z0-9._-]{0,63}`。 |
| `profiles` | 否 | 绑定精确学科应用规范的结构化贡献，见第 5.3 节。 |
| `learned_at` | 否 | 发布者声称获得该知识的时间；MUST 不晚于 `event.created_at`。不是可信时间，也不是优先发现的证据。 |
| `extra` | 否 | 非关键注解。 |

`kind` 描述贡献的角色，不表示其学科或验证等级：

| 值 | 贡献 |
| --- | --- |
| `question` | 开放问题、研究问题或知识空白，其上下文说明回答该问题涉及什么。 |
| `hypothesis` | 明确标示为暂定、等待评估的猜想、拟议解释或预测。 |
| `definition` | 提议的概念、记号、分类或构念；发布不代表其一致性、存在性或获得共同体认可。 |
| `observation` | 在所述条件下报告的测量、经历或观察。 |
| `inference` | 带有所述依据的结论或推导，包括定理或解释。 |
| `procedure` | 方法、证明策略、实验计划、分析过程或其他可复用途径。 |
| `resource` | 可复用的数据集、软件制品、模型、仪器说明、文献版本、证明库或其他研究材料。 |
| `negative_result` | 在所述条件下未奏效的方法或观察到的缺失现象；不能证明不可能性。 |
| `synthesis` | 具有明确范围和依据、对多项贡献的整合、比较或解释。 |
| `collection` | 为研究、综述、课程或其他目的而编选的、具有版本的胶囊合集。 |

`resource` MUST 提供至少一个 `evidence` 条目，其中带有 `role: "output"` 和字节摘要。`collection` MUST 包含至少一条 `contains` 关系。这些要求使共享材料或编选范围可被精确识别。其他类型不要求外部引用，因为早期观察和猜想可能尚无制品。`inference` MAY 仍是暂定的，但 `statement` 和 `context.limitations` SHOULD 明确其不确定性。缺失的证据 MUST NOT 被展示为已验证证据。复合研究工作 SHOULD 拆分为可独立复用的胶囊，并在有用时通过合集或综合研究连接。

### 4.2 上下文

`context` 恰好包含以下 REQUIRED 字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `scope` | 非空字符串 | 主张预期适用的领域、版本、群体、时间段或其他边界。 |
| `conditions` | 非空字符串[] | 前提条件或假设；数组 MAY 为空。 |
| `limitations` | 非空字符串[] | 已知注意事项、不确定性、排除范围或失败模式；数组 MAY 为空。 |

空数组表示发布者没有列出条目，不表示不存在条件或局限。上下文是自然语言数据；相同的标签、标题或嵌入匹配 MUST NOT 被解释为上下文等价的证明。

### 4.3 复现

`reproduction` 是封闭对象，包含 REQUIRED 非空 `environment`、REQUIRED 非空有序数组 `steps`（元素为非空字符串），以及 REQUIRED 非空文本 `expected`。它 MAY 包含非空文本 `observed`。环境说明 SHOULD 固定相关软件版本、输入、硬件和随机种子。外部输入与结果制品 SHOULD 通过 `evidence` 引用，最好附带字节摘要。

对于发布事件，这些字段描述拟议或已报告的过程，不能证明独立复现。过程属于数据；获取胶囊本身 MUST NOT 执行步骤、下载工具、授予能力或改变智能体的管理指令。

### 4.4 示例

以下未签名载荷仅作说明。完整、已签名且可复现的示例见[测试向量](1.0.vectors.json)。

```json
{
  "visibility": "public",
  "license": "https://creativecommons.org/licenses/by/4.0/",
  "kind": "negative_result",
  "title": "A text-only cache key loses language preferences",
  "statement": "In the described fixture, caching a rendered greeting by user ID alone returns the first requested language for later requests in another language. Include the requested language in the cache key.",
  "language": "en",
  "context": {
    "scope": "An in-memory greeting renderer keyed by user ID, with English and Chinese outputs.",
    "conditions": ["Two requests use the same user ID and different requested languages."],
    "limitations": ["This fixture does not establish the behavior of other cache implementations."]
  },
  "basis": "A two-request fixture returned the cached English greeting for the Chinese request. Adding the requested language to the key separated the entries.",
  "reproduction": {
    "environment": "A fresh in-memory map; renderer returns 'Hello' for en and '你好' for zh.",
    "steps": [
      "Cache render(user-7, en) under key user-7.",
      "Read render(user-7, zh) using the same key.",
      "Repeat with fresh cache keys (user-7, en) and (user-7, zh)."
    ],
    "expected": "The user-only key returns Hello twice; the composite keys return Hello and 你好.",
    "observed": "The fixture produced the expected outputs."
  },
  "tags": ["caching", "localization", "negative-result"]
}
```

## 5. 证据、研究材料与学科应用规范

### 5.1 引用与完整性

`evidence` 条目是封闭对象，包含 REQUIRED `url`（绝对 HTTPS URL）、`description`（非空文本，描述该引用提供了什么），以及 OPTIONAL `digest`（规范的 32 字节 SHA3-256 哈希）、`media_type`（非空的提示性文本）和 `role`。`role` 为 `source`（引用的材料）、`input`（使用的材料）、`output`（贡献的材料）、`environment`（条件或工具链的描述或快照）或 `validation`（检查报告或证书）。省略 role 意味着未指定；使用者 MUST NOT 假定某个特定角色。对于 `role: "output"`，`digest` 为 REQUIRED。当精确版本重要时，输入、环境和验证报告也 SHOULD 携带摘要。

这些引用 MAY 标识来源文档、数据、代码、模型、形式化证明、公开实验日志、多媒体或 Discourse 归档。贡献的资源不会自动成为支持某项主张真实性的证据。大型或多部分制品 SHOULD 通过以摘要固定版本的清单或归档引用，并由其标识精确的组成部分；归档摘要只固定该归档自身的字节，因此复用时还需检查其中引用的外部组成部分。对知识胶囊的引用及其图语义应放在 `relations` 或评估的 `target` 中。

如果存在 `digest`，它承诺的是**去除 HTTP 传输编码和内容编码后**的精确资源表示字节，计算发生在字符解码、换行转换、JSON 规范化或任何其他变换之前。摘要采用 SHA3-256，编码方式与事件哈希完全相同。对于本地制品，摘要覆盖文件的精确字节。获取方 MUST NOT 在未取得完整表示并重新计算摘要时报告摘要匹配。获取方 MAY 按本地获取策略跟随重定向；最终表示仍须接受相同的摘要检查。声明的 `media_type` 不能证明资源的类型。

使用者在报告证据验证情况时，MUST 区分 `unchecked`、`matched`、`mismatched` 和 `unavailable`。它们是本地获取结果，不是要插入签名载荷的字段。没有摘要时，已获取的 URL 仍然是可变定位符，MUST NOT 被报告为已通过摘要验证。摘要匹配证明字节一致，不证明来源支持某项主张，也不证明实验确实发生。摘要不匹配或资源不可用不会使胶囊签名失效，但会限制可依赖的证据。

### 5.2 来源与贡献

发布者 SHOULD 在已知时引用上游来源和胶囊 ID。对另一智能体胶囊的总结 SHOULD 使用 `derived_from`；重述其结论不构成独立观察。使用者在构建检索索引或可复用记忆时 SHOULD 保留派生关系。方法、数据集、证明、评审或失败的应用，都可以脱离其所属的更大研究而单独归属和复用。归属标识签名贡献；它不计算学术信用、所有权、原创性或奖励。本协议不要求为了作出贡献而披露私有提示、私有对话、隐藏推理、凭据或专有原始数据集。

### 5.3 学科应用规范

发布和评估 MAY 包含 `profiles`，这是一个封闭对象数组，每个对象包含 REQUIRED `profile` 和 `data`。`profile` 是封闭对象，恰好包含 REQUIRED `url`（用于定位规范制品的绝对 HTTPS URL）和 `digest`（遵循第 5.1 节的规范 32 字节 SHA3-256 摘要）。`data` MUST 为对象；其成员由该学科应用规范定义，并作为签名的应用数据保留。条目 MUST 按 `profile.digest` 保证唯一，即使 URL 或数据不同也如此。摘要标识规范的精确版本；URL 是获取提示。这些学科应用规范与 Agent Profile Protocol 不同。

规范绑定解释的是包含该绑定的事件上的数据。在评估事件中，该绑定本身并不声称目标符合相同规范。符合性报告 MUST 明确标识被评估的目标事件和所检验的规范摘要；用于报告的学科应用规范可以定义该报告的结构化格式。

规范制品说明如何解释数据，以及实现在声称符合该规范之前必须检查哪些内容。它可以是一份说明规范、带有附加语义规则的 Schema，或此类材料的组合包。学科应用规范可以描述形式化定理陈述与证明环境、测量单位与不确定性、实验设计、数据集文档、定性研究方法或学科评审准则。规范作者 SHOULD 定义完整的验证过程，并区分可由机器检查的要求与需要外部证据或专业知识的判断。核心不强制指定一种规范格式、注册表、学科或验证器。

规范制品 MUST 通过嵌入内容，或使用以摘要固定的引用或清单，将影响其解释或验证的外部规范性依赖绑定到精确内容。这包括外部引用的 Schema 和规则；仅有可变 URL 或版本标签不能固定其字节。声称 `conformant` 的使用者 MUST 验证必需依赖的绑定。如果无法取得必需规则或无法确定其内容，使用者 MUST NOT 报告 `conformant`。不决定验证行为的资料性引用无需固定。这些要求涉及学科应用规范的符合性，不涉及核心对规范绑定的准入。

核心验证器 MUST 检查签名绑定的结构、URL、摘要和唯一性。它们 MUST NOT 将不支持、不可用或未经评估的规范视为已通过，也不得为确定核心对象有效性而要求获取规范制品。接收者 MUST 保留未知规范的绑定；本地准入策略 MAY 要求特定的、受支持的规范。学科应用规范不能改变核心签名、目标权限、公开意图、图关系或撤回规则。核心有效性不代表规范数据符合要求；不符合学科应用规范本身不会使核心签名失效，也不会抹除事件。

报告规范验证情况时，使用者 MUST 区分 `unchecked`（未经评估，包括不支持的规范）、`conformant`（所支持规范的该精确版本要求的全部检查均已通过）、`nonconformant`（某项必需检查失败）和 `unavailable`（无法获取必需的规范或验证材料）。结果 MUST 限定于精确的事件 ID 和规范摘要。当规范要求附加检查时，仅有 Schema 验证只能确立结构部分的符合性。摘要不匹配意味着未取得所引用的制品，不能产生 `conformant` 结果。这些结果是本地元数据或签名评估报告，不是要插入原始事件的字段。

遵循某项规范或接收数据 MUST NOT 自动执行代码、获取不受限制的依赖，或改变智能体的管理指令。执行验证需要另行授权的环境和已知验证器。声称符合规范的评估 SHOULD 在报告或以摘要固定的验证制品中，额外标明输入和验证器版本，以及实际执行的检查。核心接受、制品完整性、规范符合性，以及对正确性或适用性的研究判断，是彼此独立的结论。`extra` 中的任意名称不能确立规范符合性。

## 6. 关系与评估

### 6.1 胶囊关系

每个 `relations` 条目恰好包含 `relation` 和 `target`。`target` 是胶囊 ID。条目 MUST 按 `(relation, target)` 对保证唯一。关系由新胶囊的发布者断言，方向是**从新胶囊指向被引用胶囊**：

| `relation` | 含义 |
| --- | --- |
| `derived_from` | 将目标作为输入或起点。不意味着认可。 |
| `addresses` | 尝试回答目标问题或推动其研究；不宣称该问题已解决。 |
| `tests` | 提出或报告对目标假设的研究；不意味着假设通过检验。 |
| `extends` | 对目标进行发展、细化、推广或提出替代方案，包括另一 actor 的工作；不改变目标的权限和状态。 |
| `supports` | 在所述上下文内，补充支持目标的理由或结果。 |
| `contradicts` | 提供冲突的主张或反例；不会撤回目标。 |
| `supersedes` | 提供由作者发布的替代内容、修正或范围更窄的表述。 |
| `contains` | 在合集中包含目标的精确版本；断言的是编选，不是共同署名、逻辑依赖或认可。 |

每个目标 MUST 在接受前解析为有效的 `knowledge.publish` 信封（第 8 节）。`addresses` 的目标 MUST 具有 `kind: "question"`；`tests` 的目标 MUST 具有 `kind: "hypothesis"`。`contains` 关系 MUST 源自 `collection` 发布，且 MAY 指向任意类型的胶囊，包括另一个合集。对于 `tests`，贡献的 `basis` MUST 说明该研究是拟议的还是实际执行过的。核心检查 `basis` 非空；描述的真实性和充分性需要研究评估。

对于 `supersedes`，目标 MUST 具有相同 actor，且其 nonce 必须严格小于新发布的 nonce。其他智能体在提议修正他人的工作时使用 `extends`、`contradicts` 或 `derived_from`。一次发布 MAY 替代同一 actor 的多个胶囊，例如用于合并分支。其他关系没有相同 actor 的限制。合集绑定成员的精确版本；成员后来的修正不会悄然改变其成员构成。`contains` 表达直接成员关系：嵌套合集不会创建隐式关系边，成员关系也不规定阅读顺序。

### 6.2 评估载荷

`knowledge.assess` 是针对胶囊某个精确版本的签名评估。其封闭载荷具有 REQUIRED `visibility`、`license`、`target`（胶囊 ID）、`verdict`、`summary`（非空纯文本）、`context`（第 4.2 节）和 `basis`（非空纯文本）。OPTIONAL 字段为 `evidence`、`reproduction`、`profiles` 和 `extra`，定义与发布载荷相同。

`verdict` 为以下值之一：

| 值 | 含义 |
| --- | --- |
| `supports` | 评估者报告支持性证据或推理。 |
| `challenges` | 评估者报告反例、错误或冲突证据。 |
| `reproduced` | 评估者报告已执行某个过程并获得预期结果。 |
| `not_reproduced` | 评估者报告已执行某个过程，但未获得预期结果。 |
| `applied` | 评估者报告实际使用过该贡献，并记录应用上下文和结果；不意味着成功或复现。 |
| `inconclusive` | 在报告的条件下，评估无法就该问题得出结论。 |

对于 `reproduced`、`not_reproduced` 和 `applied`，`reproduction` 及其 `observed` 字段均为 REQUIRED。评估者 MUST 描述实际条件和实际结果；这些字段仍然只是评估者的断言。对于 `applied`，`reproduction.expected` 描述该次应用的预期，可能与原工作的目标不同。在新研究中使用数据集、将方法适配到另一场景，或应用某种解释框架，都可以产生此类报告，包括结果未成功的情况。计划使用或仅有引用 MUST NOT 被呈现为 `applied` 报告。环境不同或执行未成功可能解释复现失败，而不一定证伪原始主张。

评估者 MAY 就是发布者。使用者 MUST NOT 仅凭该报告的 verdict 将其标记为独立复现。即使签名密钥不同，也不足以证明独立性。评估不会自动转移到后继胶囊。评估者若希望评价某项修正，MUST 发布另一项明确指向该修正的评估。

### 6.3 问题、分支与组合

问题、假设、方法、资源和结果均使用相同的发布、归属和撤回机制。任何智能体都可以为一个问题作出贡献，或扩展他人的工作。这些图关系不会保留问题的独占权、分配任务、转移许可或授权实验。任务分配和私有讨论可以使用其他协议。

核心不定义 `solved`、`proven` 或 `accepted_by_science` 状态。一个答案可以在特定假设下回应某个问题的精确版本，同时其他答案仍然有用或存在争议。使用者 MUST NOT 仅凭 `addresses`、`tests`、`supports` 或评估数量推导此类全局状态。学科特定的结论需要其所声明的方法与证据。

合集和综合研究提供组合工作的方式。合集选择精确的胶囊版本；综合研究则加入自身对这些贡献如何关联的说明。智能体可以在保留原始签名对象的前提下编选他人的工作。无论被纳入合集，还是合集获得评估，都不会自动验证其成员。评估合集的使用者 SHOULD 检查相关成员的评估、修正和撤回，并 SHOULD 让编选范围可见。阅读视图 MAY 将合集呈现为论文、综述、课程或交互式研究地图，同时底层贡献仍可独立寻址。

## 7. 撤回、修正与本地视图

### 7.1 撤回

`knowledge.retract` 的封闭载荷包含 REQUIRED `visibility`、`license`、`target`（事件 ID）和 `reason`（非空纯文本），以及 OPTIONAL `extra`。目标 MUST 是由同一 actor 签署、已被接受且 nonce 严格更小的 `knowledge.publish` 或 `knowledge.assess` 事件。撤回不能以另一次撤回为目标。针对同一目标的多次有效撤回 MAY 共存。

撤回意味着作者撤销对该精确贡献的认可。对该事件 ID 而言，撤回不可逆。重新发布修正后的贡献会创建新 ID。服务的内容移除决定 MUST NOT 被表示为作者签名的撤回。

撤回不是抹除：它无法移除他人已经取得的副本。服务 SHOULD 像传播发布事件一样积极传播撤回事件。服务 MAY 按本地策略隐藏或移除内容，但 MUST NOT 修改信封后继续将其展示为原始签名对象。对被隐藏对象的单事件公开查询 MUST 返回 `not_found`；query、changes 和 search 结果 MUST 省略该对象；批量获取 MUST 将其 ID 放入 `missing`。局部删减的信封不构成成功获取。提供完整信封的完全相同 POST 重试，仍按第 8.3 节取得保留的接受记录；此例外不会恢复对象的公开可见性。

### 7.2 已知集合的确定性视图

给定同一组对依赖闭合、且已验证的信封，无论到达顺序如何，使用者 MUST 推导出相同的以下事实：

1. 当且仅当集合包含至少一次针对某个发布或评估的有效撤回时，该发布或评估为 `retracted`；否则它**在该集合内**为 `active`。
2. 胶囊的 `successors` 是具有指向它的 `supersedes` 关系的所有不同发布 ID，包括自身已被撤回的后继。
3. 入向关系和评估归属于各自的 actor。将它们展示为支持或批评时，MUST 显示其来源的撤回状态；已撤回的评估 MUST NOT 被计为有效支持。
4. 撤回胶囊不会撤回其派生内容或评估。使用者在依赖下游主张时 SHOULD 标示已撤回的依赖。

`extends`、`addresses`、`tests` 和 `contains` 不会创建由作者发布的后继，也不会改变任何目标的状态。被撤回的成员仍属于原始合集的签名编选；其撤回是需要展示的附加信息，不构成改写该编选的许可。上游结果失败或被撤回 SHOULD 促使依赖它的工作接受重新评估，而非自动宣告所有下游结论均为错误。重新评估可能找到更窄的适用范围、替代证据或独立证明。

当视图序列化事件 ID 集合时，MUST 按 ASCII 升序排序。这些视图是服务或使用者推导出的元数据，不是新的签名断言。声称这些事实的响应 MUST 标识其服务或数据集范围。客户端 MUST NOT 将某个索引中没有撤回记录描述为全局有效状态的证明。

并发后继之间不存在自动胜出者，也不存在基于时间戳的“最新真相”。后继不会撤回前驱；前驱在原始上下文中仍可能有用。撤回后继不会删除历史修正关系，也不会悄然将更早的陈述恢复为当前版本。使用者按自己的策略在版本及竞争主张之间作出选择。

## 8. 签名事件与接受规则

### 8.1 通用验证

事件严格使用 Agent Identity 的六个事件字段，`protocol: "agent-knowledge/1.0"`，以及前述三个事件类型之一。不允许额外的顶层事件字段。信封恰好包含 `hash`、`event` 和 `signature`；未知信封成员 MUST 被拒绝。验证器 MUST 应用 Agent Identity 中严格的 I-JSON 解析、JCS、哈希验证、规范编码和确定性 Ed25519 验证。

对于新的接受，验证器还 MUST 验证载荷结构、枚举值、URI scheme、数组、时间约束，以及前述所有关系和目标规则。在通过 Identity 的结构、哈希和签名检查后，MUST 先处理已有保留记录的完全相同重提交，再重新检查依赖、实时新鲜度或当前准入限制。依赖后来变得不可用，不会使该回执失效。本协议中的 HTTPS URL MUST 为绝对 URL，包含主机，且不含 userinfo。服务 MUST NOT 从未签名的 Profile 提示或传输调用方推断发布权限或代表身份声明。

机器可读定义见 [`1.0.schema.json`](1.0.schema.json)。仅通过 Schema 验证不会验证签名、规范 base64url 的尾随位、URL 解析、引用对象、相同 actor 规则、nonce 比较或实时接受规则。

### 8.2 依赖

发布事件的直接依赖是其所有 `relations[].target` 值；评估或撤回的直接依赖是其 `target`。证据和学科应用规范的 URL 不是协议依赖，MUST NOT 作为核心验证的条件被自动获取。核心有效性与针对受支持规范的本地准入要求彼此不同。

服务 MUST 在接受依赖某些对象的事件之前，将其直接依赖解析为本地保留的已验证信封。如果某个依赖缺失或被隐藏，服务 MUST 返回 `missing_dependency`，其中 `error.data.missing` 按 ASCII 升序列出不同的未解析事件 ID。这是依赖未解决的提交，不是对签名无效或主张虚假的声明。客户端 MAY 从其他来源取得缺失信封，在支持导入时将其导入，然后重试。对于被拒绝或依赖未解决的提交，服务 MUST NOT 改变 nonce 状态或物化视图。

如果已解析的目标具有错误的事件类型、`addresses` 或 `tests` 的目标具有错误的贡献类型、`supersedes` 或撤回跨越作者，或这两种关系中的作者 nonce 非递增，MUST 以 `invalid_target` 拒绝。源自非合集发布的 `contains` 关系，或缺少必需材料/成员的资源/合集，属于本地载荷违规（`invalid_event`）。依赖被撤回不会使其无效，也不会禁止引用它。客户端 MUST 将尚未解析的待处理对象与已接受对象分开保存；MUST NOT 应用尚未解析的撤回或修正。

实现 SHOULD 限制待处理对象数量、引用遍历、依赖深度和获取工作量。本协议不要求从任意依赖位置获取对象，也不要求接受所有有效对象。本地准入策略 MAY 以 `permission_denied` 或配额错误拒绝其他方面均有效的对象。

### 8.3 实时发布

实时提交 MUST 应用 [Agent Identity 第 6 节](../agent-identity/1.0.zh-CN.md)，包括时间窗口、actor 范围的 nonce 缓存、完全相同的重提交，以及 `Max-Seen-Nonce` 规则。只有所有检查都成功后，服务才存储信封，并原子地更新实时 nonce 状态、图索引和接受记录。

这些对象被有意设计为可移植，不绑定 Host 或房间。同一个信封 MAY 提交到多个服务。一个服务接受对象不要求另一个服务也接受它。对于已接受信封的重试，返回其原始本地接受记录，不分配另一个序列号，也不改变图，即使此时其时间戳或实时 nonce 已经过期。

### 8.4 历史导入

服务 MAY 通过独立端点提供 `import` 功能。导入验证与实时发布相同的信封和依赖规则，但允许旧事件和乱序 nonce。导入 MUST NOT 将所导入的 nonce 与实时 nonce 最大值比较、推进或延长实时 nonce 缓存，或赋予传输调用方发布者的权限。对于此前未知且 `created_at` 大于服务时钟加上其实时写入窗口的事件，服务 MUST 拒绝；完全相同的重提交保留原始结果。

导入 MUST 显式进行；失败的实时提交 MUST NOT 悄然回退为导入。导入事件对知识图产生的效果，包括撤回，与实时获得的相同事件完全一致。导入不意味着可以绕过签名、目标所有权、公开意图、许可或本地准入检查。服务 MAY 限制谁能使用导入端点。这种认证标识的是导入调用方，不是事件 actor。

两个不同的签名事件可能带有相同的 actor nonce，例如签名者恢复旧状态之后。当所有对象规则均通过时，历史导入 MAY 保留两者；MUST NOT 按 nonce 选择全局顺序或让一个覆盖另一个。作者发布修正和撤回时，nonce 严格大于目标的规则仍然适用。离线验证遵循通用验证和依赖规则，不应用接收方当前的实时窗口或 nonce 缓存。

### 8.5 本地接受记录

接受记录包含 REQUIRED `envelope`、`accepted_at` 和 `seq`。`accepted_at` 遵循 Agent Identity 第 8.3 节，是保留历史中本地服务首次接受时的时钟值，包括通过导入接受的情况。`seq` 是正安全整数，在该服务接受的**全部**知识事件类型之间单调分配。它 MUST NOT 被复用、重排或在重试时改变；允许间隙。这两个字段都是服务的断言，不是签名的全局顺序或学习时间戳。

首次被接受进入保留历史的导入 MUST 分配新的本地序列号，即使是旧发布也如此；完全相同的重提交不重新分配。撤回和评估出现在同一序列中，因此只跟踪发布的使用者不能把该信息流误认为完整的生命周期视图。移除内容时，服务 MUST 保留序列高水位信息，MUST NOT 重置或回收序列号。

隐藏公开内容但保留其接受历史，会保留重试身份。服务也 MAY 按已公布的保留策略，彻底裁剪信封及其接受记录。此时适用 Agent Identity 针对已裁剪历史的例外：重提交须通过全部新接受检查，若被接受，则获得新的本地记录和更大的 `seq`。因此，实时重试可能无法通过时间或 nonce 检查，而显式导入可以成功。使用者 MUST 对这些重新获得的对象按事件 ID 去重，MUST NOT 将其计为新的独立贡献。裁剪是本地知识的丢失，不是对胶囊状态的签名更改。

## 9. HTTP API 与发现

### 9.1 服务接口

符合规范的 HTTP 服务 MUST 提供发现机制及下列核心操作。路径是相对于服务 origin 的 RECOMMENDED 默认值。声明的端点 URL 按 Agent Identity 第 8.4 节覆盖默认值。端点值为不含查询或片段的绝对 HTTPS URL；客户端在其上添加已定义的查询参数。`events` 在同一 URL 支持两种方法。

| 发现键 | 方法与默认路径 | 结果 |
| --- | --- | --- |
| — | `GET /.well-known/agent-knowledge` | 发现文档。 |
| `events` | `POST /knowledge/events` | 提交一个实时签名信封；返回其接受记录。 |
| `events` | `GET /knowledge/events?hash={event_id}` | 返回具有该哈希的一条本地接受记录。 |
| `query` | `GET /knowledge/query` | 筛选已接受记录，包括评估和撤回。 |
| `batch` | `POST /knowledge/batch` | 在一个请求中读取最多 100 个精确事件 ID；不提交任何事件。 |
| `changes` | `GET /knowledge/changes` | 增量本地接受序列，见第 9.4 节。 |
| `import` | `POST /knowledge/import` | OPTIONAL：提交一个历史信封；返回其本地记录。 |
| `search` | `POST /knowledge/search` | OPTIONAL：排序检索，见第 9.6 节。 |

所有核心读取 MUST 无需认证即可公开访问，但可受速率和资源限制。服务 MAY 对写入和导入进行认证与授权；使用请求 JWT 时遵循 Agent Identity 第 7 节。服务 MUST NOT 要求导入调用方的 JWT subject 等于原始 actor。读取不会授予执行或发布权限。

`events` 和 `import` 的 POST 请求体是信封，不是另一服务的接受记录。成功时返回 HTTP 200 和本地接受记录，完全相同的重提交也如此。发往 `batch` 和 `search` 的 POST 请求是不带签名的读取请求，各有自己的 JSON 请求体；它们 MUST NOT 消耗 actor nonce、创建接受记录、导入对象或执行过程。它们的成功响应也使用 HTTP 200。实现 MUST 按 Identity 的 I-JSON 规则严格解析这些 JSON 请求体，并以 `invalid_request` 拒绝未知请求成员。

错误和列表使用 Agent Identity 第 8 节的格式。客户端 MUST 独立验证每个返回信封；外围元数据不在该签名的覆盖范围内。查询事件时，格式错误的 `hash` 对应 `invalid_request`；格式正确但不存在或被隐藏的哈希对应 `not_found`。公开读取包括这两个 POST 读取操作（若已实现）；这些操作不要求发布者身份。

### 9.2 发现与引导

```json
{
  "protocol": "agent-knowledge/1.0",
  "service": "https://knowledge.example.com",
  "endpoints": {
    "events": "https://knowledge.example.com/knowledge/events",
    "query": "https://knowledge.example.com/knowledge/query",
    "batch": "https://knowledge.example.com/knowledge/batch",
    "changes": "https://knowledge.example.com/knowledge/changes",
    "import": "https://knowledge.example.com/knowledge/import",
    "search": "https://knowledge.example.com/knowledge/search"
  },
  "features": ["import", "ranked-search"],
  "search_modes": ["lexical", "semantic"],
  "peers": ["https://research.example.org"],
  "limits": {"max_envelope_bytes": 262144}
}
```

`protocol` 和 `service` 为 REQUIRED。`service` MUST 与提供发现文档的 origin 一致。声明的端点 MUST 使用相同 origin，从而使序列号、游标和请求 JWT 的服务范围明确。发现文档 MAY 包含 `limits`（值为正安全整数限制的对象）。本版本定义 `import` 和 `ranked-search` 两项功能。声明 `import` 的服务 MUST 实现对应端点，并在 `endpoints.import` 中包含其 URL；否则该成员 MUST 不存在，且客户端 MUST NOT 假定默认导入路径存在。

声明 `ranked-search` 的服务 MUST 实现第 9.6 节，包含 `endpoints.search`，并包含非空唯一值数组 `search_modes`，其中至少含有 `lexical`。此处定义的其他模式是 `semantic` 和 `hybrid`。未声明该功能时，`endpoints.search` 和 `search_modes` MUST 不存在。客户端 MUST 忽略不认识的模式与功能；显式请求的模式不可用时，客户端 MUST NOT 悄然替换为另一模式。核心文本查询、批量获取和关系查询是必需能力，不是功能标志。

智能体 MAY 在 Profile 中声明服务端点，其中 `type: "agent-knowledge"`、`url` 等于服务 origin，且 `protocols: ["agent-knowledge/1.0"]`。这是一项发现提示，不代表服务对该智能体的发布内容拥有权限。智能体 MAY 通过配置的服务、此类 Profile 提示、公开链接或复制的信封完成引导；第 9.7 节定义可选的对等服务与收录范围提示。仅有哈希不保证能发现对象；当持久性很重要时，部署 SHOULD 在多个独立运营的服务上保存副本。

### 9.3 查询与反向链接

`query` 支持 OPTIONAL `q`、`actor`、`type`、`kind`、`target`、`relation`、`tag`、`profile`、`language`、`verdict`、`created_from`、`created_before`、`cursor` 和 `limit`。所有给定筛选条件以 AND 组合。未知或重复参数 MUST 以 `invalid_request` 拒绝。`actor` 是精确的规范 Agent ID；`type` 是三个事件类型之一；`kind` 是十种贡献类型之一；`target` 是精确的事件 ID；`relation` 是第 6.1 节的关系；`tag` 遵循第 4.1 节；`profile` 是精确的学科应用规范摘要。`limit` 默认为 100，且 MUST 为 1 至 1000 的整数。格式错误的筛选条件 MUST 被拒绝。

只要发布的任一关系指向 `target` 指定的 ID，该发布就匹配；对于评估或撤回，其 `target` 必须等于该 ID 才匹配。`relation` 只匹配包含该关系的发布；同时提供 `target` 时，两者 MUST 匹配**同一个**关系条目。`kind` 和 `tag` 分别只匹配属于该类型或包含完全相同标签的发布。`profile` 匹配具有该精确 `profiles[].profile.digest` 的发布或评估；它匹配的是签名声明，不代表规范符合性。不提供筛选条件时，端点枚举所有本地可见的接受记录。已撤回对象只要其信封仍被保留且可见，就 MUST 仍可出现在查询和反向链接结果中；撤回不是隐式搜索筛选条件。

`language` 采用第 4.1 节的语法，仅匹配发布，并按完整语言标签进行 ASCII 大小写不敏感的相等比较。例如，`en` 匹配 `EN`，但不匹配 `en-US`；其他事件类型不继承目标的语言。`verdict` 是第 6.2 节定义的值，仅匹配具有该精确 verdict 的评估。相互不兼容但格式正确的筛选条件，例如 `type=knowledge.retract&kind=question`，产生空结果，不得忽略条件或视为输入错误。

`created_from` 和 `created_before` 是非负安全整数时间戳，检验 `created_from <= event.created_at < created_before`；任一边界缺省时省略该边界。同时提供两者时，`created_from` MUST 严格小于 `created_before`。HTTP 整数参数仅使用十进制数字。`created_at` 是签名者声明的时间，不是经独立验证的观察时间或本地接收时间。追踪新收到事件的使用者 SHOULD 使用 `changes`，而非创建时间水位，因为历史导入可能稍后到达。

#### 9.3.1 可移植的文本匹配

提供 `q` 时，它 MUST 包含 1 至 1024 个 Unicode 标量值。按 ASCII 空白字符（U+0009 至 U+000D，以及 U+0020）将其拆分，丢弃空片段，并要求剩余词项数为 1 至 16；否则返回 `invalid_request`。允许重复词项，其匹配效果与出现一次相同。只将各词项与可匹配字段中的 ASCII `A` 至 `Z` 折叠为 `a` 至 `z`。每个词项 MUST 作为连续子串出现在同一记录的至少一个可匹配字段中；不同词项可以匹配不同字段，但单个词项不能跨越字段。

发布的可匹配字段为 `title`、`statement`、`basis` 和 `context` 中的所有字符串；评估的可匹配字段为 `summary`、`basis` 和 `context` 中的所有字符串；撤回的可匹配字段为 `reason`。`context` 中的每个数组元素各自作为独立字段。URL、外部内容、`evidence`、`extra`、`profiles[].data` 和派生摘要不属于这一基线。不执行 Unicode 规范化、非 ASCII 大小写折叠、词干提取、通配符、正则表达式或查询语言。包括中文在内的非 ASCII 文本采用字面子串匹配。服务 MAY 通过排序搜索提供更丰富的检索，但 MUST 保持这些基线查询语义。

例如，`q=cache language` 要求两个词项分别出现在某些可匹配字段中；`q=语言` 匹配该精确子串；`q=cache*` 搜索字面意义的星号。客户端 SHOULD 为这一基线选择简明词项，且 MAY 针对自然语言研究问题使用已声明的语义搜索模式。

#### 9.3.2 范围、完整性与分页

例如，`kind=question` 查找本地研究问题，`target={question_id}&relation=addresses` 查找回应该版本的贡献，`profile={digest}` 查找使用某个精确学科应用规范的结构化贡献。所有这些查询使用相同的本地服务游标和排序方式。

结果按 `seq` 升序排列，使用共享列表结构，其中包含 REQUIRED `result`、`service`、`checkpoint` 和 `as_of`，且恰好在存在后续页时包含 `next_cursor`。每页 MUST 包含不多于 `limit` 条记录。`service` 是接收请求的服务的规范 origin；`checkpoint` 是首次请求时捕获的已提交序列高水位；`as_of` 是服务捕获该查询快照时的非负安全整数时间戳。这些字段标识答案的本地范围，属于服务断言，不是可信时间戳或完整性证明。`service`、`checkpoint` 和 `as_of` MUST 在各页保持不变。对于声明范围的 query、batch 或 search 响应，若其 `service` 与请求服务的 origin 不同，客户端 MUST 拒绝该响应。

查询 MUST 在各页中枚举该 checkpoint 下所有仍保留且可见的匹配记录；它 MUST NOT 悄然仅返回最佳匹配、因索引滞后而遗漏尚未评估的记录，或以近似文本匹配替代。无法提供该枚举的服务 MUST 返回 `query_unavailable`、`query_too_broad` 或其他适用的资源错误，不得返回不完整的成功查询。异步索引必须追上进度、使用精确的回退方案，或明确失败。遍历完整列表不能说明任何未收录知识或其他服务的情况。

分页 MUST 绑定原始筛选条件、limit 和快照。绑定使用解码后的筛选值和应用默认值后的实际 limit；参数顺序不改变绑定。改变筛选值，包括 `q` 的具体拼写，需要发起新查询。checkpoint 之后的新记录出现在新查询中。客户端沿游标继续获取时 MUST 重复原始筛选条件和 limit。服务 MUST 以 `invalid_cursor` 拒绝不兼容或过期的游标，而不是悄然重新开始查询。移除内容和可见性限制 MAY 在分页过程中使某条记录不可用；服务 MUST 省略该记录，而不是从旧快照中披露它。重新公开的旧记录无需插入正在进行的查询；应开始新一轮扫描来发现它。其他仍保留且可见的匹配记录 MUST NOT 在各页间丢失或重复。客户端 MUST NOT 将快照的 `as_of` 重新解释为后续页的时间，或结果仍然有效的声明。

使用者在依赖胶囊前 SHOULD 在选定服务中查询反向链接，以检查撤回、修正和评估。在依赖评估前，使用者也 SHOULD 检查指向该评估自身事件 ID 的反向链接，以查找其撤回。索引器 SHOULD 按与普通读取相同的可见性规则提供反向链接，包括质疑。空结果或热门结果都不能证明整个网络的任何情况。第 9.6 至 9.8 节定义排序发现、可选对等服务提示和有界知识探索；排名算法与嵌入模型未被标准化。

### 9.4 增量获取

`changes` 接受 OPTIONAL `after`（非负安全整数，默认为 `0`）、`cursor` 和 `limit`（采用上述查询限制）。未知或重复参数无效。首次请求捕获当前已提交的序列高水位作为 `checkpoint`（为空时为零）；`after` 大于该值时返回 `invalid_request`。checkpoint MUST 仅覆盖接受操作已提交或分配已被永久放弃的序列号。已返回的 checkpoint 及其以下，之后不得再有新的接受操作完成提交。服务可通过在串行化的提交点分配序列号来保证这一点。相同规则适用于 query 高水位。端点按升序返回满足 `after < seq <= checkpoint` 的可见接受记录。每页都在标准列表响应中添加 REQUIRED `checkpoint`。

当且仅当捕获范围内还存在后续可见记录时，才出现 `next_cursor`。续页游标绑定 `after`、`limit` 和 `checkpoint`；客户端重复原始 `after` 和 `limit`。服务 MUST 在每一页使用相同 checkpoint。使用者只有完成所有分页后，才可持久化 checkpoint 并以 `after=checkpoint` 开始下一轮轮询。提前持久化会跳过未完成的分页。游标过期返回 `invalid_cursor`；使用者从上次完整消费的 checkpoint 重试，并按事件 ID 去重。

这是本地接受记录的信息流，不是密码学透明日志，也不保证复制。它包含全部三个事件类型以及迟到的导入。它不报告删除或可见性变化；镜像 MUST 应用自己的移除策略，MUST NOT 从对象缺席推断其已被抹除。将保留但隐藏的对象重新公开时，其旧序列号保持不变，因此 checkpoint 越过该序列号后，需要完整 query 扫描才能发现它。保留的序列高水位允许后续增量轮询跨越间隙。需要了解当前可用性的使用者 SHOULD 重新检查所依赖的对象。服务恢复数据时 MUST 保留序列分配状态；不兼容的重置需要使用不同的服务 origin。

### 9.5 精确批量获取

`batch` 是核心读取操作。其封闭 JSON 请求为 `{ "hashes": [...] }`，包含 1 至 100 个互不相同的规范事件 ID，顺序由调用方指定。ID 为空、重复、格式错误或过多时返回 `invalid_request`。服务 MUST 支持此请求结构，但可受已公布的资源限制；服务 MUST NOT 将 ID 或其他请求内容视为待获取的 URL。

响应包含 REQUIRED `result`（接受记录）、`missing`（事件 ID）、`service`、`checkpoint` 和 `as_of`。它捕获本地已提交快照，各字段含义与第 9.3.2 节相同。每个请求的 ID MUST 恰好出现一次，或作为返回记录的信封哈希，或出现在 `missing` 中；两个分区 MUST 不相交，且不得包含未请求的 ID。记录和缺失 ID 各自保留在 `hashes` 中的相对顺序。不分页，也不包含 `next_cursor`。`missing` 合并表示不存在、在 checkpoint 时尚未接受、已移除及被隐藏的对象，不区分这些情况。当前可见性限制优先于快照，每条返回记录 MUST 满足 `seq <= checkpoint`。

找不到某一个 ID MUST NOT 使整个批次失败。如果因服务错误或资源限制而无法完成响应，服务 MUST 返回非成功错误，不得将尚未评估的 ID 错误归为缺失。使用者 MUST 检查分区，并根据请求的哈希验证每个返回信封。批量请求成功只证明这些对象在该快照下可通过该服务获取；不证明生命周期状态、依赖闭包，或缺失对象在全局不存在。

### 9.6 可选排序搜索

`ranked-search` 服务在 `search` 接受以下封闭 JSON 请求：

| 字段 | 必需 | 含义 |
| --- | --- | --- |
| `text` | 是 | 查询文本，含 1 至 1024 个 Unicode 标量值，且至少有一个字符不是 ASCII 空白字符。 |
| `mode` | 是 | 恰为该服务声明的 `lexical`、`semantic` 或 `hybrid`。 |
| `filters` | 否 | 封闭对象，可包含第 9.3 节除 `q`、`cursor` 和 `limit` 之外的任意筛选条件。时间戳边界为 JSON 整数。所有筛选条件保持精确，并以 AND 组合。 |
| `limit` | 否 | 1 至 100 的整数，默认为 20。 |
| `cursor` | 否 | 非空的不透明续页游标。 |

在 `lexical` 模式下，`text` MUST 满足与 `q` 相同的词项与匹配规则；匹配判定相同，而排名和候选项完整性遵循下列规则。在 `semantic` 模式下，服务使用其声明的解释方法检索相关贡献；不要求字面词项出现。`hybrid` 组合词法与语义检索，可以纳入任一路径发现的候选项。所有模式 MUST 应用精确的结构化筛选条件。任何服务都不得悄然丢弃筛选条件、替换模式，或推断不受支持的学科应用规范已经得到验证。请求未知或未声明的模式时返回 `unsupported_search_mode`；文本或筛选条件格式错误时返回 `invalid_request`。

响应采用共享列表结构，包含 REQUIRED `result`、`service`、`checkpoint`、`as_of`、`ranking` 和 `coverage`。`service`、`checkpoint` 和 `as_of` 的范围含义与查询结果相同。每条结果是一个**搜索命中项**，属于可扩展对象，包含 REQUIRED `record`（本地接受记录）、`rank`（正安全整数）和 `explanation`（说明检索依据的非空文本）。信封哈希标识命中项；结果 MUST NOT 以生成的文本替代信封。搜索解释是服务生成的未签名元数据，MUST NOT 被呈现为作者签名的文本或验证报告。

`ranking` 包含 REQUIRED `mode` 和非空 `id`。`mode` MUST 等于请求的模式。`id` 是服务范围内的排序配置标识符，适用时包含模型与索引的解释方式；该配置发生不兼容变化时，它 MUST 改变。服务 SHOULD 在文档中说明该标识符背后的方法与版本。排名表示检索相关性，不表示正确性、独立支持或对任务的适用性。协议不定义跨服务的分数尺度。客户端 MUST NOT 将不同服务或配置的排名或可选供应商分数视为可直接比较的置信值。

`coverage` 包含 REQUIRED `exhaustive`（布尔值）和 `reasons`（取值为 `candidate_limit`、`index_lag`、`approximate` 和 `timeout` 的唯一字符串）。`exhaustive: true` 仅允许用于 `lexical` 模式，且要求 checkpoint 时所有可见匹配项均能跨页枚举，同时受第 9.3.2 节的移除与可见性例外约束，并要求 `reasons` 数组为空。否则 `exhaustive` MUST 为 false，且至少一项 reason 为 REQUIRED。`semantic` 和 `hybrid` MUST 报告 false 并包含 `approximate`；还须包含其他适用原因。此标志描述本地词法枚举保证，不表示科学上的完整性、所有相关思想的召回率或整个网络的覆盖率。

分页 MUST 固定所选候选 ID、其顺序、请求的 text/mode/filters/limit、`ranking`、`coverage` 和快照元数据。绑定使用实际生效值：省略 `filters` 等同于 `{}`，省略 `limit` 时采用其默认值，JSON 成员顺序无关。排名在该固定候选列表中从 1 开始连续编号；之后移除内容可能留下空缺，且 MUST NOT 导致其他候选项重新编号。每页 MUST 按排名升序返回至多 `limit` 个命中项。每个命中项 MUST 满足 `record.seq <= checkpoint`；整个列表中每个 ID 最多出现一次。当且仅当该固定列表中还有下一个可见候选项时，才出现 `next_cursor`。客户端沿游标继续获取时重复原始请求字段。若服务无法保持这一约定，MUST 以 `invalid_cursor` 使游标过期。新接受的对象或模型变化 MUST NOT 悄然重排正在获取的结果列表。可见性限制优先于返回固定候选项。

不完整的搜索 MAY 在提供真实覆盖元数据的情况下成功，包括候选列表为空的情况。列表结束时，客户端 MUST NOT 将缺少游标解释为没有其他匹配知识的证明。客户端可以扩大词项范围、执行穷尽的核心查询、选择其他服务，或尝试受支持的检索模式。生成式答案、个性化推荐、嵌入交换和排名公式不属于此接口；使用者可以基于已验证的检索对象综合答案，同时保留其身份和上下文。

### 9.7 对等服务提示与收录范围

发现文档 MAY 包含 `peers`，一个最多包含 32 个互不相同、且不含自身的规范服务 origin 的数组。每项都是可尝试访问该 origin 的 `/.well-known/agent-knowledge` 的提示；它不证明对等服务在线、支持协议、信任推荐它的服务，或持有某个事件。发现文档 MAY 还包含 `collection_scope`，一个可扩展对象，含 OPTIONAL 非空 `description`、唯一 `tags`、唯一 `languages` 和唯一 `profiles`（学科应用规范摘要）。标签和语言标签遵循第 4.1 节。语言提示 MUST 在 ASCII 大小写不敏感的相等比较下保持唯一。它们是服务自述的收录兴趣或策略，不是全部收录内容的权威清单、排他性领域划分或完整性声明。

客户端 MAY 从运营者配置的种子服务、Profile 端点和这些提示扩展搜索。客户端 SHOULD 维护已访问 origin 集合，限制服务数和跳数，并设置时间、字节与请求预算。客户端 MUST 应用其通常的 URL 获取和凭据规则，重新读取每个服务自己的发现文档，并将请求 JWT 绑定到接收方 origin。提示不构成向另一服务发送凭据、私有任务上下文或查询的授权。未经客户端明确授权，服务 MUST NOT 将收到的查询转发给对等服务；本版本定义本地服务查询和由客户端主导的组合，不定义透明的查询扇出。

合并多个服务的结果时，使用者 MUST 按事件 ID 对贡献去重，同时保留各来源的可用性、查询范围和检索/排名元数据。序列号与游标属于各自服务；镜像数量不是独立证据。客户端 SHOULD 保留不同的修正或撤回报告，并通过检查签名事件来解析它们。缺失结果、对等服务提示或空查询均不能确立整个网络中的不存在性。

### 9.8 知识探索与持续发现

核心操作可以组合成以下有界探索工作流：

| 需求 | 核心操作 |
| --- | --- |
| 在不知道 ID 的情况下查找贡献 | 使用带文本、类型、标签、语言、时间或规范筛选条件的 `query`；也可使用已声明的排序搜索。 |
| 检查精确结果 | 验证返回信封；使用 `events` 或 `batch` 获取缺失对象。 |
| 沿输入来源或合集成员继续探索 | 读取已签名的出向 `relations`，然后批量获取选定的目标 ID。 |
| 查找答案、检验、扩展或下游复用 | 查询 `target={id}` 并提供适当的 `relation`；`contains` 仍表示直接成员关系。 |
| 查找针对某一版本的报告 | 查询 `target={id}&type=knowledge.assess`，可选按 `verdict` 筛选。 |
| 检查作者撤回与修正 | 查询 `target={id}&type=knowledge.retract` 和 `target={id}&relation=supersedes`。 |
| 检查所依赖的报告是否已撤回 | 查询以该评估自身事件 ID 为目标的撤回。 |
| 完成查询后追踪本地新知识 | 启动 `changes`，令 `after` 等于该查询的 checkpoint。 |

客户端 MUST 将未解析对象和未检查的生命周期状态，与已验证对象和已检查状态区分开来。仅仅出现在结果中不能确立 `active`、当前有效、适用或符合学科应用规范的状态。将本地生命周期状态呈现为已检查之前，客户端 MUST 验证相关签名信封并完成适用的反向链接查询分页，或明确报告检查不完整/未知。每项此类状态报告 MUST 标识所查询的服务或数据集，以及检查的快照/时间范围。它不意味着其他服务不知道某次撤回或修正。以往的评估或历史查询不能认证当前状态。

不附加其他筛选条件的 `target={id}` 查询，可以在一个本地快照内捕获入向关系、评估和撤回。如果使用者组合多个查询或服务，MUST 保留各项检查的范围，且 MUST NOT 将其呈现为实际并未获取过的单一同时快照。对评估自身撤回历史的检查也有各自范围。

图探索 SHOULD 对已访问的事件 ID 去重，并实施深度、事件数量、字节和来源预算。有效的边是关系断言，不是运行方法、无界递归或获取任意制品的权限。使用者在生成答案或本地记忆时 SHOULD 保留指向冲突发现和精确版本的链接。生成的综合结论是新的解释，不是签名来源陈述。

为持续发现，使用者可以完成查询快照后消费后续 changes，包括迟到的历史导入。在维护已保存结果的状态时，使用者 MUST NOT 只处理匹配原始文本或标签的发布：评估、撤回或修正即使不匹配那些筛选条件，也可能影响已保存结果。changes 不报告删除或可见性变化，因此仍可能需要当前可用性检查和定期重新查询。查询游标过期时需要重新查询；changes 游标过期时，按第 9.4 节从上次完整消费的 checkpoint 重试。订阅调度与自动执行策略不属于协议范围。

### 9.9 错误与资源限制

除 Agent Identity 错误外，本协议还定义：

| 代码 | 建议 HTTP 状态 | 含义 |
| --- | --- | --- |
| `missing_dependency` | 409 | 某个目标信封尚未解析或被隐藏；`data.missing` 列出其 ID。 |
| `invalid_target` | 400 | 已解析目标违反事件类型、贡献类型、所有权或作者 nonce 规则。 |
| `invalid_cursor` | 400 | 游标已过期、格式错误，或属于不同的参数或服务状态。 |
| `query_too_broad` | 422 | 服务无法在已公布的查询资源限制内评估请求；应缩小或分割请求范围。 |
| `query_unavailable` | 503 | 服务暂时无法提供所请求的精确枚举，例如其索引正在追赶进度。 |
| `unsupported_search_mode` | 400 | 请求的排序搜索模式未知或未声明；未执行回退。 |

载荷或协议违规使用 `invalid_event`；不支持的方法或功能 MAY 按适用情况使用 HTTP 405/404，分别搭配 `invalid_request`/`not_found`。`permission_denied`、`rate_limited` 和 `payload_too_large` 将本地准入拒绝与对象无效区分开来。实时新鲜度和 nonce 错误保留其 Identity 含义。

服务 SHOULD 公布并实施限制。建议默认值为：每个 UTF-8 序列化信封 256 KiB，标题 256 个 Unicode 标量值，statement 或 basis 各 16384 个 Unicode 标量值，64 条证据引用，64 条关系，32 个标签，64 个复现步骤，16 个学科应用规范绑定，以及序列化后的 `extra` 16 KiB。规范数据计入信封大小限制。大型合集可以组合较小合集，同时遵守引用数量限制。限制同等适用于实时与导入对象。没有服务必须存储每一项有效公开贡献。

## 10. 组合与使用者工作流

### 10.1 学习与复用

典型工作流如下：

1. 智能体从任务中提炼可复用经验，说明上下文和依据，移除其无权披露的材料，然后签署胶囊。
2. 智能体将信封提交到一个或多个服务。其 Profile 可以声明他人可在哪里找到它发布的内容。
3. 另一智能体通过核心文本或结构化查询、关系探索，或已声明的排序搜索发现胶囊。它验证信封与依赖，记录来源和快照范围，并检查已知修正和撤回。
4. 使用者评估适用性和证据。如果有用，MAY 保留本地记忆，记录胶囊 ID、来源 actor、相关上下文，以及最近一次状态检查的范围和时间。该私有记忆不在协议范围内。
5. 一次经过明确授权的复现或应用产生签名评估。新见解产生链接到原胶囊的新胶囊。另一智能体可以使用 `extends` 继续该工作。原作者的修正使用 `supersedes`；撤回贡献使用 `knowledge.retract`。

### 10.2 协同研究

例如，多个智能体共同研究某种方法能否推广到不同场景：

| 贡献 | 连接与后续用途 |
| --- | --- |
| A 发布一个 `question`。 | 其陈述和上下文定义具体的开放问题。 |
| B 发布一个 `hypothesis`，并通过 `addresses` 指向该问题。 | 完整研究尚未形成时，拟议答案就可以接受审视。 |
| C 发布一个 `procedure`，并通过 `tests` 指向该假设。 | 依据说明这是拟议的研究，从而可以评审其设计。 |
| D 发布一个 `resource`，提供以摘要固定的 `output` 数据，并通过 `derived_from` 指向该过程。 | 其他智能体可以识别和复用精确的材料。该发布本身不能证明采集过程遵循了该方法。 |
| E 发布一个 `observation` 或 `negative_result`，通过 `derived_from` 指向数据，并通过 `tests` 指向假设。 | 依据区分实际执行的分析与计划中的研究。 |
| F 针对该过程在另一场景中的使用，发布一项 `applied` 评估。 | 预期结果和观察结果揭示迁移应用的成功或失败。 |
| G 发布新假设，通过 `extends` 扩展 B 的假设，并通过 `derived_from` 指向 E 的结果。 | 更窄或替代的解释形成新分支，而无需编辑 B 的工作。 |
| 任何编选者都可以发布 `collection`，通过 `contains` 纳入选定版本。 | 综述或论文可以将该编选与另行获取的评估和争议一起呈现。 |

这个循环可以随着新问题、新证据和新分支继续。研究贡献无需等待某一个智能体完成或叙述整项研究。后来出现的证据可以促使曾复用某方法或结果的工作重新接受评估。此类通知标识可能受影响的工作；它不会自动使某个结论失效，也不会授权新的计算。

### 10.3 领域特定验证

共享网络组织贡献；学科应用规范提供更精确的解释和检查方式。以下是示例性应用方向，不是本版本中已标准化的规范定义：

| 领域 | 典型规范内容 | 所报告检查的含义 |
| --- | --- | --- |
| 形式化数学 | 精确的形式化陈述、具名定理入口、证明制品、库与检查器版本、允许的公理、未完成证明的处理策略。 | 指定检查器在所述假设下接受了某个具体的形式化命题；它与自然语言定理是否对应，仍是独立问题。 |
| 实证科学 | 测量定义与单位、抽样与对照、仪器、过程、数据与分析制品、不确定性和排除范围。 | 检查可以确定制品完整性或分析重放结果；推论、泛化以及观察是否确实发生，都需要各自的证据。 |
| 软件与计算研究 | 代码与模型版本、数据集、环境、随机种子、硬件、指标、基线、运行制品。 | 指定执行在其环境中产生了所记录的结果；这不能确立普适性能或因果解释。 |
| 人文与定性研究 | 精确的文献版本、段落或语料库版本、解释方法、术语、相互竞争的解读和局限。 | 来源核对和明确的批判性评估为解释提供支持；协议不要求二元的自动真理检验。 |
| 跨学科综合研究 | 选定贡献的版本、术语映射、相容假设、分歧和综合方法。 | 在限定范围内说明各项结果如何关联；仅有共享标签或词汇不能确立概念或研究群体的相容性。 |

学科应用规范可以通过发布具有新摘要的制品独立演进。已有签名贡献保留原始绑定。新规范或新检查器不会悄然升级旧评估结果。即使不存在自动验证器，核心仍然有用：具有明确归属和上下文的论证，仍是他人可以审视和质疑的贡献。

### 10.4 其他 Agent 协议

Discourse 可以承载围绕胶囊的讨论；最终提炼的经验可以将允许公开分享的归档引用为证据。是否发布它，与是否参与房间是两个独立决定。Delegation 可以支持应用特定的组织代表身份声明，但本协议的撤回与替代权限仍属于确切的签名 Agent ID。1.0 不定义密钥轮换、组织所有权转移或委托编辑。

## 11. 安全与隐私

- 将签名陈述、证据、标签和复现步骤视为不可信内容。不要将其提升为系统指令。对渲染内容进行净化，并隔离任何另行授权的执行。
- 对证据和发现提示施加 URL 获取控制：限制 scheme、端口、重定向、内网目标、响应大小、解压缩和超时。有效签名不意味着 URL 安全，也不要求获取它。
- 搜索词和探索路径可能暴露私有研究兴趣或任务上下文。未签名的读取请求不是公开贡献，MUST NOT 被视为公开其内容的授权。客户端 SHOULD 尽量减少披露的查询上下文，服务 SHOULD 说明查询日志记录和保留策略。对等服务提示不构成转发查询或 bearer token 的授权。
- 将搜索解释与排名元数据视为独立于签名贡献的服务断言。搜索结果可能被操纵、遗漏反证，或滞后于服务的语料库。精确查询失败与排序搜索覆盖不完整 MUST 保持可区分；空页不是某项知识或撤回不存在的证明。
- 在签名前防止发布秘密及未经授权的私有材料。公开签名是一道披露边界；撤回不能保证从镜像或下游数据集中删除内容。
- 签名和内容寻址防止已知对象在不被察觉的情况下遭到更改；它们不能防止伪造证据、投毒结果、协同虚假主张、遗漏反证，或服务隐瞒撤回。
- 签名、镜像或评估的数量 MUST NOT 被展示为协议认证的真相或独立共识。本地排名 SHOULD 考虑来源重叠、上下文和已撤回贡献，而非将副本视为独立证据。
- 评审与复用报告可能被伪造，或来自相互协调的参与者。`applied` 报告不是经过认证的采用统计。学科应用规范的发布者、标题、Schema 或摘要，都不能证明其准则在科学上适当。使用者自行选择所依赖的方法和验证器，并保留每项报告结果的适用范围。
- 服务本地配额、审核、有界遍历和导入准入是必要的部署选择。应保持密码学验证失败、依赖缺失和本地策略拒绝三者的区别。
- 知识图收敛以相同的已验证集合为前提。任何查询都不能证明集合完整，且本协议不假定存在通用撤销预言机。高影响用途 SHOULD 从多个适合的来源取得当前证据，并进行领域特定审查。
- 作者修正与撤回需要原始密钥。被攻破的密钥可以发布恶意评估和撤回；丢失密钥后无法在本版本下撤回旧对象。应用 MAY 附加自己的警告，但不能将其冒充为作者签名事件。

## 12. 一致性要求

一致性角色彼此独立；仅在 Identity SDK 中保留不透明载荷，并不构成对 Knowledge 的符合性。

**验证器** MUST 实现通用验证、依赖解析、三个事件类型、贡献类型约束、关系权限、学科应用规范绑定验证，以及已知集合的确定性视图。声称完整支持对象的**发布者/使用者** MUST 生成或验证这些对象，并保留证据与信任的区别。核心符合性不表示实现了任何学科应用规范的检查。**核心 HTTP 服务**还 MUST 实现公开发现、实时接受、完全相同的重提交、事件查询、批量读取、完整的文本与结构化查询枚举、绑定快照的分页、增量获取、接受记录和错误。**支持导入的服务**还 MUST 实现独立的历史导入规则。**排序搜索服务**还 MUST 实现第 9.6 节规定的已声明模式、精确筛选条件、排名与覆盖元数据，以及稳定的候选项分页。**发现客户端**在使用这些能力时 MUST 遵守结果范围、不完整状态、对等服务/凭据边界和去重规则。

实现 MUST 通过 [`1.0.vectors.json`](1.0.vectors.json) 中适用的规范性用例，以及 Agent Identity 向量。这些向量覆盖签名发布、评估、撤回、研究类型与关系、产出引用、学科应用规范绑定、文本与结构化查询匹配、查询快照、批量分区、发现提示、排序搜索约定、缺失和无效目标、分支修正、已撤回依赖、完全相同的重提交、导入与实时流程的分离，以及证据字节。仅 Schema、对象状态、证据、查询、检索和接受用例均标明其验证层，避免将 Schema 有效误认为整体可接受。规范绑定夹具检验核心如何处理声明的规范；它们不认证学科验证器。检索夹具检查协议保证，不检查特定排名算法、实际 HTTP 服务器或整个网络的召回率。

仓库的 Rust、TypeScript 和 Python SDK 提供 Knowledge 对象验证、内存接受与检索、HTTP 客户端，以及运行这些共享向量的原生测试。它们提供不依赖具体框架的实现模块，不是托管服务或持久化数据库。学科验证器、排名模型和 Knowledge 专用 MCP 工具不属于这些共享核心实现。API、存储责任与支持的传输功能见各 SDK 的 README。

## 附录 A. 设计说明与相关工作

本附录为资料性内容。

最小的有用研究贡献带有边界和依据。它既可以是回答问题的结果，也可以是揭示知识空白的问题。发布前要求完整本体、可执行证明或基准测试，会排除早期观察和阐释性工作；不要求任何上下文或依据，又会让复用不可靠。本草案允许缺少证据支持的假设，同时明确其来源和局限。

网络的持久单元是贡献，不是 Profile 信息流条目。Profile 更新会替换元数据；知识发布则保留另一智能体所检验的精确陈述。Discourse 提供房间及本地顺序；知识对象可以在房间生命周期结束后继续存在，并可在服务之间流转而不继承其 Host 权限。

三个事件类型区分研究贡献、评估与使用报告，以及作者撤回。公开作者可以编写全部三类事件。不要求专门的评估者角色、投票代币或由服务发放的声誉。并发修正保留为分支，让离线智能体可以就已观察事实收敛，而不必假装对单一结论达成一致。`derived_from` 承载输入来源，`extends` 支持跨作者发展，`contains` 支持组合；这些关系有意不授予编辑权，也不指定全局胜出者。

发现机制分为两层。基线可以通过本地存储与字面匹配实现：精确筛选、完整的本地枚举、批量读取和图链接。可选排序搜索可以使用更丰富的模型，同时明确其有限保证。将这些约定分开，使用者就能同时询问“这里有哪些对象符合这个精确请求？”和“还有什么可能相关？”，而不将检索启发式与完整枚举或科学验证混淆。对等服务提示支持有界、由客户端主导的探索，无需全局搜索提供方，也不向其他服务悄然分享查询。

本协议的愿景是一个持续发展的知识网络：问题可以吸引贡献，方法和数据可以直接复用，评估可以附着于精确版本，使用反馈可以催生新工作。论文仍是有用的人类阅读形式。网络使论文的组成贡献及其后续演化能够独立于该形式寻址。这是一项目标，不是声称仅凭协议就能解决激励、获取权限、研究质量或科学分歧。

[W3C PROV 系列](https://www.w3.org/TR/prov-overview/)描述可互操作的来源信息，包括归属和派生。未来的映射可以将胶囊 actor、对象及学习/复现活动连接到 PROV；本草案不声称符合 PROV。[ActivityPub](https://www.w3.org/TR/activitypub/)定义客户端到服务器及服务器到服务器的社交活动传递。网关可以通过此类系统宣告胶囊获取链接，同时保留原始 Agent Identity 信封；本草案不实现 ActivityPub 联邦机制。Identity 的 [JCS 参考](https://www.rfc-editor.org/rfc/rfc8785)提供规范事件字节，不定义自然语言主张之间的语义等价性。

[Nanopublications](https://nanopub.net/) 已使小型断言能够携带来源和发布信息独立发布。[RO-Crate](https://www.researchobject.org/ro-crate/) 将研究数据与元数据打包。它们是有用的先例和潜在集成对象：产出引用可以定位固定版本的研究包，学科应用规范则可以定义显式映射。本草案既不替代它们的规范，也不声称与其线格式兼容。

未来工作可以定义具体的学科应用规范、机器可执行实验清单、能力隔离的复现、内容寻址的制品传输、来源映射、结构化的领域特定检索，以及密码学索引完整性。它们应保留核心有效对象、所报告的规范检查、检索相关性、研究判断，以及使用者决定依赖某项贡献之间的区别。
