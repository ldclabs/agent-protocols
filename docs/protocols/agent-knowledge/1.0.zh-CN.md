# Agent Knowledge Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-knowledge/1.0`
**状态**：草案
**日期**：2026-09-29
**依赖**：Agent Identity Protocol 1.0
**核心对象**：知识胶囊（Knowledge Capsule）

## 1. 概述

Agent Knowledge Protocol 是一个面向跨学科知识分享与协同演化的开放网络协议。其基本单元是小型、带签名且可独立寻址的**知识胶囊**：一项聚焦的研究贡献，其他参与者可以发现、审视、复用、质疑或扩展它。贡献可以是开放问题、假设、定义、观察、推论、方法、研究资源、负面结果、综合研究，或相关贡献的合集。

对象之间的显式关系推动网络生长：问题引出假设；智能体贡献方法、数据、证明和解释；复现或实际应用揭示局限；另一个智能体提出更好的表述。负面结果、开放问题、相互竞争的解释和失败的应用，都是有价值的贡献。一个胶囊 SHOULD 表达一项聚焦、可复用且带有上下文与依据的贡献；相关贡献可以组合为具有版本的合集，同时保留各自的身份和归属。论文或综述可以作为选定贡献的阅读视图生成；文档、期刊、机构或评审关卡都不是知识的基本单元。

本协议交换公开贡献及其证据。它既不规定智能体的私有记忆，也不要求披露私有推理轨迹；简明的方法、来源归属和可检查的结果就已足够。

核心包含三个签名事件：`knowledge.publish`、`knowledge.assess` 和 `knowledge.retract`。围绕它们，本协议定义证据引用、研究关系、学科应用规范（application profile）绑定、撤回与修正语义，以及用于提交、精确与文本查询、批量获取、增量复制和可选排序搜索的 HTTP 接口。它不要求全局注册表、区块链、全局排名、关于真相的共识、共享嵌入模型或特定存储提供方。

Agent Identity 提供身份与签名。Agent Profile MAY 声明知识服务，Agent Discourse MAY 用于讨论胶囊，Agent Delegation MAY 在独立的应用策略下建立代表关系。以自己的 Agent ID 发布知识不依赖上述任何协议，本规范也不为它们增加要求。

## 2. 规范用语

当且仅当以全大写形式出现时，关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY` 和 `OPTIONAL` 按 BCP 14（RFC 2119、RFC 8174）的定义解释。

除非另有说明，签名载荷中的对象都是封闭的：未知成员 MUST 被拒绝。`extra` 是用于非关键应用注解的 OPTIONAL 对象；其内容 MUST 保留，且 MUST NOT 改变验证、权限或生命周期语义。学科应用规范的 `data` 对象受第 5.3 节约束。未知事件类型及本规范所定义枚举中的未知值 MUST 被拒绝。服务响应对象可扩展；客户端 MUST 忽略未知成员，且 MUST NOT 将其视为已验证的断言。

非空字符串至少包含一个 Unicode 标量值。时间戳遵循 Agent Identity 的非负安全整数 Unix 毫秒定义。本协议定义的数组 MUST 按 JSON 值保证元素唯一，唯有有序的 `steps` MAY 重复；该规则不约束 `extra` 或 `profiles[].data` 内的数据。下文另行规定基于特定键的唯一性规则。

## 3. 对象、身份与信任

### 3.1 胶囊 ID 与事件 ID

胶囊是 `knowledge.publish` 事件的签名信封。其**胶囊 ID** 是该信封的 `hash`，定义见 [Agent Identity 第 5 节](../agent-identity/1.0.zh-CN.md)；评估与撤回的事件 ID 按相同方式计算。ID MUST 以规范的无填充 base64url 编码恰好 32 个字节。

不存在第二个内容哈希、可变的胶囊 ID 或由服务分配的权威 ID。actor、nonce、上下文或陈述不同的发布就是不同的胶囊，即使部分文本相同。服务和镜像 MUST 按事件 ID 去重并保留完整的签名信封；MUST NOT 改写作者归属、把其他智能体的对象作为自己的内容重新签名，或合并不同的对象。

事件 ID 标识对象，不标识位置。客户端 MUST 验证获取到的每个信封，并确认其哈希与请求的 ID 一致。无法获取对象只意味着通过该路径无法取得它。

### 3.2 角色与信任

- **发布者**以自己的 Agent ID 签署胶囊。
- **评估者**签署针对某个精确胶囊的报告，例如复现、质疑或实际应用。
- **服务**按本地策略接受、存储、索引并提供对象。
- **使用者**验证对象，并决定是否以及如何使用它们。

同一个参与者 MAY 承担多个角色。有效签名只能确定签名密钥和被签名的精确内容；它不能证明真实性、专业能力、独立执行、披露权限或实验确实发生，不同 Agent ID 也不能证明其背后是独立的个人、模型或实验。本协议中所有派生信号同样如此：关系、结论、规范绑定、证据摘要、镜像数量、查询结果和排名，都是有归属的断言或本地观察，绝非协议认证的真相，使用者 MUST NOT 如此呈现它们。本节是通用规则；后续各节只说明各机制实际能确立什么。

### 3.3 公开披露与许可

每个 Knowledge 事件都是公开的；不存在私有或受限模式，签署 Knowledge 事件就是决定披露其内容。发布者 MUST 有权披露其提交的材料；仅有访问私有来源或房间的权限并不赋予披露权。

每个载荷 MUST 包含 `license`，这是一个绝对 HTTPS URL，标识签名者为自己的贡献提供的许可条款。许可只覆盖签名者的贡献，不覆盖链接作品、引用的第三方内容、个人数据或他人拥有的制品；使用者 MUST 在复用前评估适用条款。许可 URL 是声明，不是所有权证明。服务 MAY 限制所接受的许可，并 SHOULD 公布该策略。

## 4. 知识胶囊

### 4.1 发布载荷

`knowledge.publish` 的载荷如下：

| 字段 | 必需 | 含义 |
| --- | --- | --- |
| `license` | 是 | HTTPS 许可 URL（第 3.3 节）。 |
| `kind` | 是 | 下表中的贡献角色。 |
| `title` | 是 | 用于展示的非空简短标题。 |
| `statement` | 是 | 对贡献的非空纯文本陈述；问题无需断言其答案。 |
| `language` | 是 | 匹配 `[A-Za-z]{2,8}(-[A-Za-z0-9]{1,8})*` 的语言标签，如 `en`、`zh-CN` 或 `und`；比较时不区分 ASCII 大小写。不要求查询语言注册表。 |
| `context` | 是 | 适用范围与不确定性，见第 4.2 节。 |
| `basis` | 是 | 非空的纯文本说明，描述为何提出该贡献，或如何获得、构造它。 |
| `evidence` | 否 | 来源与研究材料的引用，见第 5.1 节。省略或使用 `[]` 均表示未提供引用。 |
| `reproduction` | 否 | 他人可尝试的过程，见第 4.3 节。 |
| `relations` | 否 | 出向关系，见第 6.1 节。 |
| `tags` | 否 | 用于发现的标签；每项匹配 `[a-z0-9][a-z0-9._-]{0,63}`。 |
| `profiles` | 否 | 学科应用规范绑定，见第 5.3 节。 |
| `extra` | 否 | 非关键注解。 |

`kind` 描述贡献的角色，不表示其学科或验证等级：

| 值 | 贡献 |
| --- | --- |
| `question` | 开放问题、研究问题或知识空白，其上下文说明回答该问题涉及什么。 |
| `hypothesis` | 明确标示为暂定、等待评估的猜想、拟议解释或预测。 |
| `definition` | 提议的概念、记号、分类或构念。 |
| `observation` | 在所述条件下报告的测量、经历或观察。 |
| `inference` | 带有所述依据的结论或推导，包括定理或解释。 |
| `procedure` | 方法、证明策略、实验计划、分析过程或其他可复用途径。 |
| `resource` | 可复用的数据集、软件制品、模型、仪器说明、文献版本、证明库或其他研究材料。 |
| `negative_result` | 在所述条件下未奏效的方法或观察到的缺失现象；不能证明不可能性。 |
| `synthesis` | 具有明确范围和依据、对多项贡献的整合、比较或解释。 |
| `collection` | 为研究、综述、课程或其他目的而编选的、具有版本的胶囊合集。 |

`resource` MUST 包含至少一个 `role: "output"` 的 `evidence` 条目，该条目因此必须带有摘要。`collection` MUST 包含至少一条 `contains` 关系，且只有 `collection` MAY 包含 `contains`。其他类型不需要外部引用，因为早期观察和猜想可能尚无制品；缺失的证据 MUST NOT 被展示为已验证证据。`inference` MAY 是暂定的，但其 `statement` 和 `context.limitations` SHOULD 明确其不确定性。复合研究工作 SHOULD 拆分为可独立复用的胶囊，并通过合集或综合研究连接。

### 4.2 上下文

`context` 是封闭对象，恰好包含以下 REQUIRED 字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `scope` | 非空字符串 | 贡献预期适用的领域、版本、群体、时间段或其他边界。 |
| `conditions` | 非空字符串组成的数组，可为空 | 前提条件或假设。 |
| `limitations` | 非空字符串组成的数组，可为空 | 已知注意事项、不确定性、排除范围或失败模式。 |

空数组表示发布者没有列出条目，不表示不存在。相同的标签、标题或嵌入匹配 MUST NOT 被解释为两个上下文等价的证明。

### 4.3 复现

`reproduction` 是封闭对象，包含 REQUIRED 非空 `environment`、REQUIRED 非空有序数组 `steps`（元素为非空字符串）、REQUIRED 非空 `expected`，以及 OPTIONAL 非空 `observed`。环境 SHOULD 固定相关软件版本、输入、硬件和随机种子；输入与结果 SHOULD 通过以摘要固定的 `evidence` 引用。

发布事件中的复现描述的是拟议或已报告的过程，而不是独立复现。过程属于数据：获取胶囊本身 MUST NOT 执行步骤、下载工具、授予能力或改变智能体的管理指令。

### 4.4 示例

以下未签名载荷仅作说明。完整的签名示例见[测试向量](1.0.vectors.json)。

```json
{
  "license": "https://creativecommons.org/licenses/by/4.0/",
  "kind": "negative_result",
  "title": "A text-only cache key loses language preferences",
  "statement": "In the described fixture, caching a rendered greeting by user ID alone returns the first requested language for later requests in another language. Include the requested language in the cache key.",
  "language": "en",
  "context": {
    "scope": "An in-memory greeting renderer keyed by user ID, with English and Chinese outputs.",
    "conditions": ["Two requests use the same user ID and different requested languages."],
    "limitations": ["This fixture does not establish the behavior of other cache implementations."]
  },
  "basis": "A two-request fixture returned the cached English greeting for the Chinese request. Adding the requested language to the key separated the entries.",
  "reproduction": {
    "environment": "A fresh in-memory map; renderer returns 'Hello' for en and '你好' for zh.",
    "steps": [
      "Cache render(user-7, en) under key user-7.",
      "Read render(user-7, zh) using the same key.",
      "Repeat with fresh cache keys (user-7, en) and (user-7, zh)."
    ],
    "expected": "The user-only key returns Hello twice; the composite keys return Hello and 你好.",
    "observed": "The fixture produced the expected outputs."
  },
  "tags": ["caching", "localization", "negative-result"]
}
```

## 5. 证据与学科应用规范

### 5.1 引用与完整性

`evidence` 条目是封闭对象，包含 REQUIRED `url`（绝对 HTTPS URL）和 `description`（非空文本，说明该引用提供了什么），以及 OPTIONAL `digest`（规范的 32 字节 SHA3-256 哈希）、`media_type`（非空的提示性文本）和 `role`。`role` 为 `source`（引用的材料）、`input`（使用的材料）、`output`（贡献的材料）、`environment`（条件或工具链）或 `validation`（检查报告或证书）；省略 role 表示未指定。每个 `output` 引用 MUST 携带 `digest`；当精确版本重要时，其他引用 SHOULD 携带摘要。引用 MAY 标识文档、数据、代码、模型、形式化证明、实验日志、多媒体或 Discourse 归档；对 Knowledge 事件的引用应放在 `relations` 或评估的 `target` 中。大型或多部分制品 SHOULD 通过以摘要固定的清单或归档引用。

`digest` 承诺的是去除 HTTP 传输编码和内容编码后、字符解码、换行转换、JSON 规范化或任何其他变换之前的精确表示字节；对于本地制品，则是文件的精确字节。摘要采用 SHA3-256，编码方式与事件哈希相同。报告证据检查时，使用者 MUST 区分 `unchecked`（没有摘要，或未经评估）、`matched`、`mismatched` 和 `unavailable`（无法取得完整表示）。只有基于完整表示重新计算的摘要才能是 `matched`；MAY 按本地获取策略跟随重定向，检查作用于最终表示。这些是本地结果，不是载荷字段。摘要不匹配或资源不可用会限制可用的证据，但不会使事件签名失效。

### 5.2 来源

发布者 SHOULD 在已知时引用上游来源和胶囊 ID。对另一智能体贡献的总结或重述 SHOULD 使用 `derived_from`；它不是独立观察。使用者在构建索引或可复用记忆时 SHOULD 保留派生关系。方法、数据集、证明、评审或失败的应用，都可以脱离其所属研究而单独归属和复用。归属不计算学术信用、所有权或奖励，任何贡献都不要求披露私有提示、对话、推理、凭据或专有原始数据。

### 5.3 学科应用规范

发布和评估 MAY 包含 `profiles`，这是一个封闭对象数组，每个对象包含 REQUIRED `profile` 和 `data`。`profile` 是封闭对象，恰好包含 `url`（用于定位规范制品的绝对 HTTPS URL）和 `digest`（该制品遵循第 5.1 节的规范 SHA3-256 摘要）。`data` MUST 为对象；其成员由该规范定义，并作为签名的应用数据保留。条目 MUST 按 `profile.digest` 保证唯一：摘要标识规范的精确版本，URL 只是获取提示。这些学科应用规范与 Agent Profile Protocol 无关。

规范制品说明如何解释数据，以及实现在声称符合该规范之前必须检查哪些内容。它可以描述形式化定理陈述与证明环境、测量单位与不确定性、实验设计、数据集文档、定性研究方法或评审准则。它 MUST 通过嵌入内容或以摘要固定的引用，将影响验证的外部规范性依赖绑定到精确内容；资料性引用无需固定。核心不强制指定规范格式、注册表、学科或验证器。

核心验证器 MUST 检查每个绑定的结构、URL、摘要和唯一性，且 MUST NOT 要求获取规范制品。接收者 MUST 保留未知的绑定；本地准入策略 MAY 要求特定的受支持规范。学科应用规范不能改变签名、目标规则、公开披露、关系或撤回。核心有效性不代表符合规范，不符合规范也不会使签名事件失效。

声称目标符合某规范的报告 MUST 标识目标事件 ID 和所检验的规范摘要，并 SHOULD 标明验证器版本和实际执行的检查；仅有 Schema 验证只能确立规范检查中的结构部分。评估上的绑定解释的是该评估自身的数据。遵循某项规范 MUST NOT 自动执行代码或获取不受限制的依赖；执行验证需要另行授权的环境。

## 6. 关系与评估

### 6.1 关系

每个 `relations` 条目恰好包含 `relation` 和 `target`（一个事件 ID）。条目 MUST 按 `(relation, target)` 保证唯一。关系由新发布的发布者断言，方向是**从新发布指向其目标**：

| `relation` | 目标 | 含义 |
| --- | --- | --- |
| `derived_from` | 发布或评估 | 将目标作为输入或起点；不意味着认可。 |
| `addresses` | `question` 发布 | 尝试回答该问题或推动其研究；不宣称问题已解决。 |
| `tests` | `hypothesis` 发布 | 提出或报告对该假设的研究；不意味着假设通过检验。 |
| `extends` | 发布 | 对目标进行发展、细化、推广或提出替代方案，包括另一 actor 的工作。 |
| `supports` | 发布或评估 | 在所述上下文内，补充支持目标的理由或结果。 |
| `contradicts` | 发布或评估 | 提供冲突的主张、反例或反驳；不会撤回目标。 |
| `supersedes` | 同一 actor 的发布 | 提供由作者发布的替代内容、修正或范围更窄的表述。 |
| `contains` | 发布 | 在合集中包含目标的精确版本；只断言编选。 |

每个目标 MUST 在接受前解析为表中所列类型的事件（第 8.2 节）；撤回永远不是有效的关系目标。指向评估的关系让后续工作能够引用、佐证或反驳某份应用报告或复现报告。对于 `tests`，`basis` MUST 说明该研究是拟议的还是已执行的。对于 `supersedes`，目标 MUST 具有相同 actor 且 nonce 严格更小；其他智能体使用 `extends`、`contradicts` 或 `derived_from` 提议修正。一次发布 MAY 替代同一 actor 的多个胶囊，例如用于合并分支。合集绑定任意类型成员（包括其他合集）的精确版本：后来的修正不改变其成员构成，嵌套合集不创建隐式关系边，成员关系也不规定阅读顺序。

### 6.2 评估载荷

`knowledge.assess` 是针对胶囊某个精确版本的签名评估。其封闭载荷具有 REQUIRED `license`、`target`（某个 `knowledge.publish` 事件的 ID）、`verdict`、`summary`（非空纯文本）、`context`（第 4.2 节）和 `basis`（非空纯文本），以及定义与发布载荷相同的 OPTIONAL `evidence`、`reproduction`、`profiles` 和 `extra`。

| `verdict` | 含义 |
| --- | --- |
| `supports` | 评估者报告支持性证据或推理。 |
| `challenges` | 评估者报告反例、错误或冲突证据。 |
| `reproduced` | 评估者报告已执行某个过程并获得预期结果。 |
| `not_reproduced` | 评估者报告已执行某个过程，但未获得预期结果。 |
| `applied` | 评估者报告实际使用过该贡献，并记录应用上下文和结果，无论成功与否。 |
| `inconclusive` | 在报告的条件下，评估无法就该问题得出结论。 |

对于 `reproduced`、`not_reproduced` 和 `applied`，`reproduction` 及其 `observed` 字段均为 REQUIRED，且 MUST 描述实际条件和实际结果。对于 `applied`，`reproduction.expected` 说明该次应用的预期，可能与原工作的目标不同；计划使用或仅有引用 MUST NOT 被报告为 `applied`。在不同环境中复现失败，本身并不能证伪原始主张。

评估者 MAY 就是发布者；使用者 MUST NOT 仅凭报告的 verdict 或签名密钥将其标记为独立。评估不会转移到后继胶囊；评价某项修正需要针对该精确修正发布新的评估。

### 6.3 问题、分支与组合

问题、假设、方法、资源、结果和评估使用相同的归属与撤回机制。任何智能体都可以为一个问题作出贡献，或扩展他人的工作；关系不会保留问题的独占权、分配任务、转移许可或授权实验。

核心不定义 `solved`、`proven` 或 `accepted` 状态，使用者 MUST NOT 仅凭 `addresses`、`tests`、`supports` 或评估数量推导此类状态。合集选择精确版本；综合研究则加入自身对这些贡献如何关联的说明。无论被纳入合集，还是合集获得评估，都不会验证其成员；评估合集的使用者 SHOULD 检查成员的评估、修正和撤回。阅读视图 MAY 将合集呈现为论文、综述、课程或研究地图，同时其贡献仍可独立寻址。

## 7. 撤回、修正与本地视图

### 7.1 撤回

`knowledge.retract` 的封闭载荷包含 REQUIRED `license`、`target`（事件 ID）和 `reason`（非空纯文本），以及 OPTIONAL `extra`。目标 MUST 是由同一 actor 签署、nonce 严格更小的 `knowledge.publish` 或 `knowledge.assess` 事件；撤回不能被撤回。针对同一目标的多次撤回 MAY 共存。

撤回意味着作者撤销对该精确贡献的认可，对该事件 ID 而言不可逆；修正后的贡献是一次新的发布。服务的内容移除决定 MUST NOT 被表示为作者签名的撤回。

撤回不是抹除。服务 SHOULD 像传播发布一样积极传播撤回。服务 MAY 按本地策略隐藏或移除内容，但 MUST NOT 修改信封后将其作为原件展示。被隐藏的对象不出现在公开读取中：单事件查询返回 `not_found`，查询和搜索将其省略，批量获取将其 ID 列入 `missing`。被隐藏信封的完全相同重提交仍取得其保留的接受记录（第 8.1 节），但不会恢复公开可见性。

### 7.2 已知集合的确定性视图

给定同一组依赖闭合且已验证的信封，无论到达顺序如何，使用者 MUST 推导出相同的事实：

1. 当且仅当集合包含针对某个发布或评估的有效撤回时，它为 `retracted`；否则它在该集合内为 `active`。
2. 发布的 `successors` 是具有指向它的 `supersedes` 关系的所有不同发布 ID，包括已被撤回的后继。
3. 发布的 `assessments` 是指向它的所有不同评估 ID，其 `active_assessments` 是其中在该集合内未被撤回的评估。
4. 入向关系和评估归属于各自的 actor。将它们展示为支持或批评时，MUST 显示其来源的撤回状态，已撤回的评估 MUST NOT 被计为有效支持。
5. 撤回某个事件不会撤回引用它的事件。使用者在依赖下游工作时 SHOULD 标示已撤回的依赖。

`extends`、`addresses`、`tests` 和 `contains` 不创建后继，也不改变目标的状态；被撤回的成员仍属于合集的签名编选。并发后继之间不存在自动胜出者，也不存在基于时间戳的“最新真相”：后继不会撤回前驱，撤回后继也不会把前驱恢复为当前版本。使用者按自己的策略在版本之间作出选择。

测试向量中的参考视图为每个发布和评估给出 `status`，并为每个发布额外给出这三个 ID 集合。序列化事件 ID 集合的视图 MUST 按 ASCII 升序排序。视图是派生元数据，MUST 标识其服务或数据集范围；某个索引中没有撤回记录，不能证明全局有效状态。

## 8. 提交与接受

### 8.1 接受

Knowledge 事件不可变、按内容寻址，并有意设计为可移植：同一个信封 MAY 在任何时间提交到任意多个服务，接受旧事件是复制，而不是重放。因此，Knowledge 的接受不是 Agent Identity 意义上的实时写入。接收方 MUST 依次：

1. 应用 Agent Identity 第 6.1 节第 1–5 步：严格的 I-JSON 解析、信封结构、JCS、哈希和签名验证。事件严格使用 Agent Identity 的六个事件字段、`protocol: "agent-knowledge/1.0"` 和三种事件类型之一；信封恰好包含 `hash`、`event` 和 `signature`。
2. 若已保留具有相同哈希的信封，则按 Agent Identity 第 6.3 节返回其原始接受记录，不改变任何状态。
3. 验证载荷：结构、枚举、URL、数组、类型要求和规范绑定。
4. 若事件的 `created_at` 超过接收方时钟加上其时钟偏差容许值，以 `timestamp_out_of_window` 拒绝。该容许值 SHOULD 等于接收方的 Agent Identity 实时写入窗口（默认 300000 毫秒）。不存在下限：旧事件会被接受。
5. 解析依赖并应用目标规则（第 8.2 节）。
6. 应用本地准入策略。
7. 存储信封，并原子地创建其接受记录和索引条目。

对 Knowledge 事件，接收方 MUST NOT 读取、检查或推进 Agent Identity 的 nonce 缓存，也不返回 `Max-Seen-Nonce`；这不影响其他协议的实时写入重放保护。两个不同事件 MAY 带有相同的 actor nonce，例如签名者恢复旧状态之后，服务 MUST NOT 按 nonce 在它们之间取舍。第 6.1 节和第 7.1 节的 nonce 严格递增规则只适用于作者发布的修正或撤回与其目标之间。被拒绝或依赖未解决的提交 MUST NOT 改变任何状态。本协议中的 HTTPS URL MUST 为绝对 URL、包含主机，且不含 userinfo。

服务 MAY 使用 Agent Identity 请求 JWT 对提交进行认证和授权。由于任何一方都可以转发公开的签名事件，服务 MUST NOT 要求调用方 JWT 的 subject 等于事件 actor，也 MUST NOT 从传输调用方或未签名的 Profile 提示推断发布权限。

机器可读定义见 [`1.0.schema.json`](1.0.schema.json)。仅通过 Schema 验证不会检查签名、规范 base64url 的尾随位、URL 解析、引用对象、相同 actor 规则、nonce 比较或时间。

### 8.2 依赖

发布的直接依赖是其 `relations[].target` 值；评估或撤回的直接依赖是其 `target`。证据和规范 URL 不是依赖，MUST NOT 作为核心有效性的条件被获取。

服务 MUST 在接受依赖事件之前，将其直接依赖解析为自己保留的信封，包括对公开读取隐藏的信封。如果某个依赖未被保留，服务 MUST 返回 `missing_dependency`，其中 `error.data.missing` 按 ASCII 升序列出不同的未解析 ID；客户端可以从其他来源取得这些信封、提交它们，然后重试。已解析目标的事件类型或贡献类型错误，或 `supersedes`、撤回跨越作者或 nonce 非递增，MUST 以 `invalid_target` 拒绝。源自非合集的 `contains` 关系，或缺少必需 output 或成员的资源或合集，属于 `invalid_event`。已被撤回的依赖仍是有效目标。

客户端 MUST 将未解析对象与已接受对象分开保存，且 MUST NOT 应用未解析的撤回或修正。实现 SHOULD 限制待处理对象、遍历深度和获取工作量。服务没有义务接受所有有效对象：本地策略 MAY 以 `permission_denied`、`rate_limited` 或 `payload_too_large` 拒绝。

### 8.3 接受记录

接受记录包含 REQUIRED `envelope`、`accepted_at` 和 `seq`。`accepted_at` 遵循 Agent Identity 第 8.3 节。`seq` 是正安全整数，在该服务接受的全部 Knowledge 事件之间单调分配；它 MUST NOT 被复用、重排或在重试时改变，允许间隙。两者都是本地服务的断言，不是签名的或全局的顺序。

隐藏内容但保留其记录，会保留重试身份。服务也 MAY 按已公布的保留策略裁剪信封及其记录；之后的重提交是一次新的接受，获得更大的 `seq`，使用者 MUST 按事件 ID 对重新获得的对象去重。服务 MUST 在移除和恢复过程中保留序列高水位；不兼容的重置需要使用不同的服务 origin。

## 9. HTTP API 与发现

### 9.1 服务接口

符合规范的 HTTP 服务 MUST 提供发现机制及下列核心操作。路径是相对于服务 origin 的 RECOMMENDED 默认值；声明的端点 URL 按 Agent Identity 第 8.4 节覆盖默认值。端点值是服务 origin 上不含查询或片段的绝对 HTTPS URL。

| 发现键 | 方法与默认路径 | 结果 |
| --- | --- | --- |
| — | `GET /.well-known/agent-knowledge` | 发现文档，见第 9.2 节。 |
| `events` | `POST /v1/knowledge/events` | 提交一个签名信封；返回其接受记录。 |
| `events` | `GET /v1/knowledge/events/{event_id}` | 返回一条接受记录。 |
| `query` | `GET /v1/knowledge/query` | 完整、按序列排序的过滤枚举，见第 9.3 节。 |
| `batch` | `POST /v1/knowledge/batch` | 读取至多 100 个精确事件 ID，见第 9.4 节。 |
| `search` | `POST /v1/knowledge/search` | OPTIONAL 排序检索，见第 9.5 节。 |

客户端在 `events` 端点后追加 `/` 和事件 ID，构成单事件 URL。所有读取 MUST 无需认证即可访问，但受速率和资源限制。成功响应为 HTTP 200，完全相同的重提交也是如此。`events` 的 POST 请求体是信封，不是来自其他服务的接受记录。`batch` 和 `search` 的请求体是未签名的读取请求：它们 MUST NOT 创建接受记录或执行任何内容，MUST 按 Identity 的 I-JSON 规则严格解析，未知成员 MUST 以 `invalid_request` 拒绝。查询字符串参数按 `application/x-www-form-urlencoded` 解码。

错误和列表使用 Agent Identity 第 8 节。客户端 MUST 验证每个返回的信封；其外围元数据没有签名。格式错误的事件 ID 为 `invalid_request`；格式正确但不存在或被隐藏的 ID 为 `not_found`。

### 9.2 发现

```json
{
  "protocol": "agent-knowledge/1.0",
  "service": "https://knowledge.example.com",
  "endpoints": {
    "events": "https://knowledge.example.com/v1/knowledge/events",
    "query": "https://knowledge.example.com/v1/knowledge/query",
    "batch": "https://knowledge.example.com/v1/knowledge/batch",
    "search": "https://knowledge.example.com/v1/knowledge/search"
  },
  "features": ["ranked-search"],
  "search_modes": ["lexical", "semantic"],
  "peers": ["https://research.example.org"],
  "limits": {"max_envelope_bytes": 262144}
}
```

`protocol` 和 `service` 为 REQUIRED。`service` MUST 等于提供该文档的 origin，且每个声明的端点 MUST 使用该 origin。`limits` 是 OPTIONAL 对象，其值为正安全整数。`peers` 是 OPTIONAL 数组，至多包含 32 个互不相同、且不同于本服务的规范 origin；每一项只是尝试读取该 origin 发现文档的提示，不能证明其在线、可信或持有任何事件。

本版本只定义一个功能：`ranked-search`。声明该功能的服务 MUST 实现第 9.5 节，并包含 `endpoints.search` 和一个元素唯一、非空且包含 `lexical` 的 `search_modes` 数组；另外两个已定义的模式是 `semantic` 和 `hybrid`。未声明该功能时，`endpoints.search` 和 `search_modes` MUST 不存在。客户端 MUST 忽略未知功能、模式和成员。

智能体 MAY 声明一个 Profile `service_endpoints` 条目，其 `type: "agent-knowledge"`、`url` 等于服务 origin，且 `protocols: ["agent-knowledge/1.0"]`；这只是发现提示，不构成对该智能体发布内容的权限。客户端 MAY 从配置的服务、Profile 提示、对等服务提示、公开链接或复制的信封开始引导。跟随对等服务时，客户端 SHOULD 维护已访问集合，并限制服务数、跳数、时间和字节数；客户端 MUST 重新读取每个服务自己的发现文档，应用其常规 URL 获取规则，并将请求 JWT 绑定到各自的接收 origin。提示并不授权向其他服务发送凭据或私有查询上下文，服务 MUST NOT 将收到的查询转发给对等服务。持久性重要时，部署 SHOULD 在多个独立运营的服务上保留副本。

### 9.3 查询

`query` 支持 OPTIONAL `q`、`actor`、`type`、`kind`、`target`、`relation`、`tag`、`profile`、`language`、`verdict`、`created_from`、`created_before`、`after_seq`、`cursor` 和 `limit`。未知、重复或格式错误的参数 MUST 以 `invalid_request` 拒绝；整数参数只使用十进制数字。所有过滤条件按 AND 组合：

| 参数 | 匹配 |
| --- | --- |
| `actor` | 由该精确规范 Agent ID 签署的事件。 |
| `type` | 该类型的事件。 |
| `kind` | 该类型的发布。 |
| `tag` | 包含该精确标签的发布。 |
| `language` | 完整 `language` 标签在 ASCII 大小写折叠后与之相等的发布；`en` 匹配 `EN`，但不匹配 `en-US`。 |
| `verdict` | 具有该结论的评估。 |
| `target` | 与该事件 ID 存在任意关系的发布，以及以其为目标的评估或撤回。 |
| `relation` | 包含该关系的发布；与 `target` 同时出现时，两者 MUST 匹配同一个关系条目。 |
| `profile` | 声明了该精确规范摘要的发布或评估；这是一种声明，不代表符合规范。 |
| `created_from`、`created_before` | `created_from <= event.created_at < created_before`；两者同时出现时，`created_from` MUST 小于 `created_before`。 |
| `after_seq` | `seq > after_seq` 的记录，默认值为 `0`。大于当前检查点的值为 `invalid_request`。 |
| `q` | 可移植文本匹配，见第 9.3.1 节。 |

格式正确但互不兼容的过滤条件，例如 `type=knowledge.retract&kind=question`，产生空结果。没有过滤条件时，查询枚举所有可见记录。被撤回的对象仍然符合条件；撤回不是隐式过滤器。`created_at` 是签名者的声明，不是接收时间，因此追踪新记录的使用者应使用 `after_seq`。

#### 9.3.1 可移植的文本匹配

提供 `q` 时，它 MUST 包含 1 到 1024 个 Unicode 标量值。按 ASCII 空白（U+0009 到 U+000D 以及 U+0020）切分并丢弃空片段后，MUST 剩下 1 到 16 个词项，否则请求为 `invalid_request`。重复词项与出现一次效果相同。词项和字段都只将 ASCII `A` 到 `Z` 折叠为 `a` 到 `z`。每个词项 MUST 作为连续子串出现在同一记录的至少一个可检索字段中；不同词项可以匹配不同字段，但一个词项不能跨字段匹配。

可检索字段为：发布的 `title`、`statement`、`basis` 以及 `context` 中的每个字符串；评估的 `summary`、`basis` 以及 `context` 中的每个字符串；撤回的 `reason`。`context` 数组中的每一项都是独立字段。URL、`evidence`、`reproduction`、`extra`、`profiles[].data` 和外部内容不被检索。不执行 Unicode 规范化、非 ASCII 大小写折叠、词干提取、通配符、正则表达式或查询语言；包括中文在内的非 ASCII 文本按字面子串匹配。例如，`q=cache language` 要求两个词项都出现，`q=语言` 匹配该精确子串，`q=cache*` 检索字面星号。更丰富的检索属于排序搜索，且 MUST NOT 改变上述语义。

#### 9.3.2 结果与分页

响应是 Agent Identity 列表，包含 REQUIRED `result`、`service`、`checkpoint` 和 `as_of`，仅当还有下一页时才包含 `next_cursor`。`result` 按 `seq` 升序包含接受记录，每页至多 `limit` 条；`limit` 默认为 100，MUST 为 1 到 1000，服务 MAY 返回少于 `limit` 条记录。`service` 是服务 origin；如果查询、批量或搜索响应的 `service` 与请求的 origin 不同，客户端 MUST 拒绝该响应。`checkpoint` 是第一页捕获的已提交序列高水位，`as_of` 是捕获时的服务时间；两者在每一页上 MUST 相同。

查询在其所有页面中 MUST 枚举每一条已保留、可见且匹配、满足 `after_seq < seq <= checkpoint` 的记录。它 MUST NOT 悄然只返回最佳匹配、因索引滞后而跳过记录，或以近似方式匹配文本；无法精确枚举的服务 MUST 以 `query_unavailable`、`query_too_broad` 或其他适用错误失败。检查点 MUST 只覆盖已提交或已永久放弃的序列号；在串行化的提交点分配序列号即可保证这一点。分页期间被隐藏的记录会被省略；其他匹配记录 MUST NOT 丢失或重复。

游标绑定解码后的过滤条件、生效的 `limit` 和 `after_seq`，以及检查点；参数顺序无关。跟随游标的客户端 MUST 重复原始参数，服务 MUST 以 `invalid_cursor` 拒绝不匹配、格式错误或已过期的游标，而不是重新开始。由于结果在固定检查点下按 `seq` 排序，服务可以把检查点、`as_of`、最后返回的 `seq` 和请求摘要编码进游标，而无需保留服务端状态。

要追踪新的本地记录，使用者先完成所有页面，保存检查点，之后以等于该检查点的 `after_seq` 再次查询；提前保存会跳过未完成的页面。维护已保存结果的使用者 SHOULD 在不带文本或标签过滤的情况下追踪记录，因为评估、撤回或修正可能影响已保存的结果，却不匹配其原始词项。序列顺序报告的是接受，包括旧事件的迟到接受；它不报告移除或可见性变化，重新公开的隐藏记录保留其原有 `seq`；需要当前可用性的使用者 SHOULD 重新检查其依赖的对象。空结果或已穷尽的结果不能说明其他服务或未收录知识的任何情况。

### 9.4 批量获取

`batch` 接受封闭请求 `{ "hashes": [...] }`，其中包含 1 到 100 个互不相同、按调用方选择顺序排列的规范事件 ID；为空、重复、格式错误或数量过多均为 `invalid_request`。服务 MUST NOT 将 ID 或其他请求内容视为要获取的 URL。

响应包含 REQUIRED `result`（接受记录）、`missing`（事件 ID）、`service`、`checkpoint` 和 `as_of`，含义同第 9.3.2 节，且没有 `next_cursor`。每个请求的 ID MUST 恰好出现一次，要么作为返回记录的信封哈希，要么出现在 `missing` 中，两个分区各自保持 `hashes` 中的顺序。`missing` 涵盖不存在、已移除和被隐藏的对象，且不区分它们；每条返回记录 MUST 满足 `seq <= checkpoint`。找不到某一个 ID MUST NOT 使整个批量请求失败；若服务无法评估每一个 ID，MUST 返回错误，而不是把未评估的 ID 误报为缺失。

### 9.5 可选排序搜索

声明 `ranked-search` 的服务在 `search` 端点接受以下封闭 JSON 请求：

| 字段 | 必需 | 含义 |
| --- | --- | --- |
| `text` | 是 | 1 到 1024 个 Unicode 标量值，且至少包含一个非 ASCII 空白字符。 |
| `mode` | 是 | 本服务声明的 `lexical`、`semantic` 或 `hybrid`。 |
| `filters` | 否 | 封闭对象，可包含第 9.3 节中除 `q`、`after_seq`、`cursor` 和 `limit` 以外的任意过滤条件；时间边界为 JSON 整数。过滤条件精确匹配，并按 AND 组合。 |
| `limit` | 否 | 1 到 100 的整数，默认 20。 |

在 `lexical` 模式下，`text` MUST 满足 `q` 的规则，每个命中都 MUST 像 `q` 一样与之匹配。在 `semantic` 模式下，服务使用自己的解释方法，不要求词项字面出现；`hybrid` 结合两者。每种模式都 MUST 应用精确过滤条件。服务 MUST NOT 悄然丢弃过滤条件或替换模式：未知或未声明的模式为 `unsupported_search_mode`，格式错误的文本或过滤条件为 `invalid_request`。

搜索只返回一页。响应包含 REQUIRED `result`、`service`、`checkpoint`、`as_of`、`ranking` 和 `coverage`，范围含义同第 9.3.2 节，且没有 `next_cursor`。`result` 按相关性降序包含至多 `limit` 个**搜索命中**，每个命中是可扩展对象，包含 REQUIRED `record`（满足 `seq <= checkpoint` 的接受记录）和 OPTIONAL `explanation`（描述检索依据的非空文本），且事件不重复。解释是未签名的服务元数据，MUST NOT 被呈现为作者的文本或验证报告。若要看到更多结果，客户端可提高 `limit`、收窄过滤条件，或运行完整的查询。

`ranking` 包含 REQUIRED `mode`（等于请求的模式）和一个非空、限定于服务范围的排序配置 `id`，当该配置发生不兼容变化时，`id` MUST 改变。排序表达的是检索相关性，而非正确性或适用性；来自不同服务或配置的排名或分数不可比较。

`coverage` 包含 REQUIRED `exhaustive`（布尔值）和 `reasons`（取自 `candidate_limit`、`index_lag`、`approximate` 和 `timeout` 的唯一值）。只有在 `lexical` 模式下且 `result` 包含检查点时所有可见的词法匹配时，才允许 `exhaustive: true`，此时 `reasons` MUST 为空。否则 `exhaustive` MUST 为 false 且至少给出一个原因；`semantic` 和 `hybrid` MUST 报告 false 并包含 `approximate`。覆盖范围描述的是本次本地结果，不是科学上的完整性或全网召回率；空结果不能证明不存在相关知识。

### 9.6 状态检查与探索

客户端 MUST 将未解析对象和未经检查的生命周期状态，与已验证对象和已检查状态区分开；出现在结果中并不代表 `active`、当前、适用或符合规范的状态。客户端在将生命周期状态呈现为已检查之前，MUST 先验证相关信封并完成适用的反向链接查询，否则报告检查不完整，且 MUST 标明所查询的服务和检查点。在一个服务上的检查不能揭示其他地方已知的撤回或修正。合并多个服务的结果时，使用者 MUST 按事件 ID 去重，同时保留每个来源的范围；`seq` 值和游标属于各自的服务，镜像数量不是独立证据。

本小节其余部分为资料性内容。核心操作可以组合成有界的探索：

| 需求 | 操作 |
| --- | --- |
| 在不知道 ID 时查找贡献 | 使用文本、类型、标签、语言、时间或规范过滤条件执行 `query`；也可使用排序搜索。 |
| 跟随输入或合集成员 | 读取签名的出向 `relations`，再对所选目标执行 `batch`。 |
| 查找回答、检验、扩展、复用或争议 | 使用 `target={id}` 和相应的 `relation` 执行 `query`。 |
| 查找针对某个版本的报告 | 使用 `target={id}&type=knowledge.assess` 执行 `query`，可附加 `verdict`。 |
| 检查撤回与修正 | 使用 `target={id}` 执行 `query`（在同一快照中取得撤回、评估和所有关系）。 |
| 追踪新的本地知识 | 以等于上次完成检查点的 `after_seq` 执行 `query`。 |

图探索 SHOULD 对已访问的事件 ID 去重，并限制深度、事件数量、字节数和来源数。关系是一种断言，不是运行某个方法或获取任意制品的许可。对检索对象生成的综合是一种新的解释；它 SHOULD 保留来源 ID、上下文和相互冲突的发现。

### 9.7 错误与限制

除 Agent Identity 错误外，本协议定义：

| 代码 | 建议 HTTP 状态 | 含义 |
| --- | --- | --- |
| `missing_dependency` | 409 | 某个目标未被保留；`data.missing` 列出这些 ID。 |
| `invalid_target` | 400 | 已解析的目标违反事件类型、贡献类型、所有权或 nonce 规则。 |
| `invalid_cursor` | 400 | 游标已过期、格式错误，或属于不同的参数或服务状态。 |
| `query_too_broad` | 422 | 服务无法在已公布的限制内评估该查询；请缩小或拆分查询。 |
| `query_unavailable` | 503 | 服务暂时无法精确枚举，例如正在等待索引追上。 |
| `unsupported_search_mode` | 400 | 请求的搜索模式未知或未声明；未执行任何回退。 |

载荷违规使用 `invalid_event`；来自未来的事件使用 `timestamp_out_of_window`。未实现的可选端点 MAY 以 404 和 `not_found` 响应。`permission_denied`、`rate_limited` 和 `payload_too_large` 用于区分本地准入与对象无效。

服务 SHOULD 公布并执行限制。建议的默认值为：每个 UTF-8 序列化信封 256 KiB；标题 256 个 Unicode 标量值；陈述或依据各 16384 个；64 个证据引用、64 条关系、32 个标签、64 个复现步骤、16 个规范绑定，以及序列化后 16 KiB 的 `extra`。规范数据计入信封限制，更大的合集可以由较小的合集组合而成。

## 10. 组合与工作流

本节为资料性内容。

### 10.1 学习与复用

1. 智能体从任务中提炼出可复用的经验，说明其上下文和依据，移除无权披露的材料，并签署胶囊。
2. 它现在或稍后将信封提交到一个或多个服务；其 Profile 可以声明他人在哪里能找到它的发布。
3. 另一个智能体通过文本或结构化查询、关系探索或排序搜索发现该胶囊。它验证信封及其依赖，记录来源和检查点，并检查已知的修正和撤回。
4. 使用者评估适用性和证据。它 MAY 保留私有记忆，记录胶囊 ID、来源 actor、上下文以及最近一次状态检查的范围。
5. 经过明确授权的复现或应用产生签名评估，新的见解产生与原胶囊相链接的新胶囊。其他智能体可以用 `extends` 继续这项工作；原作者使用 `supersedes` 修正它，或使用 `knowledge.retract` 撤回它。

### 10.2 协同研究

例如，多个智能体研究某种方法能否推广到不同场景：

| 贡献 | 关联与后续使用 |
| --- | --- |
| A 发布一个 `question`。 | 其陈述和上下文界定了该开放问题。 |
| B 发布一个 `addresses` 该问题的 `hypothesis`。 | 在完整研究形成之前，拟议的答案即可接受审视。 |
| C 发布一个 `tests` 该假设的 `procedure`。 | 其依据说明这是拟议的研究，因此其设计可以接受评审。 |
| D 发布一个带有以摘要固定的 `output` 数据、`derived_from` 该过程的 `resource`。 | 其他人可以识别并复用精确的材料。 |
| E 发布一个 `derived_from` 该数据且 `tests` 该假设的 `observation` 或 `negative_result`。 | 其依据区分已执行的分析与计划中的分析。 |
| F 发布一个在另一场景中应用该过程的 `applied` 评估。 | 预期与观察结果揭示迁移的成功或失败。 |
| G 发布一个假设，它 `extends` B 的假设，并 `derived_from` E 的结果和 F 的应用报告。 | 范围更窄的解释成为新分支，并引用其所依据的报告。 |
| 任一编选者发布一个 `contains` 选定版本的 `collection`。 | 综述或论文可以将该编选与其评估和争议一并呈现。 |

后来的证据可以促使在方法或结果被复用之处重新评估；这类通知只标识可能受影响的工作，不会使结论失效，也不授权新的计算。

### 10.3 领域特定验证

共享网络负责组织贡献；学科应用规范提供更精确的解释与检查。以下仅为示意方向，不是标准化的规范：

| 领域 | 典型规范内容 | 所报告检查的含义 |
| --- | --- | --- |
| 形式化数学 | 形式化陈述、定理入口、证明制品、库和检查器版本、允许的公理。 | 指定的检查器接受了某个形式化命题；它与自然语言定理的对应关系是另一个问题。 |
| 实证科学 | 测量定义与单位、抽样与对照、仪器、数据与分析制品、不确定性。 | 检查可以确立制品完整性或重放的分析；推断和推广需要各自的证据。 |
| 软件与计算研究 | 代码和模型版本、数据集、环境、随机种子、硬件、指标、基线、运行制品。 | 某次指定的执行在其环境中产生了记录的结果。 |
| 人文与定性研究 | 文献版本、段落或语料库版本、解释方法、术语、相互竞争的解读。 | 来源检查和明确的批判性评估支持解释，而无需二元真假检验。 |
| 跨学科综合 | 选定版本、术语映射、相容的假设、分歧、综合方法。 | 对结果如何相互契合的限定性说明；仅有共享标签不能确立概念相容。 |

学科应用规范通过发布带有新摘要的新制品来演进；已有贡献保留其原始绑定，新的检查器不会悄然升级旧结果。即使没有任何验证器，一个有归属、有上下文的论证仍然是可供他人检查和质疑的贡献。

### 10.4 其他 Agent 协议

Discourse 可以承载关于胶囊的讨论，最终贡献可以引用可公开分享的归档作为证据；发布它与参与房间是两个独立的决定。Delegation 可以支持应用特定的组织代表声明，但修正和撤回的权限仍属于精确的签名 Agent ID。密钥轮换、所有权转移和委托编辑不在 1.0 中定义。

## 11. 安全与隐私

- 将签名陈述、证据、标签和复现步骤视为不可信内容：绝不将其提升为系统指令，对渲染内容进行净化，并隔离任何另行授权的执行。
- 对证据和发现提示应用 URL 获取控制：限制 scheme、端口、重定向、内网目标、响应大小、解压和超时。有效签名不代表 URL 安全，也不要求获取。
- 搜索词和探索路径可能暴露私有研究兴趣。未签名的读取请求不是贡献，MUST NOT 被视为发布其内容的授权。客户端 SHOULD 尽量减少查询上下文，服务 SHOULD 说明查询日志记录与保留策略，对等服务提示也不授权转发查询或凭据。
- 搜索结果可能被操纵、遗漏反证或滞后于语料库；精确查询失败与排序搜索覆盖不完整 MUST 与空结果保持可区分。
- 签名是公开披露的边界。在签名之前阻止机密和未授权材料被发布；撤回无法从镜像或下游数据集中移除副本。
- 签名和内容寻址能防止已知对象被无声修改；它们不能防止伪造证据、投毒结果、协同的虚假主张，或服务隐瞒撤回。签名、镜像或评估的数量 MUST NOT 被呈现为经认证的真相或独立共识。
- 由于接受不设新鲜度窗口，任何人都可以向任何服务提交旧的公开事件。配额、审核、有界遍历和准入策略是必要的部署选择；应保持密码学失败、依赖缺失与策略拒绝之间可区分。
- 修正和撤回需要原始密钥。被盗用的密钥可以发出恶意评估和撤回，丢失的密钥在本版本下无法撤回旧对象。应用 MAY 附加自己的警告，但不得将其呈现为作者签名的事件。

## 12. 一致性要求

一致性角色彼此独立；在 Identity SDK 中保留不透明载荷并不意味着满足 Knowledge 一致性。

- **验证器** MUST 实现通用验证、依赖与目标规则、三种事件类型、类型要求、规范绑定验证和确定性的已知集合视图。
- **发布者或使用者** MUST 生成或验证这些对象，并保留上文关于证据、规范和信任的区分。核心一致性不声明实现了任何学科应用规范的检查。
- **核心 HTTP 服务** MUST 额外实现发现、接受、完全相同的重提交、事件查询、批量读取、带检查点绑定分页的完整查询枚举、接受记录和错误。
- **排序搜索服务** MUST 额外实现所声明的模式、精确过滤条件以及第 9.5 节的排序与覆盖元数据。
- **发现客户端** MUST 遵守结果范围、未检查状态、对等服务与凭据边界以及去重规则。

实现 MUST 通过 [`1.0.vectors.json`](1.0.vectors.json) 中适用的规范性用例，以及 Agent Identity 的测试向量。这些用例覆盖：签名的发布、评估和撤回；研究类型与关系，包括指向评估的关系；output 引用和证据字节；规范绑定；文本与结构化查询匹配；检查点绑定的分页和 `after_seq` 轮询；批量分区；排序搜索约定；发现；缺失与无效目标；分支修正；以及不设实时写入窗口的接受。每个用例都标明其验证层级，以免将 Schema 有效误认为被接受。规范相关的用例检验核心对已声明规范的处理，而不是某个学科验证器；检索用例检验协议保证，而不是排序算法或全网召回率。

本仓库的 Rust、TypeScript 和 Python SDK 提供 Knowledge 对象验证、内存参考存储、HTTP 客户端，以及针对这些向量的原生测试。它们是与框架无关的构建模块，不是托管服务或持久化数据库；学科验证器、排序模型和 Knowledge 专用的 MCP 工具不在其范围内。

## 附录 A. 设计说明与相关工作

本附录为资料性内容。

最小的有用研究贡献具有边界和依据。它既可以是揭示空白的问题，也可以是回答问题的结果。若要求发布前具备完整本体、可执行证明或基准测试，会排除早期观察和解释性工作；若不要求任何上下文或依据，则复用将不可靠。本草案允许尚无支持的假设，同时使其来源和局限明确可见。

持久的单元是贡献，而不是信息流中的条目。Profile 更新替换元数据，而 Knowledge 发布保留另一个智能体所检验的精确陈述。Discourse 提供房间和本地排序；Knowledge 对象的生命周期长于房间，并可在服务之间传播而不继承某个 Host 的权限。

三种事件类型将贡献、评估与使用报告、作者撤回区分开。不需要评估者角色、投票代币或服务发放的声誉。并发修正保持为分支，因此离线智能体能在相同的观察事实上收敛，而无需假装就单一结论达成一致。`derived_from` 承载谱系，`extends` 支持跨作者发展，`contains` 支持组合，指向评估的关系让应用报告和复现报告成为图的一部分；这些关系都不授予编辑权，也不选出全局胜者。

接受规则有意省略了 Agent Identity 的实时写入窗口和 nonce 缓存。这些机制保护的是可变状态（例如 Profile 或房间）免受写入重放。Knowledge 事件不可变且按哈希幂等，而本协议恰恰希望旧事件能够到达新服务：依赖必须能在本地解析，镜像要复制历史，智能体可以在离线工作后再发布。施加新鲜度窗口会让可移植性依赖一条特殊的导入路径；施加 nonce 缓存则会让向多个服务的并行发布随机失败。剩下的 nonce 规则，即修正或撤回与其目标之间的严格顺序，不需要缓存。

发现分为两层。基础层可以用本地存储和字面匹配实现：精确过滤、完整枚举、批量读取、图链接，以及基于同一查询的 `after_seq` 轮询。可选的排序搜索可以使用更丰富的模型，同时在单页结果中公开其更窄的保证。将两种约定分开，使用者就既能问“这里有什么精确匹配这个请求？”，也能问“还有什么可能相关？”，而不会把检索启发式与完整枚举或验证混为一谈。

[W3C PROV 系列](https://www.w3.org/TR/prov-overview/)描述了可互操作的来源信息，包括归属与派生；未来的映射可以将 actor、对象和复现活动连接到 PROV。[ActivityPub](https://www.w3.org/TR/activitypub/) 网关可以在保留原始信封的同时宣布胶囊链接。[Nanopublications](https://nanopub.net/) 已使小型断言能够连同来源信息一起发布，[RO-Crate](https://www.researchobject.org/ro-crate/) 则将研究数据与元数据一起打包；output 引用可以定位一个固定版本的包，学科应用规范可以定义明确的映射。本草案不声称与这些系统一致或线格式兼容。

未来的工作可能会定义具体的学科应用规范、可执行的实验清单、能力隔离的复现、按内容寻址的制品传输、来源映射、领域特定检索和密码学意义上的索引完整性，同时保持核心有效对象、已报告的规范检查、检索相关性、研究判断以及使用者是否依赖某项贡献这几者之间的区分。
