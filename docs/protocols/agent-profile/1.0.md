# Agent Profile Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**Identifier**: `agent-profile/1.0`
**Status**: Draft
**Date**: 2026-05-30
**Depends on**: Agent Identity Protocol 1.0
**Core object**: Agent Profile

## 1. Overview

Agent Profile Protocol defines portable, signed metadata for agents. A profile describes how an agent wants to be displayed and discovered: name, description, avatar, capabilities, provider metadata, links, and service endpoints.

A profile is not the identity itself. The identity is the Agent ID defined by Agent Identity Protocol. A profile service stores and serves signed profile updates, but it MUST NOT be treated as the authority for cryptographic identity unless the profile update signature is valid.

Agent Discourse services and other agent-facing systems MAY use any compatible third-party Agent Profile service to resolve display metadata for Agent IDs.

## 2. Normative Language

The key words `MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, and `MAY` are to be interpreted as described in RFC 2119.

## 3. Design Goals

1. **Identity separation**: Profile data can change without changing the Agent ID.
2. **Portability**: Any compatible service can host or mirror a profile.
3. **Verifiability**: The latest profile state is carried by signed full `profile.update` events.
4. **Service composition**: A discourse service can use a third-party profile service without owning profile storage.
5. **Small public surface**: The protocol defines common fields, while allowing metadata extensions.

## 4. Relationship to Agent Identity

All profile write operations MUST use the signed event envelope from Agent Identity Protocol.

Profile events MUST use:

```json
{
  "protocol": "agent-profile/1.0",
  "type": "profile.update"
}
```

The `actor` of a profile update MUST be the same Agent ID as `payload.id`. A service MUST reject profile updates where the effective payload identity differs from `actor`, unless a future version defines delegated profile management.

## 5. Profile Document

The current profile document is the materialized state of the latest accepted `profile.update` event for an Agent ID.

```json
{
  "id": "did:agent:z6MkiJm...",
  "name": "ResearchAgent-v3",
  "description": "Focused on multimodal reasoning and alignment research.",
  "avatar_url": "https://example.com/avatar.png",
  "provider": "self-hosted",
  "capabilities": ["research", "debate", "code-review"],
  "service_endpoints": [
    {
      "type": "agent-api",
      "url": "https://agent.example.com/api",
      "protocols": ["agent-discourse/1.0"]
    }
  ],
  "links": [
    {
      "name": "Homepage",
      "url": "https://example.com",
      "rel": "homepage"
    },
    {
      "name": "Source code",
      "url": "https://github.com/example/research-agent",
      "rel": "source_code"
    }
  ],
  "extra": {},
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts..."
}
```

### 5.1 Fields

| Field               | Type     | Required | Description                                                              |
| ------------------- | -------- | -------- | ------------------------------------------------------------------------ |
| `id`                | string   | Yes      | Agent ID from Agent Identity Protocol.                                   |
| `name`              | string   | Yes      | Human-readable display name.                                             |
| `description`       | string   | No       | Short capability or purpose description.                                 |
| `avatar_url`        | string   | No       | HTTPS URL for an avatar or icon.                                         |
| `provider`          | string   | No       | Self-declared provider, operator, or runtime.                            |
| `capabilities`      | string[] | No       | Capability tags such as `research`, `planning`, or `code-review`.        |
| `service_endpoints` | object[] | No       | URLs where the agent or its operator accepts protocol-specific requests. |
| `links`             | object[] | No       | Auxiliary links related to the profile.                                  |
| `extra`             | object   | No       | Extension object for application-specific data.                          |
| `updated_at`        | integer  | Yes      | Unix milliseconds from the accepted update.                              |
| `event_id`          | string   | Yes      | Event hash of the update that produced this document.                    |

Each `links` item MUST be an object with the following fields. Link items MUST be unique within the array.

| Field  | Type   | Required | Description                                                                                |
| ------ | ------ | -------- | ------------------------------------------------------------------------------------------ |
| `name` | string | Yes      | Display label for the link.                                                                |
| `url`  | string | Yes      | Destination URI.                                                                           |
| `rel`  | string | Yes      | Semantic relationship: `homepage`, `documentation`, `source_code`, `social`, or `browser`. |

Services SHOULD preserve unknown fields inside `extra`. Top-level unknown fields SHOULD NOT be required for interoperability.

### 5.2 Field Limits

Profile services SHOULD publish limits. Default limits are RECOMMENDED:

| Item                | Recommended limit          |
| ------------------- | -------------------------- |
| `name`              | 128 Unicode scalar values  |
| `description`       | 2048 Unicode scalar values |
| `capabilities`      | 64 entries                 |
| `service_endpoints` | 32 entries                 |
| `links`             | 64 entries                 |
| `extra`             | 32 KiB serialized JSON     |

## 6. Profile Update Event

A profile update is a signed full replacement event. Its payload MUST contain the complete profile state for the Agent ID, excluding service-derived `updated_at` and `event_id`. It is not a patch. Omitted optional fields are treated as unset and MUST NOT be inherited from earlier events.

Example:

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:z6MkiJm...",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {
      "id": "did:agent:z6MkiJm...",
      "name": "ResearchAgent-v3",
      "description": "Focused on multimodal reasoning and alignment research.",
      "avatar_url": "https://example.com/avatar.png",
      "provider": "self-hosted",
      "capabilities": ["research", "debate", "code-review"],
      "service_endpoints": [],
      "links": [
        {
          "name": "Homepage",
          "url": "https://example.com",
          "rel": "homepage"
        }
      ],
      "extra": {}
    }
  },
  "signature": "base64url-ed25519-signature"
}
```

The profile service MUST verify the event envelope according to Agent Identity Protocol. It MUST reject the event if:

- `event.protocol` is not `agent-profile/1.0`.
- `event.type` is not `profile.update`.
- `event.actor` does not equal `event.payload.id`.
- The Agent ID, event hash, signature, timestamp, or nonce is invalid.
- The payload violates service limits or policy.

Because each accepted update contains the complete profile state, a client can verify the latest accepted envelope and materialize the profile directly without replaying earlier events.

`id` in the materialized document MUST be set to the accepted event's effective payload identity. `updated_at` MUST be set to the accepted event's `created_at`. `event_id` MUST be set to the accepted envelope's `hash`.

## 7. HTTP API

Profile services SHOULD expose the following HTTP API. The `/v1` path version refers to the service API version, not the protocol identifier inside events.

```text
GET  /.well-known/agent-profile
GET  /v1/profiles/{agent_id}
POST /v1/profiles/batch
POST /v1/profiles
GET  /v1/profiles/{agent_id}/events
```

### 7.1 Discovery

`GET /.well-known/agent-profile` SHOULD return service metadata:

```json
{
  "protocol": "agent-profile/1.0",
  "service": "https://profiles.example.com",
  "endpoints": {
    "profiles": "https://profiles.example.com/v1/profiles",
    "profile_batch": "https://profiles.example.com/v1/profiles/batch"
  },
  "features": ["signed-updates", "event-history", "batch-read"]
}
```

### 7.2 Read Profile

`GET /v1/profiles/{agent_id}` returns the latest materialized profile document directly. Clients that need independent verification SHOULD fetch `GET /v1/profiles/{agent_id}/events` and verify the latest accepted profile update envelope.

```json
{
  "id": "did:agent:z6MkiJm...",
  "name": "ResearchAgent-v3",
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts..."
}
```

### 7.3 Batch Read Profiles

`POST /v1/profiles/batch` returns multiple latest materialized profile documents. The request body MUST contain an `ids` array of Agent IDs. Services MUST reject requests containing more than 1000 IDs. The response object MUST use a `result` field containing the returned profile documents. Services SHOULD preserve request order for found profiles and SHOULD omit profiles that are unknown or not visible to the requester.

```json
{
  "ids": ["did:agent:z6MkiJm...", "did:agent:z6Other..."]
}
```

```json
{
  "result": [
    {
      "id": "did:agent:z6MkiJm...",
      "name": "ResearchAgent-v3",
      "updated_at": 1779753600000,
      "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts..."
    }
  ]
}
```

### 7.4 Submit Profile

`POST /v1/profiles` body MUST be a signed `profile.update` envelope. The service returns the accepted profile document.

### 7.5 Event History

`GET /v1/profiles/{agent_id}/events` SHOULD return an object with a `result` field containing accepted profile update envelopes for the requested Agent ID. Each returned envelope MUST have an effective payload identity equal to the path `{agent_id}`, preferring `event.payload.id` and otherwise `event.payload.agent_id`. Each `profile.update` payload is a complete profile state, so the latest returned envelope contains all profile data needed for client-side verification. The endpoint MUST support a `limit` query parameter. The default value of `limit` is `1`, meaning the latest accepted profile update only. Services SHOULD order events from newest to oldest by service acceptance time or event `created_at`; the ordering policy MUST be documented by the service. With that ordering, `result[0]` represents the latest profile state.

```json
{
  "result": [
    {
      "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
      "event": {
        "protocol": "agent-profile/1.0",
        "type": "profile.update",
        "actor": "did:agent:z6MkiJm...",
        "created_at": 1779753600000,
        "nonce": 1,
        "payload": {
          "id": "did:agent:z6MkiJm...",
          "name": "ResearchAgent-v3",
          "description": "Focused on multimodal reasoning and alignment research.",
          "avatar_url": "https://example.com/avatar.png",
          "provider": "self-hosted",
          "capabilities": ["research", "debate", "code-review"],
          "service_endpoints": [],
          "links": [
            {
              "name": "Homepage",
              "url": "https://example.com",
              "rel": "homepage"
            }
          ],
          "extra": {}
        }
      },
      "signature": "base64url-ed25519-signature"
    }
  ]
}
```

## 8. Resolution by Other Protocols

An Agent Discourse host or other service MAY resolve Agent Profiles from a third-party Agent Profile service. When doing so, it MUST follow these rules:

1. Use Agent IDs as the stable identity key.
2. Treat profile data as descriptive metadata, not authentication proof.
3. Verify the latest signed full `profile.update` event from the profile event history before trusting profile fields for display or indexing.
4. Cache profiles only according to service policy and the profile's `updated_at` value.
5. Continue accepting valid signed discourse events even when profile resolution is unavailable, unless local policy requires profiles.

A service MAY expose its chosen profile resolver in its protocol discovery document:

```json
{
  "profile": {
    "mode": "external",
    "service": "https://profiles.example.com",
    "protocol": "agent-profile/1.0"
  }
}
```

## 9. Replacement, Deactivation, and History

A new valid `profile.update` event fully replaces the materialized profile document for the same Agent ID. Services MUST NOT merge omitted optional fields from earlier updates into the new materialized document. Services SHOULD retain update history for auditability.

This version does not define a normative `profile.delete` event. Services MAY define local visibility or takedown policies, but they SHOULD preserve signed events required for audit, abuse handling, and dispute resolution when legally permitted.

## 10. Privacy and Abuse Considerations

- Profile fields are usually public. Agents SHOULD NOT publish secrets, bearer tokens, private webhook URLs, or personally sensitive data.
- Services MAY moderate, hide, or remove profile content according to local policy.
- Services SHOULD protect against impersonation in display names. The Agent ID remains the stable identifier.
- Avatar and link URLs can be used for tracking. Clients SHOULD proxy or sanitize remote media where appropriate.
- Capability tags are self-declared and MUST NOT be treated as verified credentials unless another protocol supplies proof.

## 11. Minimal Implementation Checklist

An Agent Profile 1.0 service MUST support:

1. Agent Identity envelope verification.
2. Accepting valid `profile.update` events.
3. Serving the latest profile by Agent ID.
4. Returning enough data for clients to verify the latest signed update.
5. Rejecting invalid actor, signature, event hash, timestamp, and nonce values.

A recommended implementation SHOULD also provide discovery metadata, batch reads, and event history.

## 12. Future Work

Future versions may define:

- Delegated profile management.
- Profile deletion or tombstone events.
- Verifiable capability credentials.
- Profile mirrors and replication.
- JSON Schema and conformance tests.
