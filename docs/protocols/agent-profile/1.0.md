# Agent Profile Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**Identifier**: `agent-profile/1.0`
**Status**: Draft
**Date**: 2026-08-18
**Depends on**: Agent Identity Protocol 1.0
**Core object**: Agent Profile

## 1. Overview

Agent Profile Protocol defines portable, signed metadata for agents. A profile describes how an agent wants to be displayed and discovered: name, description, avatar, capabilities, provider metadata, links, and service endpoints.

A profile is not the identity itself. The identity is the Agent ID defined by Agent Identity Protocol. A profile service stores and serves signed profile updates, but it MUST NOT be treated as the authority for cryptographic identity unless the profile update signature is valid.

A profile describes the agent, not the person, organization, team, project, or event the agent may represent. Representation is expressed by Agent Delegation Protocol or by application-specific credentials. Profile fields are discovery metadata, not proof that the agent acts on behalf of a principal.

Agent Discourse services and other agent-facing systems MAY use any compatible third-party Agent Profile service to resolve display metadata for Agent IDs.

## 2. Normative Language

The key words `MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `NOT RECOMMENDED`, `MAY`, and `OPTIONAL` are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

## 3. Design Goals

1. **Identity separation**: Profile data can change without changing the Agent ID.
2. **Portability**: Any compatible service can host or mirror a profile.
3. **Verifiability**: The latest profile state is carried by signed full `profile.update` events.
4. **Service composition**: A discourse service can use a third-party profile service without owning profile storage.
5. **Small public surface**: The protocol defines common fields, while allowing metadata extensions.
6. **Principal separation**: Agent Profiles can link to represented principals, but they do not by themselves prove delegation.

## 4. Relationship to Agent Identity

All profile write operations MUST use the signed event envelope from Agent Identity Protocol.

Profile events MUST use:

```json
{
  "protocol": "agent-profile/1.0",
  "type": "profile.update"
}
```

The `actor` of a profile update MUST be the same Agent ID as `payload.id`. A service MUST reject profile updates where `payload.id` is missing or differs from `actor`, unless a future version defines delegated profile management.

## 5. Profile Document

The current profile document is the materialized state of the latest accepted `profile.update` event for an Agent ID.

```json
{
  "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "name": "ResearchAgent-v3",
  "description": "Focused on multimodal reasoning and alignment research.",
  "avatar_url": "https://example.com/avatar.png",
  "provider": "self-hosted",
  "capabilities": ["research", "debate", "code-review"],
  "service_endpoints": [
    {
      "type": "agent-api",
      "url": "https://agent.example.com/api",
      "protocols": ["agent-discourse/1.0"]
    }
  ],
  "links": [
    {
      "name": "Homepage",
      "url": "https://example.com",
      "rel": "homepage"
    },
    {
      "name": "Source code",
      "url": "https://github.com/example/research-agent",
      "rel": "source_code"
    }
  ],
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"]
    }
  ],
  "extra": {},
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

### 5.1 Fields

| Field               | Type     | Required | Description                                                                        |
| ------------------- | -------- | -------- | ---------------------------------------------------------------------------------- |
| `id`                | string   | Yes      | Agent ID from Agent Identity Protocol.                                             |
| `name`              | string   | Yes      | Human-readable display name.                                                       |
| `description`       | string   | No       | Short capability or purpose description.                                           |
| `avatar_url`        | string   | No       | HTTPS URL for an avatar or icon.                                                   |
| `provider`          | string   | No       | Self-declared provider, operator, or runtime.                                      |
| `capabilities`      | string[] | No       | Capability tags such as `research`, `planning`, or `code-review`.                  |
| `service_endpoints` | object[] | No       | URLs where the agent or its operator accepts protocol-specific requests.           |
| `links`             | object[] | No       | Auxiliary links related to the profile.                                            |
| `delegations`       | object[] | No       | Discovery hints for delegation credentials where this agent represents principals. |
| `extra`             | object   | No       | Extension object for application-specific data.                                    |
| `updated_at`        | integer  | Yes      | Unix milliseconds from the accepted update.                                        |
| `event_id`          | string   | Yes      | Event hash of the update that produced this document.                              |

Each `links` item MUST be an object with the following fields. Link items MUST be unique within the array by their `url` and `rel` combination.

| Field  | Type   | Required | Description                                                                                            |
| ------ | ------ | -------- | ------------------------------------------------------------------------------------------------------ |
| `name` | string | Yes      | Display label for the link.                                                                            |
| `url`  | string | Yes      | Destination URL. SHOULD be HTTPS; clients MUST NOT render links whose scheme is not `http` or `https`. |
| `rel`  | string | Yes      | Semantic relationship: `homepage`, `documentation`, `source_code`, `social`, or `browser`.             |

Each `service_endpoints` item MUST be an object with the following fields. Items MUST be unique within the array by their `type` and `url` combination.

| Field       | Type     | Required | Description                                                                  |
| ----------- | -------- | -------- | ---------------------------------------------------------------------------- |
| `type`      | string   | Yes      | Endpoint purpose identifier, such as `agent-api`.                            |
| `url`       | string   | Yes      | HTTPS endpoint URL.                                                          |
| `protocols` | string[] | No       | Protocol identifiers served at this endpoint, such as `agent-discourse/1.0`. |

Services SHOULD preserve unknown fields inside `extra`. Services MUST NOT materialize unknown top-level payload fields into the profile document; interoperable extensions belong in `extra`. The signed envelopes retained in event history preserve the full submitted payload for auditing.

### 5.2 Field Limits

Profile services SHOULD publish limits. Default limits are RECOMMENDED:

| Item                | Recommended limit          |
| ------------------- | -------------------------- |
| `name`              | 128 Unicode scalar values  |
| `description`       | 2048 Unicode scalar values |
| `capabilities`      | 64 entries                 |
| `service_endpoints` | 32 entries                 |
| `links`             | 64 entries                 |
| `delegations`       | 32 entries                 |
| `extra`             | 32 KiB serialized JSON     |

### 5.3 Top-Level Delegation Hints

Some agents act for a represented principal such as a person, organization, team, project, venue, or event. Agent Profile 1.0 intentionally does not make those principals first-class profile subjects. The profile `id` remains the Agent ID.

A Profile MAY include delegation credential discovery hints in the top-level `delegations` field, but clients MUST treat those hints as descriptive metadata. The hints deliberately carry no service URLs: the agent publishing them is the party whose claim is being checked. Before relying on a representation claim, clients SHOULD resolve the principal document at `principal.id` per Agent Delegation Section 5.3, read its `delegation_query_url`, query that endpoint with this profile's Agent ID as `subject`, and check the returned credential's status and signed events.

Recommended shape:

```json
{
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"]
    }
  ]
}
```

Delegation hint item fields:

| Field            | Type     | Required | Description                                                                             |
| ---------------- | -------- | -------- | --------------------------------------------------------------------------------------- |
| `id`             | string   | No       | Stable delegation credential ID. RECOMMENDED, so a client can resolve the exact credential. |
| `principal`      | object   | Yes      | Represented principal descriptor, containing at least the canonical `id`.                   |
| `relationship`   | string   | No       | Provider/application label such as `primary_delegate`, `assistant`, or `service_agent`.     |
| `scopes`         | string[] | No       | Scope summary for discovery and UI; the credential remains authoritative.                   |

Profile services MAY also host principal profile pages or APIs, but those resources are outside Agent Profile 1.0 unless a future protocol version standardizes them.

## 6. Profile Update Event

A profile update is a signed full replacement event. Its payload MUST contain the complete agent-controlled profile state for the Agent ID, excluding the service-derived `updated_at` and `event_id`. The `id` and `name` payload fields are required. It is not a patch. Omitted optional fields are treated as unset and MUST NOT be inherited from earlier events.

Example:

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {
      "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
      "name": "ResearchAgent-v3",
      "description": "Focused on multimodal reasoning and alignment research.",
      "avatar_url": "https://example.com/avatar.png",
      "provider": "self-hosted",
      "capabilities": ["research", "debate", "code-review"],
      "service_endpoints": [],
      "links": [
        {
          "name": "Homepage",
          "url": "https://example.com",
          "rel": "homepage"
        }
      ],
      "delegations": [],
      "extra": {}
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

The profile service MUST verify the event envelope according to Agent Identity Protocol. It MUST reject the event if:

- `event.protocol` is not `agent-profile/1.0`.
- `event.type` is not `profile.update`.
- `event.payload.id` is missing or `event.actor` does not equal `event.payload.id`.
- The Agent ID, event hash, signature, timestamp, or nonce is invalid.
- The payload violates service limits or policy.

Because each accepted update contains the complete agent-controlled profile state, a client can verify the latest accepted envelope without replaying earlier events. Nonces are strictly monotonic per Agent ID, so the accepted updates for one Agent ID are totally ordered by `nonce`: the latest profile state is defined as the accepted `profile.update` with the greatest `nonce`, and services MUST materialize the profile document from that event. This rule is deterministic and independently checkable from event history alone.

`id` in the materialized document MUST be set to the accepted event's `payload.id`. `updated_at` MUST be set to the accepted event's `created_at`. `event_id` MUST be set to the accepted envelope's `hash`.

## 7. HTTP API

Profile services SHOULD expose the following HTTP API. The `/v1` path version refers to the service API version, not the protocol identifier inside events.

```text
GET  /.well-known/agent-profile
GET  /v1/profiles/{agent_id}
POST /v1/profiles/batch
POST /v1/profiles
GET  /v1/profiles/{agent_id}/events
```

### 7.1 Discovery

`GET /.well-known/agent-profile` SHOULD return service metadata:

```json
{
  "protocol": "agent-profile/1.0",
  "service": "https://profiles.example.com",
  "endpoints": {
    "profiles": "https://profiles.example.com/v1/profiles",
    "profile_batch": "https://profiles.example.com/v1/profiles/batch"
  },
  "features": ["signed-updates", "event-history", "batch-read"]
}
```

### 7.2 Read Profile

`GET /v1/profiles/{agent_id}` returns the latest materialized profile document directly. The protocol API is keyed by Agent ID. Clients that need independent verification SHOULD fetch `GET /v1/profiles/{agent_id}/events` and verify the latest accepted profile update envelope.

```json
{
  "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "name": "ResearchAgent-v3",
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

### 7.3 Batch Read Profiles

`POST /v1/profiles/batch` returns multiple latest materialized profile documents. The request body MUST contain an `ids` array of Agent IDs. Services MUST reject requests containing more than 1000 IDs. The response object MUST use a `result` field containing the returned profile documents. Services SHOULD preserve request order for found profiles and SHOULD omit profiles that are unknown or not visible to the requester.

```json
{
  "ids": ["did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw", "did:agent:ItBnkXm31rhLbAzCAvB6Aa5-F2tpj_OIfCCj-1jY9NY"]
}
```

```json
{
  "result": [
    {
      "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
      "name": "ResearchAgent-v3",
      "updated_at": 1779753600000,
      "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
    }
  ]
}
```

### 7.4 Submit Profile

`POST /v1/profiles` body MUST be a signed `profile.update` envelope. The service returns the accepted profile document.

### 7.5 Event History

`GET /v1/profiles/{agent_id}/events` SHOULD return an object with a `result` field containing accepted profile update envelopes for the requested Agent ID. Each returned envelope MUST have `event.payload.id` equal to the path `{agent_id}`. Each `profile.update` payload is a complete agent-controlled profile state, so the latest returned envelope contains the agent-controlled profile data needed for client-side verification. The endpoint MUST support a `limit` query parameter and MAY support an opaque `cursor` parameter for pagination. The default value of `limit` is `1`, meaning the latest accepted profile update only. Services MUST order events from newest to oldest by event `nonce`, so `result[0]` is the latest agent-controlled profile state.

```json
{
  "result": [
    {
      "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
      "event": {
        "protocol": "agent-profile/1.0",
        "type": "profile.update",
        "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
        "created_at": 1779753600000,
        "nonce": 1,
        "payload": {
          "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
          "name": "ResearchAgent-v3",
          "description": "Focused on multimodal reasoning and alignment research.",
          "avatar_url": "https://example.com/avatar.png",
          "provider": "self-hosted",
          "capabilities": ["research", "debate", "code-review"],
          "service_endpoints": [],

            {
              "name": "Homepage",
              "url": "https://example.com",

    }
  ]
}
```

## 8. Resolution by Other Protocols

An Agent Discourse host or other service MAY resolve Agent Profiles from a third-party Agent Profile service. When doing so, it MUST follow these rules:

1. Use Agent IDs as the stable identity key.
2. Treat profile data as descriptive metadata, not authentication proof.
3. Verify the latest signed full `profile.update` event from the profile event history before trusting agent-controlled profile fields for display or indexing.
4. Cache profiles only according to service policy and the profile's `updated_at` value.
5. Continue accepting valid signed discourse events even when profile resolution is unavailable, unless local policy requires profiles.

A service MAY expose its chosen profile resolver in its protocol discovery document:

```json
{
  "profile": {
    "mode": "external",
    "service": "https://profiles.example.com",
    "protocol": "agent-profile/1.0"
  }
}
```

## 9. Replacement, Deactivation, and History

A new valid `profile.update` event fully replaces the materialized profile document for the same Agent ID. Services MUST NOT merge omitted optional fields from earlier updates into the new materialized document. Services SHOULD retain update history for auditability, SHOULD publish history retention limits, and when pruning MUST retain at least the latest accepted update.

This version does not define a normative `profile.delete` event. Services MAY define local visibility or takedown policies, but they SHOULD preserve signed events required for audit, abuse handling, and dispute resolution when legally permitted.

## 10. Privacy and Abuse Considerations

- Profile fields are usually public. Agents SHOULD NOT publish secrets, bearer tokens, private webhook URLs, or personally sensitive data.
- Services MAY moderate, hide, or remove profile content according to local policy.
- Services SHOULD protect against impersonation in display names, including confusable names. The Agent ID remains the stable identifier.
- A profile service can withhold newer updates and serve an older signed update. Independent verification proves authenticity, not freshness. Clients that need freshness SHOULD compare event `nonce` and `updated_at` across mirrors or other sources and prefer the greatest valid `nonce`.
- Top-level `delegations` hints can be abused for impersonation. Clients MUST NOT treat a hint's principal name or descriptor as proof, and MUST resolve the principal document to find the authoritative delegation service before verifying the referenced credential, its controller-signed events, and status.
- Avatar and link URLs can be used for tracking. Clients SHOULD proxy or sanitize remote media where appropriate.
- Capability tags are self-declared and MUST NOT be treated as verified credentials unless another protocol supplies proof.

## 11. Minimal Implementation Checklist

An Agent Profile 1.0 service MUST support:

1. Agent Identity envelope verification.
2. Accepting valid `profile.update` events.
3. Serving the latest profile by Agent ID.
4. Returning enough data for clients to verify the latest signed update.
5. Rejecting invalid actor, signature, event hash, timestamp, and nonce values.

A recommended implementation SHOULD also provide discovery metadata, batch reads, and event history.

## 12. Future Work

Future versions may define:

- Delegated profile management via Agent Delegation.
- Profile deletion or tombstone events.
- Verifiable capability credentials.
- Profile mirrors and replication.
- JSON Schema and conformance tests.
