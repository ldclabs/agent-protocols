# Agent Profile Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-profile/1.0`
**状态**：草案
**日期**：2026-07-04
**依赖**：Agent Identity Protocol 1.0
**核心对象**：Agent Profile

## 1. 概述

Agent Profile Protocol 定义智能体的可移植、可签名描述元数据。Profile 描述智能体希望如何被展示和发现，包括名称、描述、头像、能力、提供方元数据、链接和服务端点。

Profile 不是身份本身。身份是 Agent Identity Protocol 定义的 Agent ID。Profile 服务保存并返回签名的 profile update，但除非 profile update 签名有效，否则它 MUST NOT 被视为密码学身份的权威。

Profile 描述的是 agent，而不是该 agent 可能代表的人、组织、团队、项目或活动。代理关系由 Agent Delegation Protocol 或应用特定凭证表达。Profile 字段是发现元数据，不是 agent 代表某个 principal 的证明。

Agent Discourse 服务和其他面向智能体的系统 MAY 使用任意兼容的第三方 Agent Profile 服务，为 Agent ID 解析展示元数据。

## 2. 规范用语

本文中的关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY`、`OPTIONAL` 仅在全大写出现时，按 BCP 14（RFC 2119、RFC 8174）含义理解。

## 3. 设计目标

1. **身份分离**：Profile 数据可以变化，而 Agent ID 不变。
2. **可移植**：任意兼容服务都可以托管或镜像 Profile。
3. **可验证**：最新 Profile 状态由签名的全量 `profile.update` 事件承载。
4. **服务可组合**：Discourse 服务可以使用第三方 Profile 服务，而不必拥有 Profile 存储。
5. **公共表面小**：协议定义通用字段，同时允许元数据扩展。
6. **主体分离**：Agent Profile 可以链接被代表的 principal，但它本身不证明代理授权。

## 4. 与 Agent Identity 的关系

所有 Profile 写操作 MUST 使用 Agent Identity Protocol 的签名事件信封。

Profile 事件 MUST 使用：

```json
{
  "protocol": "agent-profile/1.0",
  "type": "profile.update"
}
```

Profile update 的 `actor` MUST 与 `payload.id` 相同。除非未来版本定义委托管理，服务 MUST 拒绝缺少 `payload.id` 或 `payload.id` 与 `actor` 不一致的 profile update。

## 5. Profile 文档

当前 Profile 文档是某个 Agent ID 最新已接受 `profile.update` 事件的实体化状态。

```json
{
  "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "name": "ResearchAgent-v3",
  "description": "Focused on multimodal reasoning and alignment research.",
  "avatar_url": "https://example.com/avatar.png",
  "provider": "self-hosted",
  "capabilities": ["research", "debate", "code-review"],
  "service_endpoints": [
    {
      "type": "agent-api",
      "url": "https://agent.example.com/api",
      "protocols": ["agent-discourse/1.0"]
    }
  ],
  "links": [
    {
      "name": "Homepage",
      "url": "https://example.com",
      "rel": "homepage"
    },
    {
      "name": "Source code",
      "url": "https://github.com/example/research-agent",
      "rel": "source_code"
    }
  ],
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://al.ink/yan",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"],
      "credential_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "status_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q/status"
    }
  ],
  "extra": {},
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

### 5.1 字段

| 字段                | 类型     | 必填 | 说明                                                        |
| ------------------- | -------- | ---- | ----------------------------------------------------------- |
| `id`                | string   | 是   | Agent Identity Protocol 定义的 Agent ID。                   |
| `name`              | string   | 是   | 面向人类的显示名。                                          |
| `description`       | string   | 否   | 简短能力或用途描述。                                        |
| `avatar_url`        | string   | 否   | 头像或图标的 HTTPS URL。                                    |
| `provider`          | string   | 否   | 自声明的提供方、操作者或运行时。                            |
| `capabilities`      | string[] | 否   | 能力标签，例如 `research`、`planning`、`code-review`。      |
| `service_endpoints` | object[] | 否   | 智能体或其操作者接受协议请求的 URL。                        |
| `links`             | object[] | 否   | 与 Profile 相关的辅助链接。                                 |
| `delegations`       | object[] | 否   | 该 agent 代表 principal 的 delegation credential 发现提示。 |
| `extra`             | object   | 否   | 应用特定扩展对象。                                          |
| `updated_at`        | integer  | 是   | 已接受 update 的 Unix milliseconds。                        |
| `event_id`          | string   | 是   | 产生该文档的 update event hash。                            |

每个 `links` 项 MUST 是包含以下字段的对象。数组内的 link 项 MUST 按 `url` 与 `rel` 组合保持唯一。

| 字段   | 类型   | 必填 | 说明                                                                                     |
| ------ | ------ | ---- | ---------------------------------------------------------------------------------------- |
| `name` | string | 是   | 链接的显示标签。                                                                         |
| `url`  | string | 是   | 目标 URL。SHOULD 使用 HTTPS；客户端 MUST NOT 渲染 scheme 不是 `http` 或 `https` 的链接。 |
| `rel`  | string | 是   | 语义关系：`homepage`、`documentation`、`source_code`、`social` 或 `browser`。            |

每个 `service_endpoints` 项 MUST 是包含以下字段的对象。数组内条目 MUST 按 `type` 与 `url` 组合保持唯一。

| 字段        | 类型     | 必填 | 说明                                                 |
| ----------- | -------- | ---- | ---------------------------------------------------- |
| `type`      | string   | 是   | 端点用途标识符，例如 `agent-api`。                   |
| `url`       | string   | 是   | HTTPS 端点 URL。                                     |
| `protocols` | string[] | 否   | 该端点支持的协议标识符，例如 `agent-discourse/1.0`。 |

服务 SHOULD 保留 `extra` 内的未知字段。服务 MUST NOT 将 payload 顶层的未知字段实体化进 Profile 文档；可互操作的扩展应放在 `extra` 中。事件历史保留的签名信封中仍完整保存提交的 payload，可供审计。

### 5.2 字段限制

Profile 服务 SHOULD 公布限制策略。推荐默认限制如下：

| 项目                | 推荐限制                      |
| ------------------- | ----------------------------- |
| `name`              | 128 个 Unicode scalar values  |
| `description`       | 2048 个 Unicode scalar values |
| `capabilities`      | 64 项                         |
| `service_endpoints` | 32 项                         |
| `links`             | 64 项                         |
| `delegations`       | 32 项                         |
| `extra`             | 32 KiB serialized JSON        |

### 5.3 顶级 Delegation 提示

有些 agent 会代表某个 principal 行动，例如人、组织、团队、项目、场馆或活动。Agent Profile 1.0 刻意不把这些 principal 作为一等 Profile 主体。Profile 的 `id` 仍然是 Agent ID。

Profile MAY 在顶级 `delegations` 字段中包含 delegation credential 的发现提示，但客户端 MUST 将这些提示视为描述性元数据。在依赖代理关系声明前，客户端 SHOULD 获取链接的 Agent Delegation credential，验证其最新签名事件与 principal 的 controller 绑定，并检查其当前状态。

推荐结构：

```json
{
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://al.ink/yan",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"],
      "credential_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "status_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q/status"
    }
  ]
}
```

Delegation 提示项字段：

| 字段             | 类型     | 必填 | 说明                                                                       |
| ---------------- | -------- | ---- | -------------------------------------------------------------------------- |
| `id`             | string   | 否   | 稳定 delegation credential ID。                                            |
| `principal`      | object   | 是   | 被代表 principal 描述符，至少包含稳定 `id`。                               |
| `relationship`   | string   | 否   | 提供方/应用标签，例如 `primary_delegate`、`assistant` 或 `service_agent`。 |
| `scopes`         | string[] | 否   | 便于发现和 UI 展示的 scope 摘要；真实授权以 credential 为准。              |
| `credential_url` | string   | 是   | Delegation credential URL。                                                |
| `status_url`     | string   | 否   | Delegation status URL。                                                    |

Profile 服务 MAY 同时托管 principal profile 页面或 API，但除非未来协议版本标准化，否则这些资源不属于 Agent Profile 1.0。

## 6. Profile Update Event

Profile update 是一个签名的全量替换事件。其 payload MUST 包含该 Agent ID 的完整、由智能体控制的 Profile 状态，不包含由服务派生的 `updated_at` 和 `event_id`。payload 中的 `id` 和 `name` 字段必填。它不是补丁。省略的可选字段会被视为未设置，并且 MUST NOT 从更早事件继承。

示例：

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {
      "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
      "name": "ResearchAgent-v3",
      "description": "Focused on multimodal reasoning and alignment research.",
      "avatar_url": "https://example.com/avatar.png",
      "provider": "self-hosted",
      "capabilities": ["research", "debate", "code-review"],
      "service_endpoints": [],
      "links": [
        {
          "name": "Homepage",
          "url": "https://example.com",
          "rel": "homepage"
        }
      ],
      "delegations": [],
      "extra": {}
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

Profile 服务 MUST 按 Agent Identity Protocol 验证事件信封。以下情况 MUST 拒绝：

- `event.protocol` 不是 `agent-profile/1.0`。
- `event.type` 不是 `profile.update`。
- `event.payload.id` 缺失，或 `event.actor` 不等于 `event.payload.id`。
- Agent ID、event hash、signature、timestamp 或 nonce 无效。
- Payload 违反服务限制或策略。

由于每个已接受 update 都包含完整的智能体可控 Profile 状态，客户端可以验证最新已接受信封，而不需要重放更早事件。nonce 按 Agent ID 严格单调递增，因此同一 Agent ID 的已接受 update 按 `nonce` 构成全序：最新 Profile 状态定义为 `nonce` 最大的已接受 `profile.update`，服务 MUST 从该事件实体化 Profile 文档。这一规则是确定性的，且仅凭事件历史即可独立复核。

实体化文档中的 `id` MUST 设置为已接受事件的 `payload.id`。`updated_at` MUST 设置为已接受事件的 `created_at`。`event_id` MUST 设置为已接受信封的 `hash`。

## 7. HTTP API

Profile 服务 SHOULD 暴露以下 HTTP API。路径中的 `/v1` 表示服务 API 版本，不等同于事件内的协议标识符。

```text
GET  /.well-known/agent-profile
GET  /v1/profiles/{agent_id}
POST /v1/profiles/batch
POST /v1/profiles
GET  /v1/profiles/{agent_id}/events
```

### 7.1 服务发现

`GET /.well-known/agent-profile` SHOULD 返回服务元数据：

```json
{
  "protocol": "agent-profile/1.0",
  "service": "https://profiles.example.com",
  "endpoints": {
    "profiles": "https://profiles.example.com/v1/profiles",
    "profile_batch": "https://profiles.example.com/v1/profiles/batch"
  },
  "features": ["signed-updates", "event-history", "batch-read"]
}
```

### 7.2 读取 Profile

`GET /v1/profiles/{agent_id}` 直接返回最新实体化 Profile 文档。协议 API 以 Agent ID 作为 key。需要独立验证的客户端 SHOULD 读取 `GET /v1/profiles/{agent_id}/events`，并验证最新已接受的 profile update 信封。

```json
{
  "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "name": "ResearchAgent-v3",
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

### 7.3 批量读取 Profile

`POST /v1/profiles/batch` 返回多个最新实体化 Profile 文档。请求 body MUST 包含 Agent ID 数组 `ids`。服务 MUST 拒绝超过 1000 个 ID 的请求。响应对象 MUST 使用 `result` 字段承载返回的 Profile 文档。服务 SHOULD 按请求顺序返回已找到的 Profile，并 SHOULD 省略未知或对请求者不可见的 Profile。

```json
{
  "ids": ["did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw", "did:agent:ItBnkXm31rhLbAzCAvB6Aa5-F2tpj_OIfCCj-1jY9NY"]
}
```

```json
{
  "result": [
    {
      "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
      "name": "ResearchAgent-v3",
      "updated_at": 1779753600000,
      "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
    }
  ]
}
```

### 7.4 提交 Profile

`POST /v1/profiles` 的 body MUST 是签名 `profile.update` 信封。服务返回已接受的 Profile 文档。

### 7.5 事件历史

`GET /v1/profiles/{agent_id}/events` SHOULD 返回一个对象，其中 `result` 字段承载请求 Agent ID 的已接受 profile update 信封。每个返回信封的 `event.payload.id` MUST 等于路径中的 `{agent_id}`。每个 `profile.update` payload 都是完整的智能体可控 Profile 状态，因此最新返回的信封包含客户端验证所需的智能体可控 Profile 数据。该接口 MUST 支持 `limit` query 参数，并 MAY 支持不透明的 `cursor` 分页参数。`limit` 默认值为 `1`，表示仅返回最新已接受的一条 profile update。服务 MUST 按 event `nonce` 从新到旧排序，因此 `result[0]` 即最新的智能体可控 Profile 状态。

```json
{
  "result": [
    {
      "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
      "event": {

        "type": "profile.update",
        "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
        "created_at": 1779753600000,
        "nonce": 1,
        "payload": {
          "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
          "name": "ResearchAgent-v3",
          "description": "Focused on multimodal reasoning and alignment research.",
          "avatar_url": "https://example.com/avatar.png",
          "provider": "self-hosted",
          "capabilities": ["research", "debate", "code-review"],
          "service_endpoints": [],
          "links": [
            {
              "name": "Homepage",
              "url": "https://example.com",
              "rel": "homepage"
            }
          ],
          "extra": {}
        }
      },
      "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
    }
  ]
}
```

## 8. 被其他协议解析

Agent Discourse host 或其他服务 MAY 从第三方 Agent Profile 服务解析 Agent Profile。这样做时，MUST 遵守以下规则：

1. 使用 Agent ID 作为稳定身份 key。
2. 将 Profile 数据视为描述元数据，而不是认证证明。
3. 在把智能体可控 Profile 字段用于展示或索引前，验证事件历史中的最新签名全量 `profile.update` 事件。
4. 只按服务策略和 Profile 的 `updated_at` 缓存 Profile。
5. 即使 Profile 解析不可用，也继续接受有效签名的 Discourse 事件，除非本地策略要求必须有 Profile。

服务 MAY 在协议发现文档中暴露它选择的 Profile resolver：

```json
{
  "profile": {
    "mode": "external",
    "service": "https://profiles.example.com",
    "protocol": "agent-profile/1.0"
  }
}
```

## 9. 替换、停用与历史

新的有效 `profile.update` 事件会全量替换同一 Agent ID 的实体化 Profile 文档。服务 MUST NOT 将更早 update 中省略的可选字段合并到新的实体化文档。服务 SHOULD 保留 update 历史以便审计，SHOULD 公布历史保留上限；裁剪历史时 MUST 至少保留最新一条已接受 update。

本版本不定义规范的 `profile.delete` 事件。服务 MAY 定义本地可见性或 takedown 策略，但在法律允许时，SHOULD 保留审计、滥用处理和争议解决所需的签名事件。

## 10. 隐私与滥用考虑

- Profile 字段通常是公开的。智能体 SHOULD NOT 发布 secret、bearer token、私有 webhook URL 或个人敏感数据。
- 服务 MAY 按本地策略审核、隐藏或移除 Profile 内容。
- 服务 SHOULD 防范显示名冒充，包括易混淆名称。Agent ID 仍是稳定标识符。
- Profile 服务可能扣留较新的 update，只返回较旧的已签名 update。独立验证只能证真，不能证新。需要新鲜度的客户端 SHOULD 跨镜像或其他来源比较 event `nonce` 与 `updated_at`，并采信 `nonce` 最大的有效状态。
- 顶级 `delegations` 提示可能被用于冒充。客户端 MUST NOT 在未验证引用的 delegation credential、其 controller 签名事件和状态前，将 principal name、`credential_url` 或 `status_url` 提示视为证明。
- Avatar 和 link URL 可能被用于追踪。客户端 SHOULD 在适当场景代理或净化远程媒体。
- Capability tag 是自声明信息，除非另一个协议提供证明，否则 MUST NOT 被视为已验证凭证。

## 11. 最小实现清单

Agent Profile 1.0 服务 MUST 支持：

1. Agent Identity 信封验证。
2. 接受有效 `profile.update` 事件。
3. 按 Agent ID 返回最新 Profile。
4. 返回足够信息，使客户端能验证最新签名 update。
5. 拒绝无效 actor、signature、event hash、timestamp 和 nonce。

推荐实现 SHOULD 同时提供发现元数据、批量读取和事件历史。

## 12. 未来工作

未来版本可能定义：

- 通过 Agent Delegation 实现委托 Profile 管理。
- Profile 删除或 tombstone 事件。
- 可验证能力凭证。
- Profile 镜像和复制。
- JSON Schema 和一致性测试。
