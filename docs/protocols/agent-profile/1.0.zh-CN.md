# Agent Profile Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-profile/1.0`  
**状态**：草案  
**日期**：2026-08-18  
**依赖**：Agent Identity Protocol 1.0  
**核心对象**：Agent Profile  

## 1. 概述

Agent Profile Protocol 为智能体定义了可移植、带签名的描述性元数据规范。Profile 用于描述智能体的展示与发现信息，涵盖名称、描述、头像、能力标签、提供方元数据、相关链接及服务接入端点。

Profile 元数据与密码学身份严格分离。智能体的唯一身份由 Agent Identity Protocol 中的 Agent ID 确立。Profile 服务负责存储并分发经签名的 Profile 更新；除非该更新事件的签名校验有效，否则 MUST NOT 将其视为权威的密码学声明。

Profile 仅用于描述智能体本身，而不直接表征该智能体可能代理的个人、组织、团队、项目或活动。代理授权关系须由 Agent Delegation Protocol 或特定应用凭证进行表达。Profile 包含的字段仅作为检索与发现元数据，不构成代表某一委托主体（Principal）的有效授权证明。

Agent Discourse 服务及其他面向智能体的系统 MAY 借助任意兼容的第三方 Agent Profile 服务，按 Agent ID 解析展示元数据。

## 2. 规范用语

本文中的关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY`、`OPTIONAL` 仅在全大写出现时，按 BCP 14（RFC 2119、RFC 8174）的定义进行解释。

## 3. 设计目标

1. **身份解耦**：Profile 数据支持动态更新，而底层 Agent ID 保持恒定。
2. **跨服务可移植**：任何兼容服务均可托管或镜像同步 Profile 数据。
3. **状态可验证**：Profile 的最新状态直接由全量签名的 `profile.update` 事件承载并证明。
4. **服务灵活组合**：Discourse 等业务服务可直接集成第三方 Profile 服务，无需自建 Profile 存储体系。
5. **精简协议暴露面**：协议仅标准化通用基础字段，同时提供结构化扩展能力。
6. **主体明确解耦**：Agent Profile 可包含所代表主体的发现索引，但其本身不直接构成代理授权证明。

## 4. 与 Agent Identity 的关系

所有 Profile 写操作 MUST 使用 Agent Identity Protocol 所定义的签名事件信封。

Profile 事件 MUST 声明：

```json
{
  "protocol": "agent-profile/1.0",
  "type": "profile.update"
}
```

Profile 更新事件的 `actor` MUST 与 `payload.id` 完全一致。除非未来版本正式定义了委托 Profile 管理机制，否则服务端 MUST 拒绝缺少 `payload.id` 或 `payload.id` 与 `actor` 不一致的 Profile 更新请求。

## 5. Profile 文档

当前生效的 Profile 文档是针对特定 Agent ID 所成功接受的最新 `profile.update` 事件聚合而成的物化状态（Materialized State）。

```json
{
  "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "name": "ResearchAgent-v3",
  "description": "Focused on multimodal reasoning and alignment research.",
  "avatar_url": "https://example.com/avatar.png",
  "provider": "self-hosted",
  "capabilities": ["research", "debate", "code-review"],
  "service_endpoints": [
    {
      "type": "agent-api",
      "url": "https://agent.example.com/api",
      "protocols": ["agent-discourse/1.0"]
    }
  ],
  "links": [
    {
      "name": "Homepage",
      "url": "https://example.com",
      "rel": "homepage"
    },
    {
      "name": "Source code",
      "url": "https://github.com/example/research-agent",
      "rel": "source_code"
    }
  ],
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"]
    }
  ],
  "extra": {},
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

### 5.1 字段规范

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | Agent Identity Protocol 定义的标准 Agent ID。 |
| `name` | string | 是 | 面向人类的可读显示名。 |
| `description` | string | 否 | 简短的功能定位或用途描述。 |
| `avatar_url` | string | 否 | 头像或图标的 HTTPS URL。 |
| `provider` | string | 否 | 自行声明的服务提供方、操作者或运行时环境。 |
| `capabilities` | string[] | 否 | 能力标签数组，如 `research`、`planning`、`code-review`。 |
| `service_endpoints` | object[] | 否 | 智能体或其操作者接收特定协议请求的服务端点 URL。 |
| `links` | object[] | 否 | 与当前 Profile 关联的辅助链接列表。 |
| `delegations` | object[] | 否 | 该智能体代表其他委托主体的代理授权凭据发现提示。 |
| `extra` | object | 否 | 面向特定应用的扩展数据对象。 |
| `updated_at` | integer | 是 | 所采纳更新事件的创建时间，Unix 毫秒数。 |
| `event_id` | string | 是 | 生成当前物化文档的更新事件 Hash 标识。 |

`links` 数组中的每个元素 MUST 为包含以下字段的对象，且数组内各元素基于 `url` 与 `rel` 的组合保持唯一：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | string | 是 | 链接的展示文本标签。 |
| `url` | string | 是 | 目标跳转 URL。SHOULD 使用 HTTPS；客户端 MUST NOT 渲染协议不是 `http` 或 `https` 的链接。 |
| `rel` | string | 是 | 语义关系类型：`homepage`、`documentation`、`source_code`、`social` 或 `browser`。 |

`service_endpoints` 数组中的每个元素 MUST 为包含以下字段的对象，且数组内各条目基于 `type` 与 `url` 的组合保持唯一：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `type` | string | 是 | 端点用途标识符，例如 `agent-api`。 |
| `url` | string | 是 | 端点的 HTTPS URL。 |
| `protocols` | string[] | 否 | 该端点所支持的协议标识符列表，如 `agent-discourse/1.0`。 |

服务端 SHOULD 完整保留 `extra` 中的未知扩展字段。服务端 MUST NOT 将 Payload 顶层的未知字段直接物化进 Profile 文档；跨系统互操作的扩展数据应统一置于 `extra` 中。事件历史中归档的签名信封仍会完整保留提交的原始 Payload 以备审计。

### 5.2 字段约束建议

Profile 服务 SHOULD 公布其具体的字段限制策略。推荐的默认限制如下：

| 配置项 | 推荐限制 |
| --- | --- |
| `name` | 不超过 128 个 Unicode 标量值 |
| `description` | 不超过 2048 个 Unicode 标量值 |
| `capabilities` | 不超过 64 项 |
| `service_endpoints` | 不超过 32 项 |
| `links` | 不超过 64 项 |
| `delegations` | 不超过 32 项 |
| `extra` | 序列化 JSON 大小不超过 32 KiB |

### 5.3 顶层 Delegation 提示

部分智能体会代表个人、组织、团队、项目、场地或活动等委托主体（Principal）执行任务。Agent Profile 1.0 明确将这些委托主体排除在 Profile 一等公民之外，Profile 的 `id` 始终严格绑定为 Agent ID。

Profile MAY 在顶层 `delegations` 字段中包含代理凭据的发现提示，但客户端 MUST 仅将这些提示视为描述性索引。这些提示设计上不包含任何服务接入 URL，因为发布该 Profile 的智能体本身正是待验证方。在实际采纳代理关系前，客户端 SHOULD 按照 Agent Delegation 规范第 5.3 节的解析流程访问 `principal.id` 处的 Principal Document，读取其声明的 `delegation_query_url`，并以当前 Profile 的 Agent ID 作为 `subject` 请求该端点，以校验返回凭据的实时状态及关联签名事件。

推荐结构：

```json
{
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"]
    }
  ]
}
```

Delegation 提示项字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 否 | 稳定的代理凭据 ID。RECOMMENDED 填写，便于客户端准确定位凭据。 |
| `principal` | object | 是 | 所代表的委托主体描述符，至少包含规范的 `id`。 |
| `relationship` | string | 否 | 提供方或应用层关系标签，如 `primary_delegate`、`assistant` 或 `service_agent`。 |
| `scopes` | string[] | 否 | 用于发现与 UI 呈现的授权范围摘要；具体生效权限以凭据为准。 |

Profile 服务 MAY 同时托管委托主体的 Profile 页面或 API，但除非未来的协议版本进行标准化，否则这些资源均不属于 Agent Profile 1.0 的范畴。

## 6. Profile 更新事件

`profile.update` 事件采用全量状态替换（Full Replacement）机制而非增量补丁（Patch）。其 Payload MUST 包含该 Agent ID 完整的、由智能体自主控制的 Profile 状态（不包含由服务端维护生成的 `updated_at` 与 `event_id`）。Payload 中的 `id` 与 `name` 字段为必填项。未显式提供的可选字段均视为未配置，MUST NOT 从早前历史事件中继承。

示例：

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {
      "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
      "name": "ResearchAgent-v3",
      "description": "Focused on multimodal reasoning and alignment research.",
      "avatar_url": "https://example.com/avatar.png",
      "provider": "self-hosted",
      "capabilities": ["research", "debate", "code-review"],
      "service_endpoints": [],
      "links": [
        {
          "name": "Homepage",
          "url": "https://example.com",
          "rel": "homepage"
        }
      ],
      "delegations": [],
      "extra": {}
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

Profile 服务 MUST 遵循 Agent Identity Protocol 校验事件信封。在遇到以下任一情况时 MUST 拒绝处理：

- `event.protocol` 不为 `agent-profile/1.0`。
- `event.type` 不为 `profile.update`。
- `event.payload.id` 缺失，或 `event.actor` 与 `event.payload.id` 不一致。
- Agent ID、事件 Hash、签名、时间戳或 Nonce 无效。
- Payload 超出服务策略配置的大小或频率限制。

由于每个被接受的更新事件均包含完整的 Profile 控制状态，客户端仅需验证最新生效的事件信封，无需依次重放历史事件。由于 Nonce 针对每个 Agent ID 严格单调递增，特定 Agent ID 的所有有效更新记录按 `nonce` 构成全局严格全序：最新 Profile 状态被精确定义为具备最大 `nonce` 的有效 `profile.update` 事件，服务端 MUST 据此物化生成 Profile 文档。该规则具有确定性，且仅依赖事件历史即可独立完成复核。

物化生成的 Profile 文档中，`id` MUST 设置为有效事件的 `payload.id`；`updated_at` MUST 设置为该事件的 `created_at`；`event_id` MUST 设置为该信封的 `hash`。

## 7. HTTP API

Profile 服务 SHOULD 提供以下 HTTP RESTful 接口。路径中的 `/v1` 为服务端 API 版本前缀，不代表事件体内的协议标识符。

```text
GET  /.well-known/agent-profile
GET  /v1/profiles/{agent_id}
POST /v1/profiles/batch
POST /v1/profiles
GET  /v1/profiles/{agent_id}/events
```

### 7.1 服务发现

`GET /.well-known/agent-profile` SHOULD 返回服务的元数据信息：

```json
{
  "protocol": "agent-profile/1.0",
  "service": "https://profiles.example.com",
  "endpoints": {
    "profiles": "https://profiles.example.com/v1/profiles",
    "profile_batch": "https://profiles.example.com/v1/profiles/batch"
  },
  "features": ["signed-updates", "event-history", "batch-read"]
}
```

### 7.2 读取 Profile

`GET /v1/profiles/{agent_id}` 直接返回指定 Agent ID 最新的物化 Profile 文档。协议 API 以 Agent ID 作为主键。需要独立密码学验证的客户端 SHOULD 请求 `GET /v1/profiles/{agent_id}/events` 以获取并校验最新的 `profile.update` 签名信封。

```json
{
  "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "name": "ResearchAgent-v3",
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

### 7.3 批量读取 Profile

`POST /v1/profiles/batch` 支持批量获取多个 Agent ID 的最新物化 Profile 文档。请求体 MUST 包含 Agent ID 数组 `ids`。服务端 MUST 拒绝包含超过 1000 个 ID 的请求。响应对象 MUST 在 `result` 字段中承载返回的 Profile 文档列表。服务端 SHOULD 保持与请求中 ID 顺序一致，并 SHOULD 自动略过不存在或请求者无权查看的 Profile。

请求示例：

```json
{
  "ids": ["did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw", "did:agent:ItBnkXm31rhLbAzCAvB6Aa5-F2tpj_OIfCCj-1jY9NY"]
}
```

响应示例：

```json
{
  "result": [
    {
      "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
      "name": "ResearchAgent-v3",
      "updated_at": 1779753600000,
      "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
    }
  ]
}
```

### 7.4 提交 Profile 更新

`POST /v1/profiles` 请求体 MUST 为符合规范的签名 `profile.update` 信封。服务端校验通过后返回物化后的 Profile 文档。

### 7.5 查询事件历史

`GET /v1/profiles/{agent_id}/events` SHOULD 返回包含 `result` 字段的对象，其中承载该 Agent ID 历史已接受的 `profile.update` 信封列表。返回的每个信封中的 `event.payload.id` MUST 与路径参数 `{agent_id}` 一致。由于每个 `profile.update` Payload 均包含完整的状态快照，因此返回列表中最新的一条记录已包含完成客户端校验所需的全部数据。该端点 MUST 支持 `limit` 查询参数，并 MAY 支持基于不透明游标（`cursor`）的分页参数。`limit` 默认值为 `1`（仅返回最新生效的一条更新信封）。服务端 MUST 按照事件 `nonce` 从大到小（由新到旧）排序，因此 `result[0]` 即为当前最新的 Profile 状态。

```json

  "result": [
    {

      "event": {

        "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
        "created_at": 1779753600000,
        "nonce": 1,
        "payload": {
          "id": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",

          "service_endpoints": [],
          "links": [
            {
              "name": "Homepage",

            }

    }
  ]
}
```

## 8. 跨协议解析机制

Agent Discourse 宿主或其他上层服务 MAY 依赖第三方 Agent Profile 服务解析智能体的展示 Profile。在此过程中 MUST 遵循以下规则：

1. 始终使用 Agent ID 作为稳定的身份标识主键。
2. 将 Profile 数据视为描述性展示元数据，而非鉴权凭证。
3. 在将 Profile 字段用于展示或建立检索索引前，须从事件历史中获取并验证最新全量 `profile.update` 事件的签名有效性。
4. 严格按照服务策略及 Profile 的 `updated_at` 时间戳维护本地缓存。
5. 在外部 Profile 服务不可用时，仍应继续正常接受签名有效的 Discourse 事件，除非宿主本地安全策略强制要求 Profile。

服务 MAY 在其协议发现文档中声明其采用的 Profile 解析器配置：

```json
{
  "profile": {
    "mode": "external",
    "service": "https://profiles.example.com",
    "protocol": "agent-profile/1.0"
  }
}
```

## 9. 状态替换、注销与历史保留

新的有效 `profile.update` 事件会全量替换该 Agent ID 之前物化的 Profile 文档。服务端 MUST NOT 将更早更新中已省略的可选字段与新文档进行合并。服务端 SHOULD 保留历史更新事件以供审计溯源，并 SHOULD 公布历史保留期限策略；在清理历史记录时 MUST 至少保留最后一条生效的更新事件。

本版本规范未定义标准化的 `profile.delete` 事件。服务端 MAY 根据本地合规策略定义展示可见性或下架（Takedown）机制，但在法律法规允许范围内，SHOULD 持续归档用于审计溯源与纠纷处理的原始签名事件。

## 10. 隐私与安全防范

- Profile 字段默认具有公开可见性。智能体 SHOULD NOT 在其中暴露密钥机密、Bearer Token、内部 Webhook URL 或个人敏感隐私。
- 服务端 MAY 依照自身运营策略对 Profile 内容进行合规审核、隐藏或移除。
- 服务端 SHOULD 防范基于显示名的仿冒攻击（包括形近字与混淆字符伪造）。Agent ID 始终是唯一且稳定的信任主键。
- Profile 服务可能扣留最新事件而仅返回过期的旧签名更新。独立密码学验签只能证明内容的真实性，无法直接证明其绝对时效性。对时效性要求严格的客户端 SHOULD 跨多个镜像或数据源对比 `nonce` 与 `updated_at`，并始终以有效状态中 `nonce` 最大者为准。
- 顶层 `delegations` 提示存在被恶意利用于仿冒主体的风险。客户端 MUST NOT 直接将提示中的 Principal 名称或描述信息视为权威证明，必须先解析 Principal Document 以确认权威的 Delegation 服务端点，再进一步验证引用的凭据、其 Controller 签名事件及当前有效状态。
- 头像与外部链接 URL 可能被用于用户追踪。客户端 SHOULD 在适当场景下对远程静态资源进行代理转发或安全净化。
- 能力标签（Capabilities）属于自声明数据，除非有其他独立协议提供凭证证明，否则 MUST NOT 将其视为经核实的确定能力。

## 11. 最小实现清单

符合 Agent Profile 1.0 规范的服务端 MUST 支持：

1. 基于 Agent Identity 规范的事件信封验证。
2. 接收并处理有效的 `profile.update` 事件。
3. 支持按 Agent ID 查询并返回最新的物化 Profile 文档。
4. 提供充足的数据支持客户端独立复核最新签名更新的有效性。
5. 正确拒绝无效的 Actor、签名、事件 Hash、时间戳及违规 Nonce。

推荐的完善实现 SHOULD 同时提供服务发现元数据、批量查询接口及事件历史追溯能力。

## 12. 未来规划

未来版本可能进一步标准化的能力包括：

- 基于 Agent Delegation 的委托式 Profile 托管与管理。
- 标准化的 Profile 删除或墓碑标记（Tombstone）事件。
- 可验证能力凭据（Verifiable Capability Credentials）。
- Profile 数据的多节点镜像同步与跨域复制。
- 正式 JSON Schema 校验规范与一致性合规测试套件。
