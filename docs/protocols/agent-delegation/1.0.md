# Agent Delegation Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**Identifier**: `agent-delegation/1.0`
**Status**: Draft
**Date**: 2026-07-03
**Depends on**: Agent Identity Protocol 1.0
**May use**: Agent Profile Protocol 1.0
**Core object**: Agent Delegation Credential

## 1. Overview

Agent Delegation Protocol defines portable, verifiable credentials that state when an agent is authorized to act for a represented principal such as a person, organization, team, project, venue, or event.

Agent Identity answers "which key signed this event?" Agent Profile answers "how should this agent be displayed and discovered?" Delegation answers the separate question: "on whose behalf may this agent act, and within what boundaries?"

The protocol uses one trust primitive. A principal is identified by an HTTPS URL, and that URL publishes a principal document — the principal's public card — listing the **controller keys** allowed to sign for the principal. A delegation grant is an ordinary Agent Identity signed event whose `actor` is one of those controller keys. Verifying a delegation therefore reuses the envelope verification that every Agent Protocols service already implements, plus one HTTP read of the principal document.

This protocol intentionally does not define human login, account recovery, or legal identity proofing. How a provider decides to sign with a principal's controller key — logged-in account consent, organization admin policy, human review — is a provider concern outside this protocol. The protocol defines only the principal binding, the grant and revocation events, the materialized credential, and the read APIs.

## 2. Normative Language

The key words `MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, and `MAY` in this document are to be interpreted as described in RFC 2119.

## 3. Design Goals

1. **Principal separation**: An Agent Profile describes an agent. It does not itself prove which person or organization the agent represents.
2. **One envelope**: Delegation events are standard Agent Identity signed events. There is no second proof format.
3. **URL-rooted authority**: Control of the principal URL is control of the principal identity, in the same way a `did:agent:` key controls an agent identity.
4. **Scoped delegation**: Grants carry scopes and constraints instead of a broad "acts as" statement.
5. **Revocation first**: Receivers can check current credential status before relying on a delegation.
6. **Provider neutral**: Any compatible service can host principal documents and credentials; applications define their own scopes, constraints, and consent flows on top.

## 4. Core Concepts

| Concept | Description |
| ------- | ----------- |
| Principal | The represented subject: a person, organization, team, project, venue, event, or other non-agent entity. |
| Principal document | The JSON document served at the principal URL: the principal's public card plus its controller keys. |
| Controller key | An Agent ID listed in the principal document's `controllers`. Events signed by a controller key carry the principal's authority. |
| Subject agent | The `did:agent:*` that receives delegated authority. |
| Delegation credential | The materialized current state of the latest accepted grant or revocation event plus provider status. |
| Scope | An application-defined permission string such as `inbox.screen`, `calendar.propose`, or `alink.intro.request`. |
| Constraint | A JSON object that limits how scopes may be used. |
| Status | `active`, `suspended`, `expired`, or `revoked`. |

## 5. Principals

### 5.1 Principal Identifier

A `principal.id` MUST be an HTTPS URL. Short, stable URLs are RECOMMENDED:

```text
https://al.ink/yan
https://profiles.example.com/org/acme
https://events.example.com/summit-2026
```

The URL is the identity root: whoever controls what this URL serves controls the principal identity. Other identifier schemes, such as DID methods, may be added in future versions.

### 5.2 Principal Document

`GET {principal.id}` with `Accept: application/json` MUST return the principal document as `application/json`. The same URL MAY serve HTML or other representations to other clients. Resolvers MAY follow same-origin redirects; the resolved document's `id` MUST equal the principal identifier being verified.

The principal document is the principal's public card. Descriptive fields say who the principal is; `controllers` binds the keys that may sign for it. Only `id` and `controllers` carry trust semantics — every other field is self-published display metadata, not a verified claim.

```json
{
  "id": "https://al.ink/yan",
  "type": "person",
  "name": "Yan",
  "description": "Founder of alink. Building agent-native contact infrastructure.",
  "avatar_url": "https://al.ink/yan/avatar.png",
  "links": [
    { "name": "Homepage", "url": "https://yan.example.com", "rel": "homepage" },
    { "name": "alink", "url": "https://al.ink", "rel": "social" }
  ],
  "controllers": ["did:agent:PrincipalControllerKey"],
  "delegations_url": "https://al.ink/v1/delegations/query",
  "updated_at": 1779753600000,
  "extra": {}
}
```

| Field | Type | Required | Description |
| ----- | ---- | -------- | ----------- |
| `id` | string | Yes | The principal URL. |
| `type` | string | No | SHOULD be one of `person`, `organization`, `team`, `project`, `venue`, `event`, or `other`. |
| `name` | string | No | Human-readable display name. |
| `description` | string | No | Short self-description. |
| `avatar_url` | string | No | HTTPS URL for an avatar or logo. |
| `links` | object[] | No | Auxiliary links; each item uses the Agent Profile `links` item shape (`name`, `url`, `rel`). |
| `controllers` | string[] | Yes | Agent IDs authorized to sign for this principal. MUST be non-empty; each entry MUST be a valid Agent ID. |
| `delegations_url` | string | No | HTTPS URL where this principal's delegation credentials can be queried or read. |
| `updated_at` | integer | No | Unix milliseconds of the last document change. |
| `extra` | object | No | Extension object for application-specific data. |

Consumers SHOULD preserve unknown fields. Hosts SHOULD apply field limits similar to Agent Profile Section 5.2. When verifying new events, services SHOULD NOT rely on cached principal documents older than 300 seconds.

### 5.3 Controller Keys and Rotation

Controller keys are ordinary Agent Identity keys. They can be held by the principal directly, by the principal's provider, or by a dedicated signer service; who holds them and what consent flow gates their use is a provider and application decision.

A principal changes its authority set by updating `controllers`. Removing a controller key does not retroactively invalidate grants that were accepted while the key was listed; to withdraw authority already delegated, the principal issues `delegation.revoke` events. Responding to a compromised controller key therefore means both rotating `controllers` and revoking the grants it signed.

A service MUST check that an event's `actor` is listed in the principal document at event acceptance time.

## 6. Delegation Events

Delegation events are standard Agent Identity signed event envelopes with:

```json
{
  "protocol": "agent-delegation/1.0"
}
```

The `actor` MUST be a controller key of the principal named in the payload. Anyone MAY submit an issued envelope to a delegation service — the subject agent, a provider backend, or a mirror; the signature, not the submitter, carries the principal's authority. Services MAY require request authentication for rate limiting and abuse control.

### 6.1 Grant Event

A `delegation.grant` event creates or replaces a delegation credential.

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-delegation/1.0",
    "type": "delegation.grant",
    "actor": "did:agent:PrincipalControllerKey",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://al.ink/yan",
        "type": "person",
        "name": "Yan"
      },
      "subject": "did:agent:SubjectAgentPublicKey",
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"],
      "constraints": {
        "requires_human_approval": ["meeting.accept"]
      },
      "not_before": 1779753600000,
      "expires_at": 1790000000000
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

| Payload field | Type | Required | Description |
| ------------- | ---- | -------- | ----------- |
| `id` | string | Yes | Stable delegation identifier, unique within the service. |
| `principal` | object | Yes | Principal descriptor. MUST contain `id`; SHOULD contain `type`; MAY contain `name`. |
| `subject` | string | Yes | Agent ID receiving delegated authority. |
| `relationship` | string | No | Application label such as `primary_delegate`, `assistant`, `organization_delegate`, or `service_agent`. |
| `scopes` | string[] | Yes | Application-defined delegated capabilities. |
| `constraints` | object | No | Application-defined limits. Services SHOULD preserve unknown fields. |
| `not_before` | integer | No | Unix milliseconds before which the grant is not valid. |
| `expires_at` | integer | No | Unix milliseconds after which the grant is expired. |

For `delegation.grant`, the service MUST reject the event if:

- the envelope fails Agent Identity verification: shape, hash, signature, actor, timestamp window, or nonce;
- `event.protocol` is not `agent-delegation/1.0` or `event.type` is not `delegation.grant`;
- `event.payload.id`, `event.payload.principal.id`, `event.payload.subject`, or `event.payload.scopes` is missing or invalid;
- `event.payload.principal.id` is not an HTTPS URL, or its principal document cannot be resolved and validated;
- `event.actor` is not listed in the principal document's `controllers`;
- `event.payload.subject` is not a valid Agent ID;
- `event.payload.expires_at`, when present, is not greater than `event.payload.not_before` or `event.created_at`;
- `event.payload.id` already identifies a delegation whose `principal.id` does not equal `event.payload.principal.id`;
- the event violates service limits or policy.

An accepted grant with the same `payload.id` and the same principal replaces the previous credential state, for example to adjust scopes or extend validity.

The materialized credential takes its delegation fields from the accepted grant `payload`. `status`, `status_url`, and `updated_at` are service-managed; `controller` MUST be set to the accepted event's `actor`; `event_id` MUST be set to the accepted envelope's `hash`.

### 6.2 Revocation Event

A `delegation.revoke` event revokes a previously accepted delegation credential. Its `actor` MUST be a current controller key of the principal; it does not need to be the key that signed the grant.

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-delegation/1.0",
    "type": "delegation.revoke",
    "actor": "did:agent:PrincipalControllerKey",
    "created_at": 1779757200000,
    "nonce": 2,
    "payload": {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal_id": "https://al.ink/yan",
      "reason": "rotated_primary_agent"
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

For `delegation.revoke`, the service MUST reject the event if:

- the referenced delegation does not exist;
- the envelope fails Agent Identity verification;
- `event.protocol` is not `agent-delegation/1.0` or `event.type` is not `delegation.revoke`;
- `event.payload.id` or `event.payload.principal_id` is missing or invalid;
- `event.payload.principal_id` does not equal the referenced delegation's `principal.id`;
- `event.actor` is not listed in the principal document's `controllers`;
- the event violates service limits or policy.

A subject agent can stop presenting a credential or ask the hosting service to suspend it, but only a controller-signed `delegation.revoke` is a principal revocation. Services MAY mark a delegation as `suspended` according to documented abuse, compliance, or visibility policy; provider status is not principal revocation.

## 7. Credential Document

A delegation credential is the materialized current state of the latest accepted grant or revocation event plus provider status.

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "protocol": "agent-delegation/1.0",
  "principal": {
    "id": "https://al.ink/yan",
    "type": "person",
    "name": "Yan"
  },
  "controller": "did:agent:PrincipalControllerKey",
  "subject": "did:agent:SubjectAgentPublicKey",
  "relationship": "primary_delegate",
  "scopes": ["inbox.screen", "meeting.propose"],
  "constraints": {
    "requires_human_approval": ["meeting.accept"]
  },
  "not_before": 1779753600000,
  "expires_at": 1790000000000,
  "status": "active",
  "status_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q/status",
  "updated_at": 1779753600000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

| Field | Type | Required | Description |
| ----- | ---- | -------- | ----------- |
| `id` | string | Yes | Delegation identifier from the accepted grant. |
| `protocol` | string | Yes | `agent-delegation/1.0`. |
| `principal` | object | Yes | Principal descriptor from the accepted grant. |
| `controller` | string | Yes | The `actor` that signed the event producing the current state. |
| `subject` | string | Yes | Agent ID receiving delegated authority. |
| `relationship` | string | No | Application relationship label. |
| `scopes` | string[] | Yes | Application-defined delegated capabilities. |
| `constraints` | object | No | Application-defined limits. |
| `not_before` | integer | No | Unix milliseconds before which the grant is not valid. |
| `expires_at` | integer | No | Unix milliseconds after which the grant is expired. |
| `status` | string | Yes | `active`, `suspended`, `expired`, or `revoked`. |
| `status_url` | string | No | Service-assigned HTTPS URL for current status checks. |
| `updated_at` | integer | Yes | Unix milliseconds of the latest accepted event or provider status update. |
| `event_id` | string | Yes | Envelope `hash` of the event that produced the current state. |

Clients that need independent verification SHOULD read the event history, verify the latest accepted envelope per Agent Identity, and resolve the principal document to confirm the controller binding.

## 8. HTTP API

Delegation services SHOULD expose the following HTTP API. The `/v1` path version is the service API version and is not the protocol identifier inside events.

```text
GET  /.well-known/agent-delegation
GET  /v1/delegations/{delegation_id}
GET  /v1/delegations/{delegation_id}/status
GET  /v1/delegations/{delegation_id}/events
POST /v1/delegations
POST /v1/delegations/query
```

### 8.1 Service Discovery

`GET /.well-known/agent-delegation` SHOULD return service metadata:

```json
{
  "protocol": "agent-delegation/1.0",
  "service": "https://al.ink",
  "endpoints": {
    "delegations": "https://al.ink/v1/delegations",
    "query": "https://al.ink/v1/delegations/query"
  },
  "features": ["grants", "revocations", "event-history"]
}
```

### 8.2 Read Delegation

`GET /v1/delegations/{delegation_id}` returns the latest materialized credential. `GET /v1/delegations/{delegation_id}/events` returns the accepted envelopes for independent verification.

### 8.3 Status Check

`GET /v1/delegations/{delegation_id}/status` returns the current status without the full credential:

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "status": "active",
  "checked_at": 1779757200000,
  "expires_at": 1790000000000,
  "event_id": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts"
}
```

Relying parties SHOULD check status before trusting a delegation for sensitive actions.

### 8.4 Submit Delegation Event

`POST /v1/delegations` accepts a `delegation.grant` or `delegation.revoke` envelope and returns the materialized credential or status. Submitter authentication, when required, is a transport concern and does not affect event verification.

### 8.5 Query Delegations

`POST /v1/delegations/query` lets clients resolve delegations by subject agent or principal. Services MAY require authentication, rate-limit the endpoint, and redact results according to local policy.

Request:

```json
{
  "subject": "did:agent:SubjectAgentPublicKey",
  "principal_id": "https://al.ink/yan",
  "status": "active",
  "limit": 20
}
```

Response:

```json
{
  "result": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "subject": "did:agent:SubjectAgentPublicKey",
      "principal": {
        "id": "https://al.ink/yan",
        "type": "person",
        "name": "Yan"
      },
      "scopes": ["inbox.screen", "meeting.propose"],
      "status": "active",
      "status_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q/status"
    }
  ]
}
```

## 9. Relationship to Agent Profile

Agent Profiles MAY link to delegation credentials through the top-level `delegations` field, but profile metadata MUST NOT be treated as proof of representation by itself.

A recommended shape is:

```json
{
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://al.ink/yan",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"],
      "credential_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "status_url": "https://al.ink/v1/delegations/del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q/status"
    }
  ]
}
```

Clients MUST treat this as a discovery hint. Before relying on the representation, clients SHOULD fetch the linked credential, verify its latest signed event and controller binding, and check its current status.

## 10. Security and Privacy Considerations

- Control of the principal URL origin is control of the principal identity. Principal documents MUST be served over HTTPS with valid certificates. A DNS or origin compromise is an identity compromise; high-value relying parties MAY pin known controller keys in local policy.
- Principal document descriptive fields — `name`, `description`, `avatar_url`, `links` — are self-published display metadata, not verified claims.
- Removing a controller key does not revoke grants it already signed. Compromise response requires rotating `controllers` and revoking affected delegations.
- A delegation credential proves principal authorization, not subject participation. Anyone controlling a principal URL can issue a credential naming any Agent ID as `subject`. Relying parties MUST NOT treat the existence of a credential as evidence that the subject agent uses, accepts, or endorses the principal; positive subject signals include the subject presenting the credential itself or listing it in its own signed profile `delegations` hints.
- Scopes and constraints are application-defined. Relying parties MUST NOT assume unknown scopes grant any capability.
- A delegation credential is not a session token. It does not authorize a request by itself; receivers still need request authentication, policy checks, and human approval where appropriate.
- Delegation credentials can reveal sensitive relationships. Services SHOULD support visibility controls and redaction for query APIs.
- Principal names can be abused for impersonation. Services SHOULD reserve protected names and document verification policy; the principal URL, not the display name, is the identifier.
- Principal documents and credentials SHOULD NOT contain bearer tokens, private webhook URLs, private contact channels, or secrets.
- Revocation status endpoints SHOULD be highly available and cacheable for short periods. Sensitive actions SHOULD avoid relying only on stale cached status.

## 11. Minimum Implementation Checklist

An Agent Delegation 1.0 service MUST support:

1. Agent Identity envelope verification.
2. Principal document resolution and the controller check.
3. Accepting valid `delegation.grant` events and returning the materialized credential by delegation ID.
4. Returning accepted events for independent client verification.
5. Returning current status, including `revoked` and `expired`.
6. Rejecting invalid envelopes, non-controller actors, malformed principal or subject identifiers, and inconsistent validity windows.

Recommended implementations SHOULD also support revocation events, service discovery, query by subject/principal, visibility policy, and profile integration hints.

## 12. Future Work

Future versions may define:

- non-HTTPS principal identifier schemes, such as DID methods;
- controller key labels and third-party attestation of principal documents;
- privacy-preserving controller bindings, such as blinded or zero-knowledge entries;
- standard scope registries for common applications;
- delegated profile management;
- cross-provider delegation mirroring and status replication;
- JSON Schema and conformance tests.
