# Agent Delegation Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**Identifier**: `agent-delegation/1.0`
**Status**: Draft
**Date**: 2026-09-24
**Depends on**: Agent Identity Protocol 1.0
**May use**: Agent Profile Protocol 1.0

## 1. Overview

Agent Delegation defines when an agent may act for a principal identified by a canonical HTTPS URL. The principal document binds keys to that principal; signed grant events delegate specific authority to subject agents. The HTTPS URL remains the identity root.

The protocol separates **key provenance**, **permission to issue delegations**, and **historical binding**. Registering a key does not automatically let it issue delegations or manage other controllers. A provider's default signer, a third-party application signer, and a local signer use the same record format and receive only explicitly published permissions.

Principal documents and signed events carry `agent-delegation/1.0`; implementations MUST validate the required record and event fields rather than assume the protocol identifier alone guarantees compatibility. Controller records MUST NOT be flattened into an unrestricted key list. JSON Schema definitions are in [`1.0.schema.json`](1.0.schema.json) and test vectors in [`1.0.vectors.json`](1.0.vectors.json).

## 2. Normative Language

The key words `MUST`, `MUST NOT`, `REQUIRED`, `SHOULD`, `SHOULD NOT`, and `MAY` are normative as described in BCP 14 (RFC 2119, RFC 8174).

All timestamps are non-negative JSON safe integers in milliseconds. Agent IDs MUST be valid Agent Identity 1.0 identifiers. Required strings MUST be non-empty. Protocol-defined allowlists, scopes, audiences, aliases, and `supersedes` lists MUST contain unique entries; application-defined JSON arrays retain their application semantics. Unknown display/extension fields SHOULD be preserved. Unsupported permission fields or values MUST fail closed: a verifier MUST NOT ignore a restriction it cannot enforce.

## 3. Principal Identity and Resolution

A principal represents a person, organization, team, project, venue, event, or other non-agent subject. Its `id` MUST be a canonical HTTPS URL. Stable, opaque identifiers are RECOMMENDED; renameable handles belong in `aliases`.

`GET {principal.id}` with `Accept: application/json` MUST return a public, unauthenticated JSON principal document. Resolve as follows:

1. Follow at most five redirects, using HTTPS at every hop, including across origins.
2. If the returned `document.id` exactly equals the final response URL, the document is authoritative.
3. Otherwise discard **all** authority-bearing fields from that copy, including `protocol`, `controllers`, `retired_controllers`, and `delegation_query_url`, and resolve `document.id` once using steps 1–2. If that read is not authoritative, fail.
4. Require `document.protocol` to equal `agent-delegation/1.0` before using controller authority.

URL identity comparison is exact string comparison. Publishers SHOULD normalize scheme/host case, omit default ports, and avoid queries/fragments in principal IDs. Events MUST name the canonical ID, never an alias: when a verifier resolves a principal ID taken from an event, the authoritative document's `id` MUST equal that ID. Before displaying an alias as a principal's name, a client MUST confirm that the authoritative document lists it in `aliases`. Alias mappings MUST NOT be cached longer than the document.

For accepting new events, services MUST use a document fetched no more than 300 seconds earlier, and SHOULD revalidate immediately for sensitive operations. Hosts MUST invalidate their own authority caches on controller changes. This bound is a maximum stale-authority window, not instantaneous distributed revocation.

## 4. Principal Document

```json
{
  "protocol": "agent-delegation/1.0",
  "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "type": "person",
  "name": "Yan",
  "aliases": [
    "https://al.ink/yan"
  ],
  "controllers": [
    {
      "id": "did:agent:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
      "source": "https://al.ink",
      "name": "alink default signer",
      "valid_from": 1788652800000,
      "delegation": "*"
    },
    {
      "id": "did:agent:AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE",
      "source": "https://tokenlist.ing",
      "name": "TokenList.ing user canister",
      "valid_from": 1788652800000
    }
  ],
  "retired_controllers": [],
  "delegation_query_url": "https://api.al.ink/v1/delegations/query",
  "updated_at": 1788652800000
}
```

Keys in examples illustrate wire shapes, not production keys.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `protocol` | string | Yes | Exactly `agent-delegation/1.0`. |
| `id` | string | Yes | Canonical principal URL. |
| `controllers` | Controller[] | Yes | Current records. MAY be empty, including during recovery. |
| `retired_controllers` | Controller[] | No | Historical records; absence means empty, not unknown keys authorized. |
| `delegation_query_url` | string | Conditional | Authoritative HTTPS query endpoint for delegation credentials. REQUIRED when any current or retired Controller carries `delegation`, because verification (Section 8) has no other trusted path. |
| `updated_at` | integer | Yes | Last document change time, not a cryptographic timestamp. |
| `type`, `name`, `description`, `avatar_url` | string | No | Display metadata. `type` SHOULD be `person`, `organization`, `team`, `project`, `venue`, `event`, or `other`; `avatar_url` MUST be HTTPS. |
| `aliases` | string[] | No | HTTPS aliases, governed by Section 3. |
| `links` | object[] | No | Agent Profile link items with string `name`, `url`, and `rel`. |
| `extra` | object | No | Application metadata. No display or extension field grants authority. |

### 4.1 One Controller Type

Both `controllers` and `retired_controllers` contain the **same Controller type**. A retired controller is the original record with `retired_at` added, not a separate entity or a copy with different permissions.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `id` | string | Yes | Agent ID of the key; equals the signed event's `actor`. No separate registration ID is needed. |
| `source` | string | Yes | HTTPS origin of the signer service, or `local` for a user's local signer. |
| `valid_from` | integer | Yes | Binding start, inclusive; MUST NOT be later than publication time. |
| `name` | string | No | Human-readable label, such as `alink default signer` or `Personal key vault`. |
| `delegation` | `"*"` or object | No | Delegation authority defined in Section 5. Absence means no delegation authority. |
| `supersedes` | string[] | No | Agent IDs of earlier Controller records of this principal whose credentials this key may manage (Section 5.1). |
| `retired_at` | integer | Retired only | Binding end, exclusive; MUST be at or after `valid_from`. Equality represents a binding retired before it accepted any events. |
| `invalid_from` | integer | Compromise only | Earliest time from which signatures are untrusted; MUST satisfy `valid_from <= invalid_from <= retired_at`. |

`source` origins MUST be serialized HTTPS origins: lowercase host, no userinfo, path, query, fragment, or default port. Examples are `https://al.ink`, `https://dmsg.net`, and `https://tokenlist.ing`; a local signer uses `local`. Audience origins follow the same format. `source` and `name` describe provenance asserted by the principal; they do not prove custody, user consent, or service endorsement and MUST NOT grant authority. Applications define their own signature format and consent checks; a key binding alone does not authorize an application action. Source URLs MUST NOT be fetched merely because they are listed here.

A hosted signer — a key held by `source` on the principal's behalf — is the key's operator in the sense of [Agent Identity Section 3.1](../agent-identity/1.0.md#31-key-algorithm). Registration MUST require principal-owner authorization and proof of key possession using a single-use, expiring, domain-separated challenge bound to the principal, key, source, delegation policy, and `supersedes` list. Registration, retirement, recovery, and permission changes require separate owner-management authorization; even `delegation: "*"` does not grant those management powers.

### 4.2 Immutable Binding

Within a principal, a key MUST appear at most once across both lists and MUST NOT be registered again after retirement. Its `id`, `source`, `valid_from`, `delegation`, and `supersedes` MUST NOT change after publication. Only the display `name` may be edited. A change of authority requires a new key and a new binding; this deliberately avoids registration versions and permission-history matching. No periodic rotation is required.

Retirement MUST atomically move the record from `controllers` to `retired_controllers` and add `retired_at`. Current records MUST NOT contain retirement or compromise timestamps; retired records MUST contain `retired_at`. Verifiers MUST reject duplicate keys or malformed records rather than combine their permissions.

## 5. Delegation Authority

There are exactly three configurations:

| `delegation` | Grant authority | Replace / revoke / enumerate |
| --- | --- | --- |
| Absent | None; public key binding only | None |
| `"*"` | Any explicit scopes and audiences | Any credential of this principal |
| `{ "scopes": [...], "audiences": [...] }` | Only the listed scopes and relying applications | Only credentials owned within this key's lineage (Section 5.1) |

The restricted object MUST contain exactly `scopes` and `audiences`, both non-empty arrays. Scopes match exactly, without prefix, glob, hierarchy, or wildcard. Audiences are HTTPS origins. Unknown policy fields, empty arrays, `null`, `{}`, and wildcard entries in either array MUST be rejected. The unrestricted string `"*"` is an explicit owner choice, never a registration default.

For example, a dmsg controller uses:

```json
{
  "scopes": ["inbox.screen", "message.draft"],
  "audiences": ["https://dmsg.net"]
}
```

Every granted scope and audience MUST be allowed. This key cannot issue a TokenList.ing delegation, grant another scope, or overwrite another key's credential. The TokenList.ing example in Section 4 omits `delegation` entirely because it only publishes an application-signing key. A local key can use any of the three configurations; local custody does not imply full authority.

Each credential has an immutable `owner_controller`: the Agent ID that signed its first accepted grant. Replacement, revocation, and reactivation MUST NOT transfer ownership. A restricted controller MUST own the credential through its lineage when replacing, revoking, or enumerating; every replacement also MUST satisfy the replacing key's own delegation ceiling. An unrestricted controller can manage credentials issued by other or retired keys, but only for the same principal.

For every operation, the key MUST be current and the operation time MUST be at or after `valid_from`. Enumeration requires proof of that key's identity. Signing-only keys cannot enumerate. This protocol does not add controller-level subject, TTL, or arbitrary JSON constraint policies; applications may impose additional restrictions. Grants still carry explicit subjects, validity, and constraints, which relying parties MUST enforce. Unknown scopes or constraints MUST NOT be treated as permission to act. Grants issued by restricted controllers SHOULD carry `expires_at`.

### 5.1 Succession

Because authority is immutable per key (Section 4.2), widening a restricted controller's authority means registering a new key. Without succession, the new key could not replace or revoke what the old key issued, and a principal without an unrestricted controller could not withdraw those grants at all. A Controller record therefore MAY list earlier keys in `supersedes`:

- Each entry MUST be the `id` of another Controller record of the same principal, current or retired, whose `valid_from` is earlier than this record's `valid_from`. This ordering makes cycles impossible.
- A controller's **lineage** is its own `id` plus, transitively, the lineage of every record it supersedes.
- A restricted controller owns a credential when the credential's `owner_controller` is in its lineage. `owner_controller` itself never changes.
- Succession transfers management of credentials, never authority: a replacement signed by the successor MUST satisfy the successor's own ceiling, and the superseded key keeps only its own authority until it is retired.

Verifiers MUST reject a principal document whose `supersedes` entry is unknown, names the record itself, or names a record whose `valid_from` is not earlier. Before retiring a restricted key that has no successor, the key SHOULD revoke the credentials it owns: afterwards only an unrestricted controller or provider suspension can withdraw them.

## 6. Retirement and Historical Binding

A retired Controller retains its original fields and adds `retired_at`. `invalid_from` is added only for compromise; no separate retirement reason or status enum is needed. Ordinary retirement does not revoke previously accepted grants, while compromise triggers the rules below.

For example, this record moves from `controllers` to `retired_controllers` after retirement. Before retirement, the same record without `retired_at` authorizes the Section 7 grant:

```json
{
  "id": "did:agent:AwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwM",
  "source": "https://dmsg.net",
  "valid_from": 1788652800000,
  "delegation": {
    "scopes": [
      "inbox.screen",
      "message.draft"
    ],
    "audiences": [
      "https://dmsg.net"
    ]
  },
  "retired_at": 1788746400000
}
```

Historical records MUST remain available while dependent signatures may need verification; providers SHOULD retain them indefinitely. Removal means binding evidence is unavailable, not implicitly valid. A retired key MUST NOT authorize a newly submitted event, even if its `created_at` predates retirement. Previously accepted grants may remain usable subject to their audience, scopes, constraints, validity, and current status. Providers MAY apply a disclosed policy that also suspends or revokes them.

On compromise, the host MUST retire the key and set `invalid_from` to the earliest known compromise time, or `valid_from` if unknown. A retired record MAY later gain `invalid_from` or move it earlier; it MUST NOT be moved later or cleared. Verifiers MUST consult the latest record even when holding an older snapshot. Services MUST suspend or revoke affected current credentials unless trusted evidence binds the exact grant hash to acceptance before `invalid_from`. An authorized uncompromised controller — an unrestricted controller, or a restricted successor within its ceiling — can issue a replacement grant to restore authority. Because keys cannot be re-registered, compromise handling needs no propagation across registration versions.

### 6.1 What History Proves

Reading `retired_controllers` at the canonical URL lets a verifier confirm the principal's current assertion that a particular key had particular permissions during `[valid_from, retired_at)`. It avoids retaining every whole-document snapshot. It does **not** prove when an event was signed: the signer controls `created_at` and a stolen key can backdate a signature.

Services MUST persist an [Agent Identity accepted record](../agent-identity/1.0.md#83-accepted-records) for each accepted event:

```json
{
  "envelope": { "hash": "<accepted envelope hash>", "event": {}, "signature": "..." },
  "accepted_at": 1788656400000
}
```

`accepted_at` is the service's clock at first acceptance. It MUST NOT be copied from `event.created_at`, rewritten by retries, or inferred from credential `updated_at`. The service MUST check both `created_at` and `accepted_at` against the current record's authority interval, store the exact checked controller record, and serialize local controller changes and acceptance so a retired record cannot pass a stale local check. For a remote principal, the cache bound in Section 3 still applies; later discovered retirement or compromise MUST trigger reevaluation of affected credentials.

Relying parties choose and disclose one of these evidence policies:

- **Online service-trusting**: verify the signature, full permission ceiling, historical interval, and current status using the canonical principal document and accepted records from its authoritative delegation service. An accepted record fetched over HTTPS is a service assertion; this trusts that service's clock and acceptance checks.
- **Independent historical evidence**: additionally require evidence binding the exact event hash to observation during the authority interval and before any `invalid_from`, from a timestamp/log/receipt authority independently trusted by the verifier or the verifier's own durable observation. A retired key's signature and timestamp alone MUST NOT satisfy this requirement. Evidence must also establish the event's acceptance when the decision depends on service acceptance rather than mere existence.

High-assurance relying parties SHOULD use independent historical evidence, especially after compromise. Missing or untrusted evidence means historical authorization is **unverifiable**, not that the Ed25519 signature is mathematically invalid. A signed principal snapshot may establish the issuer's assertion about a historical binding, provided the issuer key has an independently established trust chain; it does not timestamp an unrelated grant. Bare JSON snapshots, bundled untrusted keys, and signer-chosen event times are insufficient. This version does not standardize offline receipts or snapshot signature formats, and cannot prove current revocation status offline.

## 7. Delegation Events and Acceptance

Events use Agent Identity 1.0 envelopes with `event.protocol = "agent-delegation/1.0"`. Delegation events carry only the six Agent Identity event fields; following the closed event object rule, services MUST reject any other top-level event field. Anyone MAY submit an envelope; authority comes from its signature and the controller record, not the submitter's login. Services MUST verify envelope shape, hash, signature, and actor. An exact resubmission of an accepted envelope is an idempotent lookup ([Agent Identity Section 6.3](../agent-identity/1.0.md#63-exact-resubmission)) answered with the credential as it stood after that envelope was accepted; it is performed before live timestamp, nonce, and current-controller authorization checks and MUST create no new acceptance or state mutation. All other submissions MUST satisfy the live Agent Identity timestamp window and nonce rules.

A delegation `id` MUST match `^[A-Za-z0-9._~-]{1,128}$` and MUST NOT be `.` or `..`. The unreserved character set needs no percent-encoding in URLs and has no Unicode look-alikes, so IDs that are shown to people, or allocated as names, cannot be spoofed with confusable characters.

### 7.1 Grant

A `delegation.grant` payload has the following shape. In this example, both `event.created_at` and first `accepted_at` are `1788656400000`, and `event.actor` is the dmsg record's `id` from Section 6:

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "principal_id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "subject": "did:agent:AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI",
  "audiences": [
    "https://dmsg.net"
  ],
  "scopes": [
    "message.draft"
  ],
  "constraints": {
    "requires_human_approval": true
  },
  "not_before": 1788656400000,
  "expires_at": 1788742800000
}
```

`id`, `principal_id`, `subject`, `audiences`, and `scopes` are REQUIRED. `principal_id` MUST be the canonical principal ID; display metadata for the principal comes from its authoritative document, not from the grant. `audiences` MUST be a non-empty list of HTTPS origins; `scopes` MUST be a non-empty list of non-empty permission strings and MUST NOT contain `"*"`. Optional `relationship` is an application label. Optional `constraints` is an object. `not_before` and `expires_at` are optional timestamps. If present, `expires_at` MUST exceed both `event.created_at` and `not_before` (if present). A service MUST NOT accept a grant already expired at acceptance time.

Acceptance MUST:

1. Resolve `principal_id` (Section 3) and require the authoritative document's `id` to equal it exactly; an alias is rejected.
2. Find exactly one **current** record with `record.id == event.actor`; require both event creation and acceptance times at or after `valid_from`.
3. Require `delegation` and enforce the Section 5 scope and audience ceiling on the complete payload.
4. On replacement, require the existing credential's `principal_id`, `subject`, and protocol identifier to equal the new grant's, and enforce the Section 5 ownership rule. A credential ID MUST NOT be reused for another principal or another subject; delegating to a different agent requires a new ID.
5. Persist the accepted record, the checked controller record, and the materialized state atomically. The first grant assigns `owner_controller`.

An accepted replacement supplies all new grant fields; it is not a merge. A later authorized grant MAY reactivate a revoked credential under the same ID. Services MUST serialize replacements and revocations by acceptance order, not by signer-chosen timestamps. Exact-envelope retries MUST return the original acceptance result without reapplying an old event or rolling back state; current state is retrieved separately.

### 7.2 Revoke

A `delegation.revoke` payload contains REQUIRED `id` and canonical `principal_id`, plus optional `reason`; `id` follows the ID grammar above. The referenced credential MUST exist under that principal. Apply the same envelope, resolution, current-record, actor, time, persistence, and ordering checks as for a grant, then require either unrestricted `delegation: "*"` or a restricted controller that owns the credential through its lineage (Section 5.1).

A revocation withdraws the current credential's authority. A subject can decline to use a credential or request suspension; it cannot issue a principal revocation without controller permission. Service-imposed suspension is distinct from principal revocation. Every implementation MUST support revocation and compromise reevaluation.

## 8. Credential and Verification

A credential is an unsigned materialization of accepted events and provider status. Its fields are:

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | Yes | Delegation ID. |
| `protocol` | Yes | `agent-delegation/1.0`. |
| `principal_id` | Yes | Canonical principal ID from the grants. |
| `subject` | Yes | Agent ID from the grants; immutable per credential ID. |
| `relationship` | No | Application label from the latest grant. |
| `scopes` | Yes | Non-empty scope list from the latest grant. |
| `audiences` | Yes | Non-empty relying-application origins from the latest grant. |
| `constraints` | No | Constraint object from the latest grant. |
| `not_before`, `expires_at` | No | Grant validity timestamps. |
| `status` | Yes | Current status as defined below. |
| `controller` | Yes | Actor of the latest accepted grant/revoke event. |
| `owner_controller` | Yes | Agent ID of the first grant signer, immutable. |
| `grant_event_id` | Yes | Hash of the latest accepted grant, including after revocation. |
| `event_id` | Yes | Hash of the latest accepted grant/revoke event. |
| `accepted_at` | Yes | Acceptance time of that latest event. |
| `updated_at` | Yes | Last event or provider status change timestamp. |
| `checked_at` | Yes | Service clock when this view was produced. |

Grant-derived fields remain from the latest grant after revocation; controller fields and `event_id` identify the revoker. `status` is `active`, `suspended`, `expired`, or `revoked`; revocation MUST NOT be hidden by a later expiration calculation. `updated_at` includes provider status changes and is never historical time evidence. `checked_at` lets a relying party judge how fresh the status is; provider status changes do not change event acceptance times. Before `not_before` the grant is unusable regardless of an `active` label; at or after `expires_at` it is unusable.

Credentials and accepted records are unsigned service views. A presented credential MUST be checked through `delegation_query_url` obtained from authoritative principal resolution, never through a URL supplied by the presenter. The returned `principal_id`, subject, ID, and event hashes MUST match the claim being relied upon. A direct service read can use that same service for status, but does not by itself establish principal authority for the service.

A verifier MUST check the latest grant's signature, controller record, grant ceiling, authority interval, and evidence under Section 6.1, together with current status. When reconstructing ownership, replacements, or revocations, it MUST verify the necessary accepted event history, each event's controller permissions, and any `supersedes` lineage it relies on, not just the latest signature. Historical verification MUST NOT apply the live timestamp/nonce submission window to archived events; it verifies their cryptography and recorded acceptance-time conditions. A fresh submission remains subject to the live window.

Before an action, the relying application MUST match its own configured origin against the signed grant's `audiences`, enforce scopes and constraints, check the validity window and current status, and authenticate the subject's request. An audience is never inferred from `source`, HTTP `Origin`, or an untrusted caller parameter. Stale or unavailable status MUST NOT silently become `active`, and relying parties MUST check current status before sensitive actions. A credential is not a bearer session token and does not prove the subject accepted representation.

## 9. HTTP API and Profile Integration

Services MUST expose public credential, event-history, submission, and existence-query endpoints. Errors, lists, accepted records, and discovery follow [Agent Identity Section 8](../agent-identity/1.0.md#8-http-conventions). The following paths are RECOMMENDED; the HTTP path version is independent of the protocol identifier:

```text
GET  /.well-known/agent-delegation
GET  /v1/delegations/{delegation_id}
GET  /v1/delegations/{delegation_id}/events
POST /v1/delegations
POST /v1/delegations/query
```

### 9.1 Authentication and Visibility

Reads, submissions, and public existence queries MUST be available without account authentication. Services MAY apply rate limits, quotas, API keys, or proof-of-work for abuse control and SHOULD retain an unauthenticated verification path. Transport credentials MUST NOT substitute for controller signature and permission checks. A submitter need not be the subject, controller, or an account holder.

Anyone who knows a credential ID can read it. Services MAY redact private data, but MUST NOT present incomplete evidence as independently verifiable. Missing necessary evidence MUST cause verification to fail closed. IDs may be guessed; hosts SHOULD keep private information out of credentials.

### 9.2 Service Discovery

`GET /.well-known/agent-delegation` SHOULD return an Agent Identity discovery document. The endpoint names are `delegations` (the base URL of the credential and event reads and of submission) and `query`:

```json
{
  "protocol": "agent-delegation/1.0",
  "service": "https://api.al.ink",
  "endpoints": {
    "delegations": "https://api.al.ink/v1/delegations",
    "query": "https://api.al.ink/v1/delegations/query"
  },
  "features": [
    "grants",
    "revocations",
    "event-history"
  ]
}
```

Endpoint URLs MUST use HTTPS. A client MAY read discovery at the origin of the principal's authoritative `delegation_query_url` to locate the other endpoints. A presenter-supplied discovery URL does not establish authority.

### 9.3 Credential and Event Reads

Delegation IDs are drawn from the unreserved URL character set, so `delegation_id` appears in these paths unchanged. `GET /v1/delegations/{delegation_id}` returns the Section 8 credential with a fresh `checked_at`. `GET /v1/delegations/{delegation_id}/events` returns an Agent Identity list whose `result` contains accepted records `{ envelope, accepted_at }` in service acceptance order. Different controllers have separate nonces; nonce order MUST NOT replace acceptance order.

### 9.4 Submission

`POST /v1/delegations` accepts a signed grant or revoke envelope, applies all Section 7 checks, and returns the resulting Section 8 credential. Exact accepted-envelope retries follow Section 7's idempotent lookup rule.

### 9.5 Queries

`POST /v1/delegations/query` accepts an object with optional `subject`, `principal_id`, `id`, `status`, `limit`, and `cursor`. Agent IDs and principal URLs MUST be valid; `principal_id` MUST be canonical. `limit` MUST be a positive integer, defaults to 20, and SHOULD be capped at 100.

A public existence query MUST include both `subject` and `principal_id`. A query omitting either is private enumeration: it MUST include at least one and MUST require authenticated authorization from the side being enumerated. The subject may authorize listing its own delegations; a current controller requires delegation authority and the ownership check from Section 5. Separately authenticated owner management MAY authorize the principal's side. Controller membership alone is insufficient. Services MAY refuse enumeration entirely.

The response is an Agent Identity list whose `result` contains Section 8 credentials, subject to the Section 9.1 redaction rule. No match returns an empty `result`; services SHOULD give the same empty response for nonexistent principals.

### 9.6 Agent Profile Hints

An Agent Profile MAY publish a `delegations` array with hints containing `principal`, optional `id`, optional `relationship`, and optional `scopes`. It proves no authority. Clients MUST resolve the canonical principal, query its authoritative `delegation_query_url` with the profile's Agent ID as `subject` and the hint's delegation ID when present, and verify the credential for their own audience under Section 8. A hint cannot select a trusted status service.

### 9.7 Errors

In addition to the Agent Identity codes, delegation services use:

| Code | Meaning |
| --- | --- |
| `principal_unresolvable` | The principal document cannot be resolved authoritatively. |
| `principal_not_canonical` | A signed `principal_id` or query `principal_id` is an alias or otherwise not canonical. |
| `controller_not_current` | `actor` is not a current Controller of the principal, or the time is outside its interval. |
| `delegation_not_permitted` | The Controller has no `delegation` authority. |
| `delegation_ceiling_exceeded` | A granted scope or audience is outside the Controller's ceiling. |
| `not_owner_controller` | A restricted Controller does not own the credential through its lineage. |
| `credential_not_found` | The referenced credential does not exist under the principal. |
| `credential_identity_mismatch` | A replacement changes the credential's principal, subject, or protocol. |
| `grant_expired` | `expires_at` is not after the event time, `not_before`, or the acceptance time. |

## 10. Security and Privacy

The principal URL remains the trust root, including for historical assertions. Archive retention does not protect against a malicious or compromised principal host rewriting its own history. Offline or stronger historical claims require independently anchored evidence. HTTPS resolution and redirects SHOULD enforce local network-access policies to prevent SSRF.

Separate keys per application reduce compromise impact. Provenance is public metadata and may expose which applications a person uses; hosts SHOULD explain this before registration and avoid device serials, account identifiers, or private endpoints in labels. Default hosted keys SHOULD be visibly identified, and full wildcard authority MUST be an explicit owner choice, never a third-party registration default.

Compromise response has three separate effects: stop accepting new signatures, reassess grants already accepted, and retain historical key and permission evidence. Mathematical signature validity, historical authorization, and current credential usability MUST NOT be collapsed into one verification result. A permission change affects future issuance; to withdraw already delegated authority, revoke or suspend the relevant credentials. `supersedes` lets a successor manage its predecessors' credentials, so registering a successor deserves the same owner scrutiny as registering authority.

A credential's subject never changes, so a Profile hint or relying-party cache keyed by delegation ID cannot be redirected to another agent. Public existence queries do not imply public enumeration. Sources, profile hints, and controller registration prove neither legal identity nor subject consent. Unknown scopes grant no capability. Credentials and principal documents MUST NOT contain private keys or bearer secrets.

## 11. Conformance

An implementation MUST enforce these outcomes in addition to Agent Identity envelope checks:

| Case | Required outcome |
| --- | --- |
| A key without `delegation` submits a grant, revoke, or enumeration query | Reject. Application signatures are verified separately. |
| dmsg grants an unlisted scope or an audience of `https://tokenlist.ing` | Reject. |
| Restricted controller replaces, revokes, or enumerates a credential outside its lineage | Reject, including revoked credentials. |
| Restricted successor revokes a credential its superseded key issued | Allow after the normal signature, time, and current-binding checks. |
| Unrestricted controller revokes another key's credential of the same principal | Allow after the normal signature, time, and current-binding checks. |
| Replacement grant changes `subject` or `principal_id` under an existing ID | Reject. |
| Grant names an alias instead of the canonical principal ID | Reject. |
| Retired key submits a backdated event | Reject new acceptance; an exact accepted retry cannot reapply state. |
| Ordinarily retired key's earlier grant is unexpired and unrevoked | May remain usable if historical evidence and all action checks pass. |
| Compromised key claims an old timestamp without trusted pre-cutoff acceptance evidence | Suspend/revoke affected credential; historical authorization is unverifiable. |
| A key is duplicated across current and retired lists, or re-registered after retirement | Reject the document. |
| `supersedes` names an unknown key, the record itself, or a record that is not earlier | Reject the document. |
| A Controller carries `delegation` but the document has no `delegation_query_url` | Reject the document. |
| Published authority is changed under the same key | Prohibited; use a new key. Old events cannot inherit new authority. |
| A retired Controller lacks `retired_at`, or a current one contains it | Reject the document. |
| A different controller revokes a grant | Preserve grant fields and `grant_event_id`; latest event fields identify the revoker. |
| Alias copy injects current or retired controllers | Discard copy authority and resolve the canonical URL. |
| A bare string in `controllers`, an unknown delegation policy, an empty object, or a wildcard in a restricted list | Reject; never infer unrestricted authority. |
| Delegation ID outside the ID grammar | Reject. |
| Offline bundle supplies its own untrusted snapshot issuer key | Insufficient independent historical proof. |

## Appendix A. Design Notes and Alternatives

This appendix is informative.

The repository’s Rust, TypeScript, and Python source SDKs include the types and validation helpers for this document. Service implementations remain responsible for authenticated historical evidence, live replay checks, atomic acceptance, and current status; SDK materialization alone is not verification. External applications such as TokenList.ing must match `record.id`, source, and lifecycle while keeping their application-signature scheme separate.

Labels on a string array would solve provenance only. A single `scopes` field would still miss audiences, cross-controller replacement, revocation, enumeration, and signing-only bindings. Archiving just keys would lose historical permission ceilings. Whole-document snapshots or a mandatory public transparency log can provide additional evidence, but are not required for the ordinary online history lookup; retained immutable controller records are the minimal storage model. No unsigned archive alone prevents backdating or supplies independent offline proof.

Succession is modeled as an immutable `supersedes` list rather than mutable ownership. Transferring `owner_controller` would make ownership depend on event history interpretation; a registration-time lineage keeps every ownership decision a pure function of the current principal document and the credential.
