# Agent Delegation Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-delegation/1.0`  
**状态**：草案  
**日期**：2026-08-18  
**依赖**：Agent Identity Protocol 1.0  
**可搭配**：Agent Profile Protocol 1.0  
**核心对象**：Agent Delegation Credential  

## 1. 概述

Agent Delegation Protocol 定义了可移植、可验证的代理授权凭据（Delegation Credential），用于声明特定智能体何时获得授权以代表某一委托主体（Principal）执行操作。委托主体可以是个人、组织、团队、项目、场地、活动或其他非智能体实体。

在整体架构中：Agent Identity 确立事件签名的密钥归属；Agent Profile 规范智能体的展示与检索元数据；Agent Delegation 则专注于解决代理授权边界问题：特定智能体被允许代表哪个委托主体在何种权限范围内行动。

本协议基于简洁的信任原语：委托主体由标准的 HTTPS URL 唯一标识，该 URL 公开发布一份 Principal Document（主体元数据文档），其中声明了获权代表该主体签名的 Controller Keys。授权事件本身即为标准的 Agent Identity 签名事件信封，其 `actor` 为受信任的 Controller Key 之一。因此，验证代理凭据直接复用了通用的信封验签逻辑，外加一次对 Principal Document 的标准 HTTP GET 读取。

本协议明确不涉及人类登录流程、账号恢复机制或法定身份核验。服务提供方如何判定并使用主体的 Controller Key 执行签名（如通过已登录用户的授权确认、组织管理员策略或人工审批），属于协议范围之外的具体实现考量。本协议核心聚焦于主体绑定机制、授权与撤销事件规范、当前生效凭证的生成规则及标准读取 API。

## 2. 规范用语

本文中的关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY`、`OPTIONAL` 仅在全大写出现时，按 BCP 14（RFC 2119、RFC 8174）的定义进行解释。

## 3. 设计目标

1. **主体明确解耦**：Agent Profile 仅描述智能体本身，不直接证明其代表的具体主体。
2. **统一信封体系**：Delegation 事件完全沿用标准 Agent Identity 签名信封，无须引入第二套证明格式。
3. **基于 URL 的信任锚点**：掌控 Principal URL 即掌控委托主体的身份权威，与通过私钥控制 `did:agent:` 保持同构。
4. **精确权限边界**：授权必须明确携带作用域（Scopes）与约束条件（Constraints），避免宽泛模糊的代理声明。
5. **撤销状态优先**：依赖方在实际采纳授权执行关键操作前，可快速核实凭据的实时有效状态。
6. **公开可验、关系图私密**：任何收到授权凭据的第三方均可公开核验；但未获授权的外部调用者无法枚举特定主体的完整授权关系图。
7. **提供方中立**：任何兼容服务均可托管 Principal Document 与凭据数据；应用层可在其上自主定义特定的 Scopes、Constraints 与授权流程。

## 4. 核心概念

| 概念 | 说明 |
| --- | --- |
| Principal（委托主体） | 被代表的实体主体：个人、组织、团队、项目、场地、活动或其他非 Agent 实体。 |
| Principal 标识符 | 标识该委托主体的规范 HTTPS URL。它是比对校验、持久化存储及签名覆盖的唯一权威字符串。 |
| Principal Document | 通过请求 Principal 标识符返回的 JSON 文档：包含委托主体的公开展示信息及其绑定的 Controller Keys。 |
| Alias（别名） | 指向该主体的其他可访问 HTTPS URL，仅作为便捷入口或展示句柄，不构成身份凭据，且可能动态变更。 |
| Controller Key | Principal Document 的 `controllers` 中列出的 Agent ID。由其签名的事件承载该主体的权威意志。 |
| Subject Agent（代理智能体） | 获得代理授权的 `did:agent:*` 标识符。 |
| Delegation Credential（代理凭证） | 由最新采纳的授权或撤销事件结合服务状态生成的生效凭据文档。 |
| Scope（作用域） | 应用层定义的授权能力标识，如 `inbox.screen`、`calendar.propose`、`alink.intro.request`。 |
| Constraint（约束条件） | 限制 Scope 使用边界的结构化 JSON 对象。 |
| Status（凭证状态） | 取值为 `active`（有效）、`suspended`（已挂起）、`expired`（已过期）或 `revoked`（已撤销）。 |

## 5. Principal 委托主体

### 5.1 Principal 标识符

`principal.id` MUST 为合法的 HTTPS URL。它是该委托主体的**规范标识符**（Canonical Identifier）：在各类事件与凭证中严格以此字符串形式出现，同时也是依赖方进行比较和持久化的唯一标准字串。

服务提供方 SHOULD 分配长期稳定且不包含易变语义的规范标识符，并将面向人类的易读名称（Handle）作为别名（Alias）进行发布（详见第 5.4 节）。Handle 可能因重命名、注销或转让而变更所有权；直接基于 Handle 构造的标识符会继承这种易变性，导致引用该标识符的所有凭据在 Handle 转让时被静默转移至下一任持有者名下。

标识符示例：

```text
https://api.al.ink/d9c6a99cne5g00a6scn0
https://profiles.example.com/org/acme
https://events.example.com/summit-2026
```

URL 是身份的信任根：对该 URL 所返回内容的控制权，直接等同于对该 Principal 身份的控制权。未来版本可能引入其他标识符方案（如去中心化 DID Method）。

### 5.2 Principal Document

携带请求头 `Accept: application/json` 发起的 `GET {principal.id}` 请求 MUST 以 `application/json` 格式返回 Principal Document。同一 URL MAY 为其他类型的客户端提供 HTML 等其他内容形式。Principal Document MUST 允许未认证客户端公开读取：核验代理凭据属于公开操作，若无法读取该文档，依赖方将无法完成任何验证。

Principal Document 是委托主体的公开名片。描述性字段用于说明主体信息；`controllers` 字段用于绑定获权代表其签名的密钥。在安全语义上，只有 `id` 与 `controllers` 承载信任权重——其余字段均为自声明的展示元数据，不构成经过验证的断言。

```json
{
  "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "type": "person",
  "name": "Yan",
  "description": "Founder of alink. Building agent-native contact infrastructure.",
  "avatar_url": "https://api.al.ink/d9c6a99cne5g00a6scn0/avatar.png",
  "aliases": ["https://al.ink/yan", "https://al.ink/d9c6a99cne5g00a6scn0"],
  "links": [
    { "name": "Homepage", "url": "https://yan.example.com", "rel": "homepage" },
    { "name": "alink", "url": "https://al.ink", "rel": "social" }
  ],
  "controllers": ["did:agent:PrincipalController-00000000000000000000000"],
  "delegation_query_url": "https://api.al.ink/v1/delegations/query",
  "updated_at": 1779753600000,
  "extra": {}
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 规范 Principal URL。 |
| `type` | string | 否 | 主体类型，SHOULD 取值为 `person`、`organization`、`team`、`project`、`venue`、`event` 或 `other`。 |
| `name` | string | 否 | 面向人类的可读名称。 |
| `description` | string | 否 | 简短自我介绍或描述。 |
| `avatar_url` | string | 否 | 头像或徽标的 HTTPS URL。 |
| `aliases` | string[] | 否 | 指向该主体的其他别名 HTTPS URL 列表。每项 MUST 为合法的 HTTPS URL，详见第 5.4 节。 |
| `links` | object[] | 否 | 辅助链接列表；每项遵循 Agent Profile `links` 规范结构（`name`、`url`、`rel`）。 |
| `controllers` | string[] | 是 | 获权代表该主体签名的 Agent ID 列表。MUST 非空；每项 MUST 为有效的 Agent ID。 |
| `delegation_query_url` | string | 否 | 该主体的代理凭据查询端点（详见第 8.6 节）的 HTTPS URL。MUST NOT 暴露允许未认证调用者遍历全部授权凭据的接口。 |
| `updated_at` | integer | 否 | 文档最后变更的 Unix 毫秒数。 |
| `extra` | object | 否 | 特定于应用的扩展数据对象。 |

签发 Delegation Credential 的 Principal SHOULD 显式声明 `delegation_query_url`：依赖方据此可直接定位权威凭据验证服务，无须盲目信任出示凭证方所声称的任意 URL。

消费端 SHOULD 保留未知扩展字段。托管方 SHOULD 采用与 Agent Profile 5.2 节类似的字段约束。在校验新提交事件时，服务端 SHOULD NOT 依赖缓存时间超过 300 秒的 Principal Document。

### 5.3 解析算法

委托主体可能通过别名发起访问，因此解析过程须遵循一套严谨的算法流程，而非单一 HTTP 请求：

1. 发送携带 `Accept: application/json` 的 `GET {url}` 请求，最多允许跟随 5 次 HTTP 重定向。每一次跳转 MUST 严格使用 HTTPS；解析器 MUST NOT 跟随至非 HTTPS Scheme 的目标地址。重定向 MAY 跨越不同 Origin。
2. 记重定向终止后的最终响应 URL 为 `final_url`，返回的 JSON 对象为 `document`。
3. 若 `document.id` 与 `final_url` 完全一致，则本次读取确认为权威响应：`document.id` 即为规范 Principal 标识符，`document.controllers` 即为绑定的权威密钥集。
4. 若不一致，表明该响应只是脱离自身标识符存放的非权威副本。解析器 MUST 丢弃其中的 `controllers` 数据，并 MUST 以 `document.id` 为目标重复执行步骤 1–3。若第二次请求仍无法获得权威响应，则判定解析失败。

字符串等值校验必须采用精确比对：发布方 SHOULD 统一采用归一化的标准 URL——Scheme 与 Host 采用小写，移除默认端口，不带 Query 参数与 Fragment 锚点——任何微小的字符串差异均代表不同主体。

上述步骤 4 是保障“URL 即身份锚点”的关键机制：只有在与自身 `id` 完全一致的端点上读取到的文档，才具备绑定 Controller Key 的法定权威；否则，任何第三方 Origin 均可通过在文档中填入他人的 `id` 并配上自己的 `controllers` 来伪造身份控制权。

### 5.4 别名机制

`aliases` 用于列出指向该委托主体的其他 HTTPS URL（如短链接、历史旧链接或个性化独立域名）。别名仅作为用户友好的入口，不代表底层权威身份。

- 各类事件与凭证中的 `principal.id` 和 `principal_id` MUST 严格填写规范 `id`。从别名发起的解析器在执行比对、存储、展示或签名之前，MUST 将其转换为规范 `id`。
- 别名端点 SHOULD 直接重定向至规范 URL，使常规解析在首次读取时即可权威终止。
- 在将别名作为委托主体的名称向人类用户展示前，客户端 MUST 确认该别名已列在规范文档的 `aliases` 列表中。任何 Origin 均可单向重定向至任意 Principal；只有 Principal Document 自身声明的列表才代表主体对该 URL 的权威认可。
- 别名 MAY 被重新分配所有权。客户端缓存“别名至规范标识符”的映射时间，MUST NOT 超过 Principal Document 自身的缓存生命周期。

### 5.5 Controller 密钥与轮换

Controller Key 是标准的 Agent Identity 密钥。它可由 Principal 本人直接持有、由其服务提供方代管，或由专门的签名服务统一管理；密钥由谁持有以及签名触发何种授权流程，属于提供方与应用层的策略范畴。

委托主体通过更新 `controllers` 列表来调整其授权密钥集合。从列表中移除某把 Controller Key 并不会自动追溯性地废止该密钥在列期间已获准的授权；若要彻底收回已委托出去的代理权力，Principal 须主动签发 `delegation.revoke` 撤销事件。因此，针对 Controller Key 泄露的标准应急响应必须同时包含两个动作：轮换更新 `controllers` 列表，并针对该密钥签发过的授权逐一签发撤销事件。

服务端在接受新事件时，MUST 严格校验事件的 `actor` 是否列于当前 Principal Document 的 `controllers` 中。

由于 Controller 的有效性校验发生在事件接受时刻，且本协议未定义 Principal Document 的历史快照机制，某把密钥被移出 `controllers` 后，早前由其签名的凭据依然维持已接受状态，但第三方在重新解析 Principal Document 时将无法直接溯源历史绑定关系。依赖方应根据第 7 节所述在两种信任策略之间进行选择。

## 6. Delegation 事件

Delegation 事件统一采用标准 Agent Identity 签名事件信封，并声明：

```json
{
  "protocol": "agent-delegation/1.0"
}
```

事件的 `actor` MUST 为 Payload 中所指委托主体当前合法的一把 Controller Key。任何实体均 MAY 向 Delegation 服务提交已签发的事件信封（包括代理智能体、提供方后台或镜像服务）；承载主体意志的是密码学签名，而非网络提交者。在符合第 8.1 节的前提下，服务端 MAY 针对请求实施限流与防滥用认证。

### 6.1 授权事件（Grant）

`delegation.grant` 事件用于创建或更新代理授权凭据。

```json
{
  "hash": "QWdlbnQtRGVsZWdhdGlvbi1ncmFudC1oYXNoLTAwMDA",
  "event": {
    "protocol": "agent-delegation/1.0",
    "type": "delegation.grant",
    "actor": "did:agent:PrincipalController-00000000000000000000000",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "subject": "did:agent:SubjectAgent-000000000000000000000000000000",
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"],
      "constraints": {
        "requires_human_approval": ["meeting.accept"]
      },
      "not_before": 1779753600000,
      "expires_at": 1790000000000
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

| Payload 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 稳定的代理凭据标识符，在当前服务内保持唯一。 |
| `principal` | object | 是 | 委托主体描述符。MUST 包含规范 `id`；SHOULD 包含 `type`；MAY 包含 `name`。 |
| `subject` | string | 是 | 获得代理权的 Agent ID。 |
| `relationship` | string | 否 | 应用层关系标签，如 `primary_delegate`、`assistant`、`organization_delegate` 或 `service_agent`。 |
| `scopes` | string[] | 是 | 应用层定义的具体代理权限集合。 |
| `constraints` | object | 否 | 应用层定义的结构化约束条件。服务端 SHOULD 保留未知字段。 |
| `not_before` | integer | 否 | 生效时间，在此 Unix 毫秒数之前授权尚未生效。 |
| `expires_at` | integer | 否 | 失效时间，在此 Unix 毫秒数之后授权失效。 |

针对 `delegation.grant` 事件，服务端在遇到以下任一情况时 MUST 拒绝接受：

- 信封未通过 Agent Identity 校验（结构、Hash、签名、Actor、时间窗口或 Nonce 违规）；
- `event.protocol` 不为 `agent-delegation/1.0`，或 `event.type` 不为 `delegation.grant`；
- `event.payload.id`、`event.payload.principal.id`、`event.payload.subject` 或 `event.payload.scopes` 缺失或非法；
- `event.payload.principal.id` 不是有效的 HTTPS URL，或未能按照第 5.3 节完成解析；
- 解析后的权威文档 `id` 与 `event.payload.principal.id` 不一致（授权 MUST 使用规范标识符，禁止使用别名）；
- `event.actor` 未列于 Principal Document 的 `controllers` 列表中；
- `event.payload.subject` 不是有效的 Agent ID；
- 同时提供了 `expires_at` 与 `not_before`，且 `expires_at` 不大于 `not_before`；
- 提供了 `expires_at`，且其数值不大于 `event.created_at`；
- `event.payload.id` 对应已存在的凭据，但其 `principal.id` 与本次提交的 `event.payload.principal.id` 不一致；
- 事件超出服务端设定的配额或策略限制。

同一 Principal 使用相同 `payload.id` 成功提交的新授权事件，将被用于全量替换旧凭据状态（例如调整 Scopes 或延长有效期）。该规则同样适用于已撤销的凭据：相同 `id` 与 Principal 的后续有效授权将把状态恢复为 `active` 并更新各字段——撤销动作终止的是当前授权实例，并非永久作废该标识符。标识符命名空间的管理策略（如保留、定价或短 ID 订阅）属于服务端的业务考量，不属于本协议规范范畴。

生成的凭据文档中，各代理业务字段直接取自授权事件的 `payload`。`status` 与 `updated_at` 由服务端维护管理；`controller` MUST 设置为有效事件的 `actor`；`event_id` MUST 设置为对应信封的 `hash`。

### 6.2 撤销事件（Revoke）

`delegation.revoke` 事件用于撤销之前已生效的代理凭据。其 `actor` MUST 为该 Principal 当前合法的一把 Controller Key（不强制要求与签发授权时的密钥相同）。

```json
{
  "hash": "QWdlbnQtRGVsZWdhdGlvbi1yZXZva2UtaGFzaC0wMDA",
  "event": {
    "protocol": "agent-delegation/1.0",
    "type": "delegation.revoke",
    "actor": "did:agent:PrincipalController-00000000000000000000000",
    "created_at": 1779757200000,
    "nonce": 2,
    "payload": {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal_id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
      "reason": "rotated_primary_agent"
    }
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

针对 `delegation.revoke` 事件，服务端在遇到以下任一情况时 MUST 拒绝处理：

- 引用的代理凭据不存在；
- 信封未通过 Agent Identity 校验；
- `event.protocol` 不为 `agent-delegation/1.0`，或 `event.type` 不为 `delegation.revoke`；
- `event.payload.id` 或 `event.payload.principal_id` 缺失或非法；
- `event.payload.principal_id` 与被引用凭据的 `principal.id` 不一致；
- `event.actor` 未列于 Principal Document 的 `controllers` 列表中；
- 事件超出服务端设定的配额或策略限制。

代理智能体自身可以停止出示凭据，或请求托管服务将凭证标记为挂起（Suspended），但只有经 Controller 签名的 `delegation.revoke` 事件才代表 Principal 的权威撤销。服务端 MAY 依照合规或滥用防范策略将凭据标记为 `suspended`；该服务状态不等同于主体的密码学撤销。

## 7. 凭证文档

Delegation Credential（代理凭据）文档是服务端根据最新被采纳的授权或撤销事件及提供方状态生成的当前凭证视图。

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "protocol": "agent-delegation/1.0",
  "principal": {
    "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
    "type": "person",
    "name": "Yan"
  },
  "controller": "did:agent:PrincipalController-00000000000000000000000",
  "subject": "did:agent:SubjectAgent-000000000000000000000000000000",
  "relationship": "primary_delegate",
  "scopes": ["inbox.screen", "meeting.propose"],
  "constraints": {
    "requires_human_approval": ["meeting.accept"]
  },
  "not_before": 1779753600000,
  "expires_at": 1790000000000,
  "status": "active",
  "updated_at": 1779753600000,
  "event_id": "QWdlbnQtRGVsZWdhdGlvbi1ncmFudC1oYXNoLTAwMDA"
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 来自有效授权事件的凭据标识符。 |
| `protocol` | string | 是 | 固定为 `agent-delegation/1.0`。 |
| `principal` | object | 是 | 来自有效授权事件的主体描述符。 |
| `controller` | string | 是 | 签署当前生效状态事件的 Controller `actor`。 |
| `subject` | string | 是 | 获得代理权的 Agent ID。 |
| `relationship` | string | 否 | 应用层关系标签。 |
| `scopes` | string[] | 是 | 应用层定义的代理权限列表。 |
| `constraints` | object | 否 | 应用层定义的约束条件。 |
| `not_before` | integer | 否 | 授权生效的 Unix 毫秒数。 |
| `expires_at` | integer | 否 | 授权失效的 Unix 毫秒数。 |
| `status` | string | 是 | 当前状态：`active`、`suspended`、`expired` 或 `revoked`。 |
| `updated_at` | integer | 是 | 最新事件接受或状态变更的 Unix 毫秒数。 |
| `event_id` | string | 是 | 生成当前状态的事件信封 `hash`。 |

凭证文档是服务端生成的只读视图，本身未经签名，也不包含内部服务端点 URL。这是严格的设计考量：当依赖方在带外收到一份凭证时，MUST NOT 盲目请求凭证内部携带的端点来校验状态——凭证出示方完全可能自行搭建虚假端点。权威验证链路必须溯源至委托主体：按照第 5.3 节解析 `principal.id`，从权威解析出的文档中读取 `delegation_query_url` 并发起校验。直接从某服务读取的凭证，则直接在该服务进行核验。

需要独立密码学核验的客户端 SHOULD 读取事件历史，按 Agent Identity 规范验证最新事件信封，并解析 Principal Document 校验 Controller 绑定。由于 Controller 绑定检查发生在事件接受时刻，而 Principal Document 本身不包含版本历史，因此依赖方可根据自身安全策略采用以下两种信任姿态之一：

1. **信任服务端（Service-trusting）**：认可 Delegation 服务在接受事件时所完成的 Controller 校验，客户端仅验证信封签名与服务端的实时状态。该姿态建立在信任该服务不会违规接受未经授权事件的前提之上。
2. **严格模式（Strict）**：仅当凭证对应的 `controller` 依然存在于当前 Principal Document 的 `controllers` 列表中时，才采信该凭据。一旦 Controller 发生轮换，严格模式下的依赖方将把旧凭据视为不可验证，并要求由当前有效的 Controller 重新签发授权。

对安全性要求极高的系统 SHOULD 采用严格模式。

## 8. HTTP API

Delegation 服务 SHOULD 暴露以下 HTTP 接口。路径中的 `/v1` 为服务端 API 版本，不代表事件内的协议标识符。

```text
GET  /.well-known/agent-delegation
GET  /v1/delegations/{delegation_id}
GET  /v1/delegations/{delegation_id}/status
GET  /v1/delegations/{delegation_id}/events
POST /v1/delegations
POST /v1/delegations/query
```

### 8.1 认证与可见性策略

除第 8.6 节的枚举查询外，本节定义的所有端点均为公开且无须鉴权的操作。本协议的权威基础源自密码学签名，而非传输层的 Access Token：

- 读取端点 MUST 对未认证的外部依赖方开放。提供公开验证是本协议的核心目标，而需要验证代理授权的一方通常与托管该凭证的服务无直接商业关联。
- `POST /v1/delegations` 的合法性完全由提交信封内的 Controller 签名决定。服务端 MUST NOT 将 Access Token 作为事件的权威依据，MUST NOT 因为提交者已通过 HTTP 鉴权就放行校验未通过的信封，也 MUST NOT 强制要求提交者必须为 Subject、Controller 或特定账号持有者。
- 服务端 MAY 在端点层应用 API Key、配额管理、IP 限流或工作量证明（PoW）以抵御 DoS 滥用。此类措施属于网络传输防护：其绝对不能替代密码学验签，且服务端 SHOULD 为依赖方保留无需认证的基础验证通道。
- 枚举查询是唯一的鉴权特例，MUST 要求合法授权（详见第 8.6 节）。

### 8.2 服务发现

`GET /.well-known/agent-delegation` SHOULD 返回服务的标准元数据：

```json
{
  "protocol": "agent-delegation/1.0",
  "service": "https://api.al.ink",
  "endpoints": {
    "delegations": "https://api.al.ink/v1/delegations",
    "query": "https://api.al.ink/v1/delegations/query"
  },
  "features": ["grants", "revocations", "event-history"]
}
```

通过 Principal Document 的 `delegation_query_url` 发现服务的客户端，MAY 读取该 URL 所在 Origin 的 `/.well-known/agent-delegation` 来探索该服务的其他可用端点。

### 8.3 读取凭证

`GET /v1/delegations/{delegation_id}` 返回当前最新的生效凭证。`GET /v1/delegations/{delegation_id}/events` 返回历史已接受信封列表供独立验签，按服务端接受的时间顺序从旧到新排列。由于同一份凭据的授权与撤销事件可能由不同的 Controller 签署，因此决定凭据状态变更序列的是服务端接受顺序，而非单一密钥的 Nonce 顺序。

基于 Delegation ID 的查询属于公开接口：任何获知 ID 的实体均可获取对应凭据。服务端 MAY 制定内容脱敏或可见性策略，且 SHOULD 假定服务端生成的任何凭据对知晓其 ID 的实体均属可公开数据——短 ID 或自定义语义 ID 在设计上天然具备可猜测性。

### 8.4 状态快速检查

`GET /v1/delegations/{delegation_id}/status` 仅返回当前有效状态，无需拉取完整凭证对象：

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "status": "active",
  "checked_at": 1779757200000,
  "expires_at": 1790000000000,
  "event_id": "QWdlbnQtRGVsZWdhdGlvbi1ncmFudC1oYXNoLTAwMDA"
}
```

依赖方在依据代理授权执行敏感操作前 SHOULD 显式核查实时状态，且核查动作 SHOULD 在经由 Principal Document 权威解析出的端点上执行，而非直接使用出示方提供的未经核实 URL。

### 8.5 提交 Delegation 事件

`POST /v1/delegations` 接收 `delegation.grant` 或 `delegation.revoke` 事件信封，并返回更新后的凭证或最新状态。请求体即为标准签名信封，无需附带外部 Access Token。

### 8.6 查询 Delegation 授权

`POST /v1/delegations/query` 专注于解决单一核心问题：特定智能体是否持有来自特定委托主体的有效授权？该端点在设计上是**精准存在性核验**接口，而非全量列表遍历接口。

**公开查询** MUST 同时包含 `subject` 与 `principal_id`；`id`、`status` 与 `limit` 为可选参数，`limit` 默认值为 `20`，服务端 SHOULD 设置最大上限为 `100`。服务端 MUST 在无需调用方提供身份认证的情况下直接响应公开查询。

未同时提供 `subject` 与 `principal_id` 的请求被归类为**枚举查询**（例如试图列出“特定主体的全部授权”或“特定智能体代理的全部主体”）。服务端 MUST NOT 向未认证调用者响应枚举查询，MUST 要求发起方提供被枚举方的合法授权证明（即 Principal 的 Controller Key 签名，或 Subject Agent 自身的密钥签名），并 MAY 完全拒绝此类枚举请求。即使单份凭据本身可公开，委托主体的完整授权关系网仍然属于高度敏感的隐私：其可能暴露主体的组织架构、人员分工、家庭成员构成、法律代理关系或商业合作网络，而这些是任何单一凭证所不会泄露的。

每个 `result` 项可为第 7 节所定义的完整凭据文档，亦可为合规脱敏后的子集；在对请求者可见时，子集 MUST 至少保留 `id`、`principal`、`subject`、`scopes` 及 `status`。服务端 MAY 进行进一步脱敏，并 MAY 对该端点施加频率限制。无匹配记录时返回空数组 `result`；针对不存在的 Principal，服务端 SHOULD 返回相同的空结果，以避免该端点成为主体枚举探测工具（Oracle）。

查询请求示例：

```json
{
  "subject": "did:agent:SubjectAgent-000000000000000000000000000000",
  "principal_id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "status": "active",
  "limit": 20
}
```

查询响应示例：

```json
{
  "result": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "subject": "did:agent:SubjectAgent-000000000000000000000000000000",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "scopes": ["inbox.screen", "meeting.propose"],
      "status": "active"
    }
  ]
}
```

## 9. 与 Agent Profile 的协同关系

Agent Profile MAY 在顶层 `delegations` 字段中提供代理凭据的索引提示，但 Profile 元数据本身 MUST NOT 被直接当作代理关系的有效证明。

推荐结构：

```json
{
  "delegations": [
    {
      "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
      "principal": {
        "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
        "type": "person",
        "name": "Yan"
      },
      "relationship": "primary_delegate",
      "scopes": ["inbox.screen", "meeting.propose"]
    }
  ]
}
```

该提示设计上不携带服务接入 URL，因为发布该 Profile 的智能体正是待核验方。客户端 MUST 将其仅作为发现线索，并经由委托主体展开权威验证：按第 5.3 节解析 `principal.id`，从权威文档中读取 `delegation_query_url`，以当前智能体为 `subject`（若提示中包含 `id` 则一并带上）发起精准查询，随后验证返回凭据的有效状态及关联签名事件。

## 10. 安全与隐私考量

- 控制 Principal URL 所在的 Origin 即等同于掌控该主体的身份。Principal Document MUST 通过配置有效 TLS 证书的 HTTPS 协议提供。DNS 劫持或 Origin 攻陷等同于身份被冒用；关键系统 MAY 在本地安全策略中静态锁定已知的 Controller Keys。
- 别名（Alias）仅是指向主体的寻址路径，绝不能代表主体表达权威。任何 Origin 均可自由重定向至任意 Principal URL，因此解析器 MUST 严格以在自身 `id` 处读取到的文档作为唯一权威（第 5.3 节），MUST NOT 将别名所在的 Origin 视为任何维度的信任依据。
- Principal Document 中的描述性字段（`name`、`description`、`avatar_url`、`links`、`aliases`）属于自声明展示元数据，不构成经过验证的断言。
- 仅移除 Controller Key 并不会自动撤销已签发的历史授权。应急响应须同时执行 Controller 轮换与受影响凭据的显式撤销。轮换后第三方将无法独立溯源历史绑定，依赖方应依据第 7 节策略选择信任模式。
- Delegation 凭据证明的是委托主体的单向授权意图，并不证明代理智能体的实际参与。任何控制 Principal URL 的实体均可单方面签发指向任意 Agent ID 的授权凭证。依赖方 MUST NOT 仅凭凭证的存在就推定该代理智能体已接受或认可该委托主体；正向的参与信号包括智能体主动出示凭据，或在其自主签名的 Profile `delegations` 列表中显式声明该凭据。
- 凭证文档是服务端生成的只读视图，本身未经签名。依赖方 MUST 溯源至 Principal Document 获取权威服务地址，禁止盲目信任凭据内部或 Profile 提示中附加的 URL，以防状态校验被引导至攻击者控制的恶意端点。
- 委托主体的全量授权关系网比单份凭证具有更高的隐私敏感度。查询端点面向未认证调用者 MUST 仅提供精准存在性校验，服务端 SHOULD 严格规范枚举接口的访问控制与鉴权凭据。
- 凭证 ID 在事实层面上具有公开性：采用简短 ID 或自定义规律 ID 的服务应当预见遍历探测风险。服务端 SHOULD 避免在 `constraints` 与 `extra` 中存放机密数据，并 MAY 依照策略对读取结果进行脱敏。
- Scopes 与 Constraints 均由应用层定义。依赖方 MUST NOT 假定未识别的未知 Scope 具备任何合法权限。
- Delegation 凭据不属于 Session Token。其本身不直接授权单次 HTTP 请求；服务端仍需结合请求级认证、业务策略检查及必要的人工审批确认。
- 主体显示名称存在被仿冒的风险。服务端 SHOULD 保留常见敏感名称并公布审核机制；系统的唯一权威标识是规范 Principal URL，而非可读显示名或别名。
- Principal Document 与凭据中 SHOULD NOT 包含 Bearer Token、内部 Webhook URL、私密联系方式或机密数据。
- 撤销状态查询端点 SHOULD 具备高可用性并支持短期缓存。执行敏感业务操作时 SHOULD 避免仅依赖过期的缓存状态。

## 11. 最小实现清单

符合 Agent Delegation 1.0 规范的服务端 MUST 支持：

1. 基于 Agent Identity 规范的事件信封验证。
2. 遵循第 5.3 节的 Principal Document 权威解析算法（含非权威副本识别与 Controller 校验）。
3. 接收包含规范 Principal 标识符的有效 `delegation.grant` 事件，并支持按 Delegation ID 返回生成的有效凭证。
4. 提供历史已接受事件列表供客户端独立验签。
5. 准确返回凭证的实时状态（包含 `revoked` 与 `expired`）。
6. 支持同时携带 `subject` 与 `principal_id` 的公开存在性查询，并严格拒绝未认证的枚举查询。
7. 正确拦截无效信封、非 Controller 签署的事件、格式错误的标识符、以别名作为 `principal.id` 的事件以及生效时间窗口矛盾的请求。

推荐的完善实现 SHOULD 同时支持撤销事件处理、服务发现机制、别名解析支持、针对 Principal 与 Subject 的受权枚举能力、细粒度可见性控制策略以及与 Agent Profile 的协同发现。

## 12. 未来规划

未来版本可能进一步标准化的方向包括：

- 支持非 HTTPS 的 Principal 标识符方案（如去中心化 DID Method）；
- 服务端签名的凭证文档，支持在发起实时状态查询前进行离线核验；
- 枚举查询的标准鉴权协议；
- Controller 密钥标签化及 Principal Document 的第三方权威背书机制；
- 具备隐私保护特性的 Controller 绑定方案（如盲签名或零知识证明条目）；
- 面向主流应用场景的标准 Scope 注册表体系；
- 代理智能体（Subject）针对授权凭据的显式签名确认或拒绝机制；
- 委托式 Profile 托管与权限管理；
- 跨提供方的 Delegation 数据镜像与状态多活复制；
- 正式 JSON Schema 校验规范与一致性合规测试套件。
