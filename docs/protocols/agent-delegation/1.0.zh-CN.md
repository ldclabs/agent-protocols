# Agent Delegation Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-delegation/1.0`
**状态**：Draft
**日期**：2026-09-06
**依赖**：Agent Identity Protocol 1.0
**可选使用**：Agent Profile Protocol 1.0

## 1. 概述

Agent Delegation 定义智能体何时可以代表以规范 HTTPS URL 标识的主体（principal）行动。主体文档将密钥绑定到主体，签名的 grant 事件向 subject 智能体授予具体权限。HTTPS URL 仍是身份信任根。

协议将**密钥来源**、**签发 delegation 的权限**与**历史归属**分开。登记一把密钥不自动赋予它签发 delegation 或管理其他 controller 的权限。服务商的默认签名器、第三方应用签名器和用户本地签名器使用相同的记录格式，只取得文档显式授予的权限。

本规范仍为尚未发布的 1.0 草案，本次修订直接替换早期字符串数组形式的 controller 模型。主体文档和签名事件均使用 `agent-delegation/1.0`；实现 MUST 检查必填记录和事件字段，不能只凭协议标识符判断兼容性。controller 记录 MUST NOT 被压平为不受限的密钥列表。

## 2. 规范用语

关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHOULD`、`SHOULD NOT`、`MAY` 按 BCP 14（RFC 2119、RFC 8174）解释，具有规范性含义。

所有时间戳均为非负 JSON 安全整数，单位毫秒。Agent ID MUST 符合 Agent Identity 1.0。必填字符串 MUST 非空。协议定义的允许列表、scopes、audiences、aliases MUST 无重复条目；应用自定义 JSON 数组保留其应用语义。未知展示或扩展字段 SHOULD 保留。不支持的权限字段或值 MUST 按拒绝处理：验证器 MUST NOT 忽略自己无法执行的限制。

## 3. 主体身份与解析

主体可以是个人、组织、团队、项目、场所、活动或其他非智能体对象。其 `id` MUST 为规范 HTTPS URL。RECOMMENDED 使用稳定、不透明的标识符；可能改名的 handle 放入 `aliases`。

`GET {principal.id}` 携带 `Accept: application/json` MUST 返回公开、无需认证的 JSON 主体文档。解析步骤：

1. 最多跟随五次重定向，每一跳均使用 HTTPS，允许跨源。
2. 若返回的 `document.id` 与最终响应 URL 完全相等，该文档具有权威性。
3. 否则，丢弃副本中**全部**携带信任语义的字段，包括 `protocol`、`controllers`、`retired_controllers`、`delegation_query_url`，再对 `document.id` 执行一次步骤 1–2。第二次仍非权威读取则失败。
4. 使用 controller 权限前，要求 `document.protocol` 等于 `agent-delegation/1.0`。

URL 身份按字符串精确比较。发布者 SHOULD 将 scheme/host 小写、去掉默认端口，并避免在主体 ID 中使用查询和片段。事件 MUST 使用规范 ID，不得使用别名。将别名显示为主体名称前，客户端 MUST 确认权威文档的 `aliases` 包含它。别名映射的缓存时间 MUST NOT 长于主体文档。

接受新事件时，服务 MUST 使用最近 300 秒内获取的文档；敏感操作 SHOULD 立即重新验证。宿主 MUST 在 controller 变更时使自己的权限缓存失效。此上限表示陈旧权限的最大窗口，不代表分布式系统中的即时撤销。

## 4. 主体文档

```json
{
  "protocol": "agent-delegation/1.0",
  "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "type": "person",
  "name": "Yan",
  "aliases": [
    "https://al.ink/yan"
  ],
  "controllers": [
    {
      "id": "did:agent:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
      "source": "https://al.ink",
      "name": "alink default signer",
      "valid_from": 1788652800000,
      "delegation": "*"
    },
    {
      "id": "did:agent:AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE",
      "source": "https://tokenlist.ing",
      "name": "TokenList.ing user canister",
      "valid_from": 1788652800000
    }
  ],
  "retired_controllers": [],
  "delegation_query_url": "https://api.al.ink/v1/delegations/query",
  "updated_at": 1788652800000
}
```

示例密钥只用于说明数据形状，不是生产密钥。

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `protocol` | string | 是 | 必须为 `agent-delegation/1.0`。 |
| `id` | string | 是 | 主体规范 URL。 |
| `controllers` | Controller[] | 是 | 当前记录。MAY 为空，包括恢复账号期间。 |
| `retired_controllers` | Controller[] | 否 | 历史记录；缺省表示空数组，不表示未知密钥获得授权。 |
| `delegation_query_url` | string | 否 | delegation 凭证的权威 HTTPS 查询端点。签发方 SHOULD 发布。 |
| `updated_at` | integer | 是 | 文档最后变更时间，不是密码学时间戳。 |
| `type`、`name`、`description`、`avatar_url` | string | 否 | 展示元数据。`type` SHOULD 为 `person`、`organization`、`team`、`project`、`venue`、`event` 或 `other`；`avatar_url` MUST 为 HTTPS URL。 |
| `aliases` | string[] | 否 | HTTPS 别名，适用第 3 节。 |
| `links` | object[] | 否 | Agent Profile 链接条目，包含字符串 `name`、`url`、`rel`。 |
| `extra` | object | 否 | 应用元数据。展示与扩展字段均不授予权限。 |

### 4.1 统一的 Controller 类型

`controllers` 和 `retired_controllers` 都使用**同一个 Controller 类型**。淘汰 controller 就是在原记录上增加 `retired_at`，不是另一个实体，也不是权限不同的副本。

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 密钥的 Agent ID，等于签名事件的 `actor`，无需额外登记 ID。 |
| `source` | string | 是 | 签名服务的 HTTPS origin；用户本地签名器使用 `local`。 |
| `valid_from` | integer | 是 | 绑定起点，包含该时刻；MUST NOT 晚于发布时间。 |
| `name` | string | 否 | 展示标签，例如 `alink default signer` 或 `Personal key vault`。 |
| `delegation` | `"*"` 或 object | 否 | 第 5 节定义的 delegation 权限；缺省表示没有 delegation 权限。 |
| `retired_at` | integer | 仅淘汰时 | 绑定终点，不包含该时刻；MUST 不早于 `valid_from`。相等表示尚未接受任何事件便淘汰。 |
| `invalid_from` | integer | 仅泄漏时 | 从何时起签名不可信；MUST 满足 `valid_from <= invalid_from <= retired_at`。 |

`source` 的 origin MUST 为序列化 HTTPS origin：主机名小写，无 userinfo、路径、查询、片段或默认端口。例如 `https://al.ink`、`https://dmsg.net`、`https://tokenlist.ing`；本地签名器使用 `local`。audience origin 使用相同格式。`source` 和 `name` 描述主体声明的来源，不证明保管方式、用户同意或服务背书，MUST NOT 授予权限。应用自行定义签名格式与同意检查；密钥绑定本身不授权应用动作。MUST NOT 仅因来源 URL 被列出便抓取它。

登记 MUST 取得主体所有者授权，并通过单次、会过期、具有域分离且绑定主体、密钥、来源与 delegation 策略的挑战验证密钥持有证明。登记、淘汰、恢复和权限变更需要独立的所有者管理授权；即使 `delegation: "*"` 也不授予这些管理能力。

### 4.2 不可变绑定

在同一主体下，一把密钥在两份列表中合计 MUST 最多出现一次，淘汰后 MUST NOT 重新登记。发布后 `id`、`source`、`valid_from`、`delegation` MUST NOT 修改；只有展示用 `name` 可以编辑。改变权限需要新密钥和新绑定，以此省去登记版本和历史权限匹配。不要求定期轮换。

淘汰 MUST 原子地将记录从 `controllers` 移入 `retired_controllers`，并添加 `retired_at`。当前记录 MUST NOT 包含淘汰或泄漏时间戳；淘汰记录 MUST 包含 `retired_at`。验证器 MUST 拒绝重复密钥或畸形记录，不能合并权限。

## 5. Delegation 权限

只保留三种配置：

| `delegation` | 签发权限 | 替换 / 撤销 / 枚举 |
| --- | --- | --- |
| 不提供 | 无，仅公示密钥绑定 | 无 |
| `"*"` | 任意显式 scope 和 audience | 此主体的任意凭证 |
| `{ "scopes": [...], "audiences": [...] }` | 仅列出的 scope 和依赖方应用 | 仅本密钥最初创建的凭证 |

受限对象 MUST 仅包含 `scopes` 和 `audiences`，两者均为非空数组。scope 精确匹配，不支持前缀、glob、层级或通配符；audience 为 HTTPS origin。未知策略字段、空数组、`null`、`{}` 和数组内通配符 MUST 被拒绝。不受限字符串 `"*"` 是所有者显式选择，绝不是登记默认值。

例如，dmsg controller 使用：

```json
{
  "scopes": ["inbox.screen", "message.draft"],
  "audiences": ["https://dmsg.net"]
}
```

授予的每个 scope 和 audience MUST 被允许。此密钥不能签发面向 TokenList.ing 的授权、授予其他 scope 或覆盖其他密钥的凭证。第 4 节 TokenList.ing 示例完全省略 `delegation`，因为它只公示应用签名密钥。本地密钥同样可以采用三种配置中的任一种；本地保管不意味着全权。

每份凭证有不可变的 `owner_controller`，取第一次接受的 grant 签名者 Agent ID。替换、撤销和重新激活 MUST NOT 转移所有权。受限 controller 在替换、撤销和枚举时 MUST 匹配 owner；每次替换也 MUST 满足自身 delegation 权限上限。不受限 controller 可以管理其他或已淘汰密钥签发的凭证，但仅限同一主体。

每种操作均 MUST 要求密钥仍为当前密钥，且操作时间不早于 `valid_from`。枚举需要证明该密钥身份；仅签名密钥不能枚举。本协议不再定义 controller 级别的 subject、TTL 或任意 JSON 约束策略；应用可施加额外限制。grant 仍携带显式 subject、有效期和约束，依赖方 MUST 执行。MUST NOT 将未知 scope 或约束视为允许执行动作。

## 6. 淘汰与历史归属

淘汰 Controller 保留原字段，增加 `retired_at`。仅泄漏时增加 `invalid_from`，无需独立的淘汰原因或状态枚举。普通淘汰不撤销已接受的 grant；泄漏则触发下述规则。

例如，淘汰后此记录从 `controllers` 移入 `retired_controllers`。淘汰前，同一记录去掉 `retired_at` 后允许第 7 节的 grant：

```json
{
  "id": "did:agent:AwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwM",
  "source": "https://dmsg.net",
  "valid_from": 1788652800000,
  "delegation": {
    "scopes": [
      "inbox.screen",
      "message.draft"
    ],
    "audiences": [
      "https://dmsg.net"
    ]
  },
  "retired_at": 1788746400000
}
```

历史记录 MUST 保留到依赖它的签名不再需要验证，服务商 SHOULD 无限期保留。删除表示归属证据不可用，不是默认有效。淘汰密钥 MUST NOT 授权新提交的事件，即使其 `created_at` 早于淘汰时间。已接受 grant 在满足 audience、scope、约束、有效期和当前状态时可以继续使用。服务商 MAY 按已说明的策略连带暂停或撤销。

发生泄漏时，宿主 MUST 淘汰密钥，并将 `invalid_from` 设为已知最早泄漏时间，未知则取 `valid_from`。淘汰记录 MAY 后续添加 `invalid_from` 或将其提前，但 MUST NOT 推迟或清除。即使持有旧快照，验证器也 MUST 查询最新记录。除非可信证据将准确 grant 哈希绑定到 `invalid_from` 之前的接受事实，否则服务 MUST 暂停或撤销受影响的当前凭证。经授权且未泄漏的 controller 可以签发替换 grant 恢复权限。由于禁止重复登记密钥，不需要跨登记版本传播泄漏状态。

### 6.1 历史究竟证明什么

在规范 URL 读取 `retired_controllers`，验证器可以确认主体当前声明“某密钥曾在 `[valid_from, retired_at)` 内拥有某些权限”，无需保留每个整份文档快照。但它**不能**证明事件实际何时签名：`created_at` 由签名者控制，盗取密钥后可以伪造旧时间。

服务 MUST 为每个已接受事件持久保存接受记录：

```json
{
  "event_id": "<accepted envelope hash>",
  "accepted_at": 1788656400000
}
```

`accepted_at` 取服务首次接受事件时的时钟。MUST NOT 从 `event.created_at` 复制、被重试改写或由凭证 `updated_at` 推断。服务 MUST 将 `created_at` 与 `accepted_at` 都与当前记录的权限区间核对，保存当时准确核验的 controller 记录，并串行处理本地 controller 变更与事件接受，防止已淘汰记录通过陈旧本地检查。远程主体仍受第 3 节缓存上限约束；后续发现淘汰或泄漏时 MUST 重新评估受影响凭证。

依赖方选择并明示以下证据策略之一：

- **在线信任服务**：通过规范主体文档及其权威 delegation 服务的接受记录，验证签名、完整权限上限、历史区间和当前状态。HTTPS 获取的接受记录是服务声明；此策略信任该服务的时钟和接受检查。
- **独立历史证据**：额外要求验证器独立信任的时间戳、日志、回执机构或验证器自己的持久观察，将准确事件哈希绑定到权限区间内且早于任何 `invalid_from` 的观察时刻。淘汰密钥自己的签名和时间戳 MUST NOT 满足此要求。如果判定依赖服务的接受事实，而非事件仅仅已存在，证据也必须证明事件已被接受。

高保证依赖方 SHOULD 使用独立历史证据，尤其在泄漏后。证据缺失或不可信表示历史授权**不可验证**，不表示 Ed25519 签名在数学上无效。若签发方密钥具有独立建立的信任链，签名主体快照可以证明签发方对历史归属的声明，但它不会为另一份无关 grant 提供时间证明。裸 JSON 快照、包内自带的不可信密钥、签名者自报的事件时间都不够。本版本不标准化离线回执或快照签名格式，也不能离线证明当前撤销状态。

## 7. Delegation 事件与接受规则

事件使用 Agent Identity 1.0 事件信封，`event.protocol = "agent-delegation/1.0"`。任何调用方 MAY 提交信封；授权完全取决于签名与 Controller 记录，而非提交者的登录态。服务 MUST 校验信封结构、哈希、签名与 actor。若通过密码学验证的完整信封与已持久化的历史记录完全相同，则作为幂等查询处理，优先于实时时间戳、Nonce 及当前 Controller 权限检查执行，且 MUST NOT 产生新的接受记录或引发状态变更。其他提交 MUST 符合 Agent Identity 的实时时间窗口与 Nonce 规则。

### 7.1 Grant

`delegation.grant` payload 形状如下。此例的 `event.created_at` 与首次 `accepted_at` 均为 `1788656400000`，`event.actor` 为第 6 节 dmsg 记录的 `id`：

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "principal": {
    "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
    "type": "person"
  },
  "subject": "did:agent:AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI",
  "audiences": [
    "https://dmsg.net"
  ],
  "scopes": [
    "message.draft"
  ],
  "constraints": {
    "requires_human_approval": true
  },
  "not_before": 1788656400000,
  "expires_at": 1788742800000
}
```

`id`、`principal.id`、`subject`、`audiences`、`scopes` 全部 REQUIRED。Delegation `id` MUST NOT 为 `.` 或 `..`，因为这两个值是 URL 点段，无法作为稳定的不透明路径段。`audiences` MUST 为非空 HTTPS origin 列表，`scopes` MUST 为由非空权限字符串构成的非空列表，且 MUST NOT 包含 `"*"`。可选 `relationship` 为应用标签；可选 `principal.type` 与 `principal.name` 为展示提示。可选 `constraints` 为对象。`not_before` 与 `expires_at` 为可选时间戳。若存在，`expires_at` MUST 同时大于 `event.created_at` 与 `not_before`（若有）。服务 MUST NOT 接受在接受时刻已到期的 grant。

接受流程 MUST：

1. 解析指定的规范主体并核验版本，拒绝在签名主体 ID 中使用别名。
2. 查找唯一满足 `record.id == event.actor` 的**当前**记录，要求事件创建时刻与接受时刻均不早于 `valid_from`。
3. 要求记录中包含 `delegation`，并按第 5 节规则对整个 payload 校验 scope 与 audience 上限。
4. 执行替换时，要求已有凭证的主体与协议一致，并执行第 5 节所有权校验。凭证 ID MUST NOT 允许跨版本或跨主体覆盖。
5. 原子化持久存储事件信封、接受记录、已核验的 controller 记录与物化状态。首个 grant 的签名者 Agent ID 赋值给 `owner_controller`。

接受的替换提供所有新 grant 字段，不作合并。同一 ID 下，后续经过授权的 grant MAY 重新激活已撤销凭证。服务 MUST 按接受顺序串行处理替换和撤销，不按签名者自选的时间排序。完全相同 envelope 的重试 MUST 返回原接受结果，不重新应用旧事件或回滚状态；当前状态单独读取。

### 7.2 Revoke

`delegation.revoke` payload REQUIRED 包含 `id`、规范 `principal_id`，以及可选 `reason`；`id` 适用与 grant 相同的点段限制。被引用凭证 MUST 存在于该主体与版本下。执行与 grant 相同的信封、解析、当前记录、actor、时间、持久化与排序检查，然后要求不受限的 `delegation: "*"`，或受限 controller 匹配 `owner_controller`。

撤销将收回当前凭证权限。subject 可以拒绝使用凭证或请求暂停；没有 controller 权限时不能签发主体撤销。服务施加的暂停与主体撤销不同。每个实现 MUST 支持撤销与泄漏重新评估。

## 8. 凭证与验证

凭证是已接受事件与服务商状态的未签名物化视图，字段如下：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | 是 | Delegation ID。 |
| `principal` | 是 | 最新 grant 的主体描述。 |
| `subject` | 是 | 最新 grant 的 Agent ID。 |
| `relationship` | 否 | 最新 grant 的应用标签。 |
| `scopes` | 是 | 最新 grant 的非空 scope 列表。 |
| `constraints` | 否 | 最新 grant 的约束对象。 |
| `not_before`、`expires_at` | 否 | grant 有效期时间戳。 |
| `status` | 是 | 下文定义的当前状态。 |
| `updated_at` | 是 | 最近事件或服务商状态变更时间。 |
| `protocol` | 是 | `agent-delegation/1.0`。 |
| `controller` | 是 | 最新接受的 grant/revoke 事件的 actor。 |
| `owner_controller` | 是 | 第一次 grant 签名者的 Agent ID，不可变。 |
| `audiences` | 是 | 最新 grant 的非空依赖方应用 origin 列表。 |
| `grant_event_id` | 是 | 最新接受的 grant 哈希，撤销后仍保留。 |
| `event_id` | 是 | 最新接受的 grant/revoke 哈希。 |
| `accepted_at` | 是 | 该最新事件的接受时刻。 |

撤销后，grant 派生字段仍来自最新 grant；controller 字段与 `event_id` 指向撤销者。`status` 为 `active`、`suspended`、`expired` 或 `revoked`；后续到期计算 MUST NOT 掩盖撤销状态。`updated_at` 包含服务商状态变更，绝不是历史时间证据。即使标记 `active`，`not_before` 之前也不可使用；到达或超过 `expires_at` 后不可使用。

凭证与接受记录是未签名的服务视图。外部出示的凭证 MUST 通过权威主体解析获得的 `delegation_query_url` 查询，不能使用出示者提供的 URL。返回的主体、subject、ID、版本和事件哈希 MUST 与依赖的声明匹配。直接从服务读取时，可以向同一服务检查状态，但这本身不能证明主体授权该服务。

验证器 MUST 检查最新 grant 的签名、controller 记录、grant 权限上限、权限区间、第 6.1 节证据以及当前状态。重建所有权、替换或撤销时，MUST 验证所需的已接受事件历史和每个事件的 controller 权限，不能只验最新签名。历史验证 MUST NOT 将实时提交的时间/nonce 窗口用于归档事件；它验证密码学有效性和记录的接受时条件。新提交仍受实时窗口限制。

执行动作前，依赖方应用 MUST 将自己配置的 origin 与签名 grant 的 `audiences` 比对，执行 scope 和约束，检查有效期和当前状态，并认证 subject 请求。audience 不能从 `source`、HTTP `Origin` 或不可信调用方参数推断。凭证不是 bearer 会话令牌，也不能证明 subject 已同意代表该主体。

## 9. HTTP API 与 Profile 集成

服务 MUST 提供公开凭证、状态、事件历史、提交与存在性查询端点。RECOMMENDED 使用以下路径；HTTP 路径版本独立于协议标识符：

```text
GET  /.well-known/agent-delegation
GET  /v1/delegations/{delegation_id}
GET  /v1/delegations/{delegation_id}/status
GET  /v1/delegations/{delegation_id}/events
POST /v1/delegations
POST /v1/delegations/query
```

### 9.1 认证与可见性

读取、提交和公开存在性查询 MUST 无需账号认证。服务 MAY 使用限速、配额、API key 或工作量证明防滥用，并 SHOULD 保留无需认证的验证路径。传输凭证 MUST NOT 替代 controller 签名和权限检查。提交者不必是 subject、controller 或账号所有者。

知道凭证 ID 的任何人都可以读取它。服务 MAY 隐去私有数据，但 MUST NOT 将不完整证据呈现为可独立验证。缺少必要证据时验证 MUST 按拒绝处理。ID 可能被猜中；宿主 SHOULD 避免在凭证中放入私有信息。

### 9.2 服务发现

`GET /.well-known/agent-delegation` SHOULD 返回：

```json
{
  "protocol": "agent-delegation/1.0",
  "service": "https://api.al.ink",
  "endpoints": {
    "delegations": "https://api.al.ink/v1/delegations",
    "query": "https://api.al.ink/v1/delegations/query"
  },
  "features": [
    "grants",
    "revocations",
    "event-history"
  ]
}
```

端点 URL MUST 使用 HTTPS。客户端 MAY 在主体权威 `delegation_query_url` 的 origin 读取发现文档，定位其他端点。出示者提供的发现 URL 不建立权威性。

### 9.3 凭证与事件读取

这些路径中的 `delegation_id` MUST 序列化为单个 UTF-8 百分号编码路径段；编码只改变 HTTP 路径，不改变协议中存储或签名的 ID。`GET /v1/delegations/{delegation_id}` 返回第 8 节凭证。`/events` 返回对象，REQUIRED 包含 `result` 和 `acceptances` 数组。`result` 按服务接受顺序包含已接受 envelope；`acceptances` 按相同顺序为每个 envelope 包含对应第 6.1 节记录，并匹配其哈希。不同 controller 的 nonce 独立，MUST NOT 用 nonce 排序替代接受顺序。

### 9.4 状态

`/status` 响应 REQUIRED 包含 `id`、`protocol`、`status`、`checked_at`、`event_id`、`grant_event_id`、`accepted_at`，以及可选 `expires_at`。含义见第 8 节；`checked_at` 为服务进行本次状态检查的时间。服务商状态变化不改变事件接受时间。敏感动作前，依赖方 MUST 检查当前状态；陈旧或不可获取的状态 MUST NOT 静默转换为 `active`。

### 9.5 提交

`POST /v1/delegations` 接受签名 grant 或 revoke envelope，执行第 7 节全部检查，返回物化凭证或状态。精确重试已接受 envelope 时，执行第 7 节幂等查询规则。

### 9.6 查询

`POST /v1/delegations/query` 接受对象，可含 `subject`、`principal_id`、`id`、`status`、`limit`。Agent ID 和主体 URL MUST 有效；`principal_id` MUST 为规范 ID。`limit` MUST 为正整数，默认 20，SHOULD 以 100 为上限。

公开存在性查询 MUST 同时包含 `subject` 和 `principal_id`。缺少其中任一项即为私有枚举：MUST 至少包含一项，且 MUST 取得被枚举一侧的认证授权。subject 可以授权列出自己的 delegation；当前 controller 需要第 5 节规定的 delegation 权限与所有权检查。独立认证的所有者管理 MAY 授权主体侧查询。仅被列为 controller 不足以枚举。服务 MAY 完全拒绝枚举。

响应为 `{"result": [...]}`。每个可见条目 MUST 包含 `id`、`principal`、`subject`、`scopes`、`status`，MAY 返回完整凭证。无匹配返回空数组；不存在的主体 SHOULD 返回相同空响应。脱敏摘要是发现结果，不是充分的验证证据。

### 9.7 Agent Profile 提示

Agent Profile MAY 发布 `delegations` 数组，其提示含 `principal`、可选 `id`、可选 `relationship`、可选 `scopes`。提示不证明权限。客户端 MUST 解析规范主体，以 profile 的 Agent ID 为 `subject`、并在提示含 ID 时将其作为 delegation ID，查询其权威 `delegation_query_url`，并按第 8 节为自己的 audience 验证凭证。提示不能选择可信状态服务。

## 10. 安全与隐私

主体 URL 仍是信任根，历史声明也不例外。保留归档不能阻止恶意或被攻陷的主体宿主改写自己的历史。离线或更强的历史声明需要独立锚定的证据。HTTPS 解析及重定向 SHOULD 执行本地网络访问策略以防 SSRF。

为每个应用使用独立密钥可以缩小泄漏影响。来源是公开元数据，可能暴露个人使用了哪些应用；宿主 SHOULD 在登记前说明，并避免在标签中放入设备序列号、账号标识符或私有端点。默认托管密钥 SHOULD 清晰标识；完整通配权限 MUST 是所有者的显式选择，绝不能成为第三方登记的默认值。

泄漏响应有三个独立效果：停止接受新签名，重新评估已经接受的授权，保留历史密钥和权限证据。数学签名有效性、历史授权和当前凭证可用性 MUST NOT 合并成单一验证结果。权限变更影响未来签发；撤回已委托权限需要撤销或暂停相关凭证。

公开存在性查询不意味着公开枚举。来源、profile 提示和 controller 登记都不能证明法律身份或 subject 同意。未知 scope 不授予能力。凭证和主体文档 MUST NOT 包含私钥或 bearer 秘密。

## 11. 一致性要求

除 Agent Identity envelope 检查外，实现 MUST 执行以下结果：

| 案例 | 要求结果 |
| --- | --- |
| 未配置 `delegation` 的密钥提交 grant、revoke 或枚举查询 | 拒绝；应用签名单独验证。 |
| dmsg 授予未列出的 scope 或面向 `https://tokenlist.ing` 的 audience | 拒绝。 |
| 受限 controller 替换、撤销或枚举其他密钥的凭证 | 拒绝，包括已撤销凭证。 |
| 不受限 controller 撤销同一主体的另一密钥凭证 | 常规签名、时间和当前绑定检查通过后允许。 |
| 淘汰密钥提交伪造旧时间的事件 | 拒绝新接受；精确重试已接受事件不能重复应用状态。 |
| 普通淘汰密钥的历史 grant 未到期且未撤销 | 历史证据与动作检查通过时可继续使用。 |
| 泄漏密钥自报旧时间，无可信截止前接受证据 | 暂停/撤销受影响凭证；历史授权不可验证。 |
| 密钥在当前和淘汰列表重复，或淘汰后重新登记 | 拒绝文档。 |
| 在同一密钥下修改已发布权限 | 禁止，需使用新密钥；旧事件不能继承新权限。 |
| 淘汰 Controller 缺少 `retired_at`，或当前记录包含该字段 | 拒绝文档。 |
| 另一 controller 撤销 grant | 保留 grant 字段和 `grant_event_id`；最新事件字段记录撤销者。 |
| 别名副本注入当前或淘汰 controller | 丢弃副本权限，解析规范 URL。 |
| 旧字符串数组、未知 delegation 策略、空对象或受限列表包含通配符 | 拒绝，绝不推断全权。 |
| 离线包自带不可信的快照签发方密钥 | 不足以独立证明历史归属。 |

## 附录 A. 草案实现说明与方案取舍

本附录保留草案一致性要求，并说明方案取舍。

本修订直接更新尚未发布的 1.0 草案。早期字符串数组主体文档，以及缺少 audiences 的事件，均不符合本修订。实现者 MUST 同步更新发布端、消费端与验证规则，MUST NOT 为旧形状数据静默推断全权。测试数据 SHOULD 使用 Agent ID、来源、delegation 策略与生命周期时间重新生成；MUST NOT 改写签名字节后仍将其作为原签名出示。

本仓库 Rust、TypeScript、Python 源码 SDK 已包含修订后的类型与校验辅助函数。服务实现仍负责认证历史证据、实时防重放、原子接受与当前状态；SDK 物化本身不等于验证。TokenList.ing 等外部应用需要匹配 `record.id`、来源与生命周期，同时保持应用签名机制独立。已有签名归属快照保留其原证据和信任语义；新归档不能制造缺失的历史证明。

给字符串数组加标签只能解决来源问题。单一 `scopes` 字段仍缺少 audience、跨 controller 替换、撤销、枚举和仅签名绑定。只归档密钥会丢失历史权限上限。整份文档快照或强制公开透明日志可以提供更多证据，但普通在线历史查询不要求它们；保留不可变 controller 记录是最小存储模型。任何未签名归档都不能独立阻止回填旧时间或提供独立离线证明。
