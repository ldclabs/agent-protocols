# Agent Delegation Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-delegation/1.0`
**状态**：草案
**日期**：2026-09-29
**依赖**：Agent Identity Protocol 1.0
**可选使用**：Agent Profile Protocol 1.0

## 1. 概述

Agent Delegation 定义智能体何时可以代表以规范 HTTPS URL 标识的主体（principal）行动。主体文档将密钥绑定到主体，签名的 grant 事件向 subject 智能体授予具体权限。HTTPS URL 仍是身份信任根。

协议将**密钥来源**、**签发 delegation 的权限**与**历史归属**分开。登记一把密钥不会自动赋予它签发 delegation 或管理其他 controller 的权限。服务商的默认签名器、第三方应用签名器和本地签名器使用相同的记录格式，只取得文档显式发布的权限。

主体文档与签名事件均携带 `agent-delegation/1.0`；实现 MUST 校验必填的记录与事件字段，而不能假定仅凭协议标识符即可保证兼容。Controller 记录 MUST NOT 被压平为不受限的密钥列表。JSON Schema 定义见 [`1.0.schema.json`](1.0.schema.json)，测试向量见 [`1.0.vectors.json`](1.0.vectors.json)。

## 2. 规范用语

关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHOULD`、`SHOULD NOT` 和 `MAY` 按 BCP 14（RFC 2119、RFC 8174）解释。

所有时间戳均为以毫秒为单位的非负 JSON 安全整数。Agent ID MUST 是有效的 Agent Identity 1.0 标识符，源遵循 [Agent Identity 第 4.4 节](../agent-identity/1.0.zh-CN.md#44-源origin)。必填字符串 MUST 非空。协议定义的允许列表、scopes、audiences、aliases 与 `supersedes` 列表 MUST 不含重复项；应用自定义的 JSON 数组保持其应用语义。未知的展示或扩展字段 SHOULD 被保留。不受支持的权限字段或取值 MUST 按失败关闭处理：验证方 MUST NOT 忽略自己无法执行的限制。

## 3. 主体身份与解析

主体代表个人、组织、团队、项目、场所、活动或其他非智能体对象。其 `id` MUST 是规范 HTTPS URL。RECOMMENDED 使用稳定、不透明的标识符；可改名的句柄应放在 `aliases` 中。

以 `Accept: application/json` 请求 `GET {principal.id}` MUST 返回公开、无需认证的 JSON 主体文档。解析步骤如下：

1. 最多跟随五次重定向，每一跳（包括跨源跳转）都使用 HTTPS。
2. 若返回的 `document.id` 与最终响应 URL 完全相等，该文档具有权威性。
3. 否则丢弃该副本中**全部**承载权限的字段，包括 `protocol`、`controllers`、`retired_controllers` 与 `delegation_query_url`，并按第 1–2 步解析一次 `document.id`。若该次读取仍不具权威性，则解析失败。
4. 在使用 controller 权限前，要求 `document.protocol` 等于 `agent-delegation/1.0`。

URL 身份比较为精确的字符串比较。发布方 SHOULD 规范化协议与主机大小写、省略默认端口，并避免在主体 ID 中使用查询串与片段。事件 MUST 使用规范 ID 而非别名：当验证方解析取自事件的主体 ID 时，权威文档的 `id` MUST 等于该 ID。在将别名展示为主体名称之前，客户端 MUST 确认权威文档的 `aliases` 列出了它。别名映射的缓存时长 MUST NOT 超过文档本身。

接受新事件时，服务 MUST 使用不早于 300 秒前获取的文档，并 SHOULD 对敏感操作立即重新验证。宿主在 controller 变更时 MUST 使自身的权限缓存失效。该时长是陈旧权限窗口的上限，而非分布式的即时撤销。

## 4. 主体文档

```json
{
  "protocol": "agent-delegation/1.0",
  "id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "type": "person",
  "name": "Yan",
  "aliases": [
    "https://al.ink/yan"
  ],
  "controllers": [
    {
      "id": "did:agent:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
      "source": "https://al.ink",
      "name": "alink default signer",
      "valid_from": 1788652800000,
      "delegation": "*"
    },
    {
      "id": "did:agent:AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE",
      "source": "https://tokenlist.ing",
      "name": "TokenList.ing user canister",
      "valid_from": 1788652800000
    }
  ],
  "retired_controllers": [],
  "delegation_query_url": "https://api.al.ink/v1/delegations/query",
  "updated_at": 1788652800000
}
```

示例中的密钥仅用于说明传输格式，并非生产密钥。

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `protocol` | string | 是 | 固定为 `agent-delegation/1.0`。 |
| `id` | string | 是 | 规范主体 URL。 |
| `controllers` | Controller[] | 是 | 当前记录。MAY 为空，包括恢复期间。 |
| `retired_controllers` | Controller[] | 否 | 历史记录；缺失表示为空，而不是授权未知密钥。 |
| `delegation_query_url` | string | 条件必填 | delegation 凭证的权威 HTTPS 查询端点。只要任一当前或已淘汰 Controller 携带 `delegation` 即为 REQUIRED，因为验证（第 8 节）没有其他可信路径。 |
| `updated_at` | integer | 是 | 文档最近变更时间，不是密码学时间戳。每个 Controller 的 `valid_from` 与 `retired_at` MUST 不晚于它。 |
| `type`、`name`、`description`、`avatar_url` | string | 否 | 展示元数据。`type` SHOULD 为 `person`、`organization`、`team`、`project`、`venue`、`event` 或 `other`；`avatar_url` MUST 使用 HTTPS。 |
| `aliases` | string[] | 否 | HTTPS 别名，受第 3 节约束。 |
| `links` | object[] | 否 | Agent Profile 链接项，包含字符串 `name`、`url` 与 `rel`。 |
| `extra` | object | 否 | 应用元数据。任何展示或扩展字段都不授予权限。 |

### 4.1 统一的 Controller 类型

`controllers` 与 `retired_controllers` 包含的是**同一种 Controller 类型**。已淘汰的 controller 是原记录加上 `retired_at`，而不是另一种实体，也不是权限不同的副本。

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `id` | string | 是 | 密钥的 Agent ID，等于签名事件的 `actor`，无需另设登记 ID。 |
| `source` | string | 是 | 签名服务的 HTTPS 源，用户本地签名器则为 `local`。 |
| `valid_from` | integer | 是 | 绑定起始时间（含）；MUST NOT 晚于文档的 `updated_at`。 |
| `name` | string | 否 | 人类可读标签，例如 `alink default signer` 或 `Personal key vault`。 |
| `delegation` | `"*"` 或对象 | 否 | 第 5 节定义的 delegation 权限。缺失表示没有 delegation 权限。 |
| `supersedes` | string[] | 否 | 本主体更早 Controller 记录的 Agent ID，本密钥可管理其签发的凭证（第 5.1 节）。 |
| `retired_at` | integer | 仅淘汰记录 | 绑定结束时间（不含）；MUST 不早于 `valid_from`。两者相等表示在接受任何事件前即已淘汰的绑定。 |
| `invalid_from` | integer | 仅泄露记录 | 签名开始不可信的最早时间；MUST 满足 `valid_from <= invalid_from <= retired_at`。 |

`source` 为源，例如 `https://al.ink`、`https://dmsg.net` 或 `https://tokenlist.ing`；本地签名器使用 `local`。`source` 与 `name` 描述的是主体声明的来源，既不证明托管关系、用户同意或服务背书，也 MUST NOT 授予权限。应用自行定义签名格式与同意检查；仅凭密钥绑定不能授权应用操作。不得仅因某个 source URL 列于此处就去请求它。

托管签名器（由 `source` 代表主体持有的密钥）即 [Agent Identity 第 3.1 节](../agent-identity/1.0.zh-CN.md#31-密钥算法) 意义上该密钥的操作者。登记 MUST 要求主体所有者授权，并使用第 4.3 节的挑战证明对密钥的持有。登记、淘汰、恢复与权限变更需要独立的所有者管理授权；即使 `delegation: "*"` 也不包含这些管理权。

### 4.2 不可变绑定

在同一主体内，一把密钥在两个列表中合计 MUST 至多出现一次，且淘汰后 MUST NOT 再次登记。其 `id`、`source`、`valid_from`、`delegation` 与 `supersedes` 在发布后 MUST NOT 修改，只有展示用的 `name` 可以编辑。变更权限需要新密钥与新绑定；这一设计刻意避免了登记版本与权限历史匹配。协议不要求定期轮换。

淘汰 MUST 以原子方式把记录从 `controllers` 移到 `retired_controllers` 并加上 `retired_at`。当前记录 MUST NOT 包含淘汰或泄露时间戳；已淘汰记录 MUST 包含 `retired_at`。验证方 MUST 拒绝重复密钥或格式错误的记录，而不是合并其权限。

### 4.3 Controller 注册挑战

注册通过两步证明对密钥的持有：先申请挑战，再提交密钥对挑战的签名。Provider 自行定义 HTTPS 管理路径与所有者认证机制；它们独立于第 9 节的公开 delegation 端点。挑战请求 MUST 验证对指定主体的管理授权；仅有 controller 签名或请求 JWT 并不提供该授权。Provider 自己生成的密钥（例如其默认托管签名器）无需挑战。

挑战请求是包含以下字段的 JSON 对象：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `principal_id` | 是 | 由此 provider 管理的规范主体 URL。 |
| `id` | 是 | 待注册密钥的 Agent ID；成为 `Controller.id`。 |
| `source` | 是 | 第 4.1 节定义的 HTTPS 签名器源或 `local`。 |
| `name` | 否 | Controller 的展示名称。 |
| `delegation` | 否 | 所有者按第 5 节批准的权限；省略表示没有 delegation 权限。 |
| `supersedes` | 否 | 第 5.1 节定义的更早 controller ID。 |

Provider MUST 按第 4 节与第 5 节校验这些字段，并校验所有者对它们的授权。它 MAY 在此时就拒绝已存在于任一 controller 列表中的密钥；注册时无论如何都会拒绝。响应包含 REQUIRED 的 `challenge` 与 `expires_at`：

```json
{
  "challenge": "agent-delegation/1.0:controller-registration:AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8",
  "expires_at": 1788653100000
}
```

`challenge` 为 `agent-delegation/1.0:controller-registration:` 加上 43 个 base64url 字符，共 88 个 ASCII 字符；客户端将后缀视为不透明值。后缀 MUST 除 provider 外无人能够预测，且 provider MUST 能在之后判断它是为哪些字段与 `expires_at` 签发的：例如随机生成 32 字节并与这些值一同保存，或者不做存储，以 provider 密钥对挑战请求与 `expires_at` 的 JCS 计算 HMAC-SHA-256。不带密钥的哈希不满足要求。`expires_at` 为 Unix 毫秒时间戳，不超过签发后 300,000 毫秒。

密钥对挑战的精确 UTF-8 字节签名——不解码、不求摘要、不加引号，也不带尾部换行：

```text
signature = base64url(Ed25519.sign(private_key, UTF8(challenge)))
```

签名器 MUST 拒绝签署不匹配 `^agent-delegation/1\.0:controller-registration:[A-Za-z0-9_-]{43}$` 的字符串。固定前缀使注册证明与 Agent Identity 事件摘要及请求 JWT 相互区分。该证明只表明密钥持有者签署了这个挑战：它不证明所有者同意或所声明的 `source`，也不向签名器表明密钥将被注册到哪个主体。签名器 SHOULD 只签署从所有者本人与 provider 的会话中取得的挑战。

注册请求原样回传挑战请求的字段与 `expires_at`，并添加 REQUIRED 的 `challenge` 与 `signature`。Provider MUST：

1. 要求其当前时间严格早于 `expires_at`。
2. 通过查找或重新计算 MAC，确认 `challenge` 正是为回传的字段与 `expires_at` 签发的，按 JCS（[Agent Identity 第 4.1 节](../agent-identity/1.0.zh-CN.md#41-json-规范化)）比较。任何差异都拒绝。
3. 使用 `id` 中的公钥，按 [Agent Identity 第 3.1 节](../agent-identity/1.0.zh-CN.md#31-密钥算法) 验证对 `UTF8(challenge)` 的 `signature`。
4. 根据当前主体文档重新检查第 4.2 节与第 5.1 节，以回传的字段及 provider 分配的 `valid_from` 发布 Controller，更新文档的 `updated_at`，并返回已发布的 Controller。

由于挑战已承载所有者的批准，注册请求 MAY 由所有者或签名器提交；provider 也 MAY 要求该请求具备所有者授权。Provider MAY 在挑战使用后将其遗忘。重放挑战不会注册出任何新内容：其字段是固定的，而同一密钥只能注册一次（第 4.2 节）。

缺少所有者授权使用 `permission_denied`；字段无效、挑战过期或无法识别、或回传的值不一致使用 `invalid_request`；持有证明验证失败使用 `invalid_signature`。挑战与证明属于管理数据，不加入公开 Controller 或 delegation 事件历史。

## 5. Delegation 权限

恰有三种配置：

| `delegation` | 签发权限 | 替换 / 撤销 / 枚举 |
| --- | --- | --- |
| 缺失 | 无；仅公开密钥绑定 | 无 |
| `"*"` | 任意显式的 scopes 与 audiences | 本主体的任意凭证 |
| `{ "scopes": [...], "audiences": [...] }` | 仅列出的 scopes 与依赖方 | 仅本密钥谱系（第 5.1 节）内拥有的凭证 |

受限对象 MUST 恰好包含 `scopes` 与 `audiences`，且两者均为非空数组。Scope 精确匹配，不支持前缀、glob、层级或通配。每个 audience 指明一个依赖方：依赖方应用用源表示，没有源的依赖方智能体（如命令行或桌面智能体）用 Agent ID 表示。Audience 同样按精确字符串相等匹配。未知策略字段、空数组、`null`、`{}` 以及任一数组中的通配项 MUST 被拒绝。不受限的字符串 `"*"` 是所有者的显式选择，绝不能作为登记默认值。

例如，dmsg 的 controller 使用：

```json
{
  "scopes": ["inbox.screen", "message.draft"],
  "audiences": ["https://dmsg.net"]
}
```

每个授予的 scope 与 audience 都 MUST 在允许范围内。该密钥不能签发 TokenList.ing 的 delegation、授予其他 scope，或覆盖其他密钥的凭证。第 4 节中的 TokenList.ing 示例完全省略了 `delegation`，因为它只发布应用签名密钥。本地密钥可以使用三种配置中的任意一种；本地托管并不意味着拥有全部权限。

每个凭证都有不可变的 `owner_controller`：签发其首个被接受 grant 的 Agent ID。替换、撤销与重新激活 MUST NOT 转移所有权。受限 controller 在替换、撤销或枚举时 MUST 通过其谱系拥有该凭证；每次替换还 MUST 满足替换方密钥自身的 delegation 上限。不受限 controller 可以管理其他密钥或已淘汰密钥签发的凭证，但仅限同一主体。

每项操作都要求密钥为当前密钥，且操作时间 MUST 不早于 `valid_from`。枚举需要证明该密钥的身份。仅签名密钥不能枚举。本协议不增加 controller 级的 subject、TTL 或任意 JSON 约束策略；应用可以施加额外限制。grant 仍携带显式的 subject、有效期与约束，依赖方 MUST 执行这些约束。未知的 scope 或约束 MUST NOT 被视为行动许可。受限 controller 签发的 grant SHOULD 携带 `expires_at`。

### 5.1 继承

由于每把密钥的权限不可变（第 4.2 节），扩大受限 controller 的权限意味着登记新密钥。若没有继承机制，新密钥无法替换或撤销旧密钥签发的内容，没有不受限 controller 的主体也就根本无法收回这些 grant。因此 Controller 记录 MAY 在 `supersedes` 中列出更早的密钥：

- 每一项 MUST 是同一主体另一条 Controller 记录（当前或已淘汰）的 `id`，且其 `valid_from` 早于本记录的 `valid_from`。这一顺序约束使环路不可能出现。
- controller 的**谱系**（lineage）是其自身 `id`，加上其所继承的每条记录的谱系（传递闭包）。
- 当凭证的 `owner_controller` 位于受限 controller 的谱系中时，该 controller 拥有该凭证。`owner_controller` 本身永不改变。
- 继承转移的是凭证管理权，而非权限：继承者签发的替换 MUST 满足继承者自身的上限，被继承的密钥在淘汰前只保留其自身权限。

验证方 MUST 拒绝 `supersedes` 项未知、指向记录自身，或指向 `valid_from` 不更早之记录的主体文档。在淘汰一把没有继承者的受限密钥之前，该密钥 SHOULD 撤销其拥有的凭证：此后只有不受限 controller 或服务商暂停才能收回这些凭证。

## 6. 淘汰与历史归属

已淘汰的 Controller 保留原有字段并加上 `retired_at`。只有在泄露时才添加 `invalid_from`；无需额外的淘汰原因或状态枚举。普通淘汰不会撤销此前已接受的 grant，泄露则触发下述规则。

例如，下列记录在淘汰后从 `controllers` 移到 `retired_controllers`。淘汰之前，不含 `retired_at` 的同一条记录授权了第 7 节中的 grant：

```json
{
  "id": "did:agent:AwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwM",
  "source": "https://dmsg.net",
  "valid_from": 1788652800000,
  "delegation": {
    "scopes": [
      "inbox.screen",
      "message.draft"
    ],
    "audiences": [
      "https://dmsg.net"
    ]
  },
  "retired_at": 1788746400000
}
```

只要仍可能需要验证依赖其的签名，历史记录 MUST 保持可用；服务商 SHOULD 无限期保留。移除意味着绑定证据不可用，而非默认有效。已淘汰密钥 MUST NOT 授权新提交的事件，即使其 `created_at` 早于淘汰时间。此前已接受的 grant 在其 audience、scopes、约束、有效期与当前状态允许的范围内可以继续使用。服务商 MAY 按公开的策略一并暂停或撤销它们。

发生泄露时，宿主 MUST 淘汰该密钥，并将 `invalid_from` 设为已知最早的泄露时间；未知时设为 `valid_from`。已淘汰记录之后 MAY 新增 `invalid_from` 或将其提前；MUST NOT 推后或清除。即使持有较旧快照，验证方也 MUST 参考最新记录。除非可信证据将确切的 grant Hash 绑定到 `invalid_from` 之前的接受，否则服务 MUST 暂停或撤销受影响的当前凭证。获授权且未泄露的 controller（不受限 controller，或在其上限内的受限继承者）可以签发替换 grant 以恢复权限。由于密钥不能重新登记，泄露处理无需在登记版本之间传播。

### 6.1 历史究竟证明什么

在规范 URL 上读取 `retired_controllers`，验证方可以确认主体当前的声明：某把密钥在 `[valid_from, retired_at)` 期间拥有某些权限。这避免了保存每一份完整文档快照。它**不能**证明事件何时签名：签名方控制 `created_at`，被盗密钥可以倒签时间。

服务 MUST 为每个已接受事件持久化一条 [Agent Identity 已接受记录](../agent-identity/1.0.zh-CN.md#83-已接受记录)：

```json
{
  "envelope": { "hash": "<accepted envelope hash>", "event": {}, "signature": "..." },
  "accepted_at": 1788656400000
}
```

`accepted_at` 是首次接受时服务的时钟。它 MUST NOT 从 `event.created_at` 复制，也不得被重试改写。服务 MUST 同时对照当前记录的权限区间检查 `created_at` 与 `accepted_at`，保存所检查的确切 controller 记录，并将本地 controller 变更与接受操作串行化，使已淘汰记录无法通过陈旧的本地检查。对于远程主体，第 3 节的缓存时限仍然适用；之后发现的淘汰或泄露 MUST 触发对受影响凭证的重新评估。

本版本只定义一种证据策略，即**在线信任服务**：依赖方使用规范主体文档以及该主体权威 delegation 服务提供的已接受记录验证凭证（第 8 节）。经 HTTPS 获取的已接受记录是服务的断言，因此该策略信任该服务的时钟与接受检查。

不信任服务已接受记录的依赖方，需要自己独立信任的证据，例如它自身对确切事件 Hash 在权限区间内、且在任何 `invalid_from` 之前的持久观测。已淘汰密钥的签名与签名方自选的 `created_at` MUST NOT 被接受为这类证据。缺少这类证据时，历史授权**无法验证**，这不同于 Ed25519 签名在数学上无效。本版本不标准化独立证据的格式，也无法离线证明当前撤销状态；附录 A 讨论了可选方案。

## 7. Delegation 事件与接受规则

事件使用 Agent Identity 1.0 信封，`event.protocol = "agent-delegation/1.0"`。Delegation 事件仅携带 Agent Identity 的六个事件字段；依据封闭 Event 对象规则，服务 MUST 拒绝任何其他顶层事件字段。任何人 MAY 提交信封；权限来自其签名与 controller 记录，而非提交者的登录身份。服务 MUST 校验信封结构、Hash、签名与 actor。对已接受信封的原样重提交是幂等查询（[Agent Identity 第 6.3 节](../agent-identity/1.0.zh-CN.md#63-原样重提交)），以该信封被接受后当时的凭证作答；它在实时时间戳、Nonce 与当前 controller 授权检查之前执行，且 MUST NOT 产生新的接受或状态变更。其他所有提交 MUST 满足 Agent Identity 的实时时间窗口与 Nonce 规则。

Delegation 事件不携带服务绑定字段。这种可移植性是 [Agent Identity 第 10 节](../agent-identity/1.0.zh-CN.md#10-安全与隐私) 意义上的有意设计：权限来自主体，依赖方只信任通过主体权威 `delegation_query_url` 读取的凭证（第 8 节）。被其他服务接受的 grant 不产生任何权限。将 `delegation_query_url` 迁移到其他服务（包括迁移已接受记录）属于主体宿主的操作，不在本版本范围内；新服务没有的凭证即为不存在。

delegation `id` MUST 匹配 `^[A-Za-z0-9._~-]{1,128}$`，且 MUST NOT 为 `.` 或 `..`。该非保留字符集在 URL 中无需百分号编码，也没有 Unicode 形近字符，因此展示给人看或作为名称分配的 ID 无法被易混淆字符仿冒。

### 7.1 Grant

`delegation.grant` 载荷结构如下。在此示例中，`event.created_at` 与首次 `accepted_at` 均为 `1788656400000`，`event.actor` 为第 6 节 dmsg 记录的 `id`：

```json
{
  "id": "del_01J8ZM7A3G2T9B4Q6X8R0N1P2Q",
  "principal_id": "https://api.al.ink/d9c6a99cne5g00a6scn0",
  "subject": "did:agent:AgICAgICAgICAgICAgICAgICAgICAgICAgICAgICAgI",
  "audiences": [
    "https://dmsg.net"
  ],
  "scopes": [
    "message.draft"
  ],
  "constraints": {
    "requires_human_approval": true
  },
  "not_before": 1788656400000,
  "expires_at": 1788742800000
}
```

`id`、`principal_id`、`subject`、`audiences` 与 `scopes` 为 REQUIRED。`principal_id` MUST 为规范主体 ID；主体的展示元数据来自其权威文档，而非 grant。`audiences` MUST 为非空的 audience 列表（第 5 节）；`scopes` MUST 为非空权限字符串组成的非空列表，且 MUST NOT 包含 `"*"`。可选的 `relationship` 是应用标签。可选的 `constraints` 为对象。`not_before` 与 `expires_at` 为可选时间戳。若存在 `expires_at`，其 MUST 同时大于 `event.created_at` 与 `not_before`（若存在）。服务 MUST NOT 接受在接受时刻已经过期的 grant。

接受时 MUST：

1. 解析 `principal_id`（第 3 节），并要求权威文档的 `id` 与之完全相等；别名一律拒绝。
2. 找到恰好一条 `record.id == event.actor` 的**当前**记录；要求事件创建时间与接受时间都不早于 `valid_from`。
3. 要求存在 `delegation`，并对完整载荷执行第 5 节的 scope 与 audience 上限检查。
4. 替换时，要求现有凭证的 `principal_id`、`subject` 与协议标识符与新 grant 相同，并执行第 5 节的所有权规则。凭证 ID MUST NOT 被复用于其他主体或其他 subject；委托给另一个智能体需要使用新 ID。
5. 以原子方式持久化已接受记录、所检查的 controller 记录与物化状态。首个 grant 确定 `owner_controller`。

被接受的替换提供全部新的 grant 字段，而不是合并。之后获得授权的 grant MAY 以同一 ID 重新激活已撤销的凭证。服务 MUST 按接受顺序而非签名方自选的时间戳，串行化替换与撤销。对确切信封的重试 MUST 返回原始接受结果，而不重新应用旧事件或回滚状态；当前状态需单独获取。

### 7.2 Revoke

`delegation.revoke` 载荷包含 REQUIRED 的 `id` 与规范 `principal_id`，以及可选的 `reason`；`id` 遵循上述 ID 语法。所引用的凭证 MUST 存在于该主体之下。执行与 grant 相同的信封、解析、当前记录、actor、时间、持久化与排序检查，再要求签名方为不受限的 `delegation: "*"`，或是通过谱系拥有该凭证的受限 controller（第 5.1 节）。

撤销收回当前凭证的权限。subject 可以拒绝使用某个凭证或请求暂停，但没有 controller 权限就不能以主体名义撤销。服务施加的暂停不同于主体撤销。所有实现 MUST 支持撤销与泄露后的重新评估。

## 8. 凭证与验证

凭证是已接受事件与服务商状态的未签名物化结果，字段如下：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | 是 | Delegation ID。 |
| `protocol` | 是 | `agent-delegation/1.0`。 |
| `principal_id` | 是 | 来自 grant 的规范主体 ID。 |
| `subject` | 是 | 来自 grant 的 Agent ID；对同一凭证 ID 不可变。 |
| `relationship` | 否 | 最新 grant 中的应用标签。 |
| `scopes` | 是 | 最新 grant 中的非空 scope 列表。 |
| `audiences` | 是 | 最新 grant 中的非空依赖方 audience。 |
| `constraints` | 否 | 最新 grant 中的约束对象。 |
| `not_before`、`expires_at` | 否 | grant 的有效期时间戳。 |
| `status` | 是 | 下文定义的当前状态。 |
| `controller` | 是 | 最新被接受 grant/revoke 事件的 actor。 |
| `owner_controller` | 是 | 首个 grant 签名方的 Agent ID，不可变。 |
| `grant_event_id` | 是 | 最新被接受 grant 的 Hash，撤销后依然保留。 |
| `event_id` | 是 | 最新被接受 grant/revoke 事件的 Hash。 |
| `accepted_at` | 是 | 该最新事件的接受时间。 |
| `checked_at` | 是 | 生成该视图时的服务时钟。 |

撤销后，grant 派生字段保持为最新 grant 的取值；controller 字段与 `event_id` 标识撤销方。`status` 为 `active`、`suspended`、`expired` 或 `revoked`；撤销状态 MUST NOT 被之后的过期计算掩盖。`checked_at` 让依赖方判断状态的新鲜程度；服务商状态变更不改变 `accepted_at`。在 `not_before` 之前，无论是否标记为 `active`，grant 都不可用；在 `expires_at` 及之后也不可用。

凭证与已接受记录是未签名的服务视图。出示的凭证 MUST 通过权威主体解析得到的 `delegation_query_url` 核验，绝不能通过出示方提供的 URL 核验。返回的 `principal_id`、subject、ID 与事件 Hash MUST 与所依赖的声明相符。直接读取服务可以使用同一服务查询状态，但这本身并不能证明该服务拥有主体权限。

依赖方根据凭证最新 grant 的已接受记录（即信封 Hash 等于 `grant_event_id` 的记录）验证凭证。它 MUST 检查：

1. grant 信封的 Hash 与签名。
2. 其 `actor` 与主体的某条 Controller 记录（当前或已淘汰）匹配，且该记录的权限区间同时包含 grant 的 `created_at` 与记录的 `accepted_at`，并早于任何 `invalid_from`。
3. grant 不超出该记录的 delegation 上限。
4. grant 字段与凭证一致；当 `event_id` 等于 `grant_event_id` 时，记录的 `accepted_at` 与 `actor` 还须分别等于凭证的 `accepted_at` 与 `controller`。`event_id` 不同于 `grant_event_id` 的凭证最后一次变更是撤销，因此其 `status` MUST 为 `revoked`。
5. 凭证的当前状态。

依赖方不重放所有权或 `supersedes` 谱系。这些规则决定哪个 controller 可以替换或撤销凭证，权威服务已在接受时执行（第 7 节）。审计方则验证完整的已接受历史：每个事件的签名与 controller 权限，以及每次替换与撤销所依据的谱系。历史验证 MUST NOT 对归档事件应用实时时间戳/Nonce 提交窗口；它验证的是其密码学与记录的接受时条件。新提交仍受实时窗口约束。

在执行操作前，依赖方 MUST 将自身的 audience（配置的源，或依赖方智能体自身的 Agent ID）与签名 grant 的 `audiences` 进行匹配，执行 scopes 与约束，检查有效期与当前状态，并认证 subject 的请求。Audience 绝不能从 `source`、HTTP `Origin` 或不可信的调用参数推断。陈旧或不可用的状态 MUST NOT 被悄然视为 `active`，依赖方在敏感操作前 MUST 检查当前状态。凭证不是 Bearer 会话令牌，也不能证明 subject 已接受代理关系。

## 9. HTTP API 与 Profile 集成

服务 MUST 提供公开的凭证、事件历史、提交与存在性查询端点。错误、列表、已接受记录与服务发现遵循 [Agent Identity 第 8 节](../agent-identity/1.0.zh-CN.md#8-http-约定)。RECOMMENDED 使用以下路径；HTTP 路径版本与协议标识符相互独立：

```text
GET  /.well-known/agent-delegation
GET  /v1/delegations/{delegation_id}
GET  /v1/delegations/{delegation_id}/events
POST /v1/delegations
POST /v1/delegations/query
```

### 9.1 认证与可见性

读取、提交与公开的存在性查询 MUST 无需账户认证即可使用。这不适用于签发 controller 注册挑战（第 4.3 节）等所有者管理操作。服务 MAY 施加速率限制、配额、API Key 或工作量证明以防滥用，并 SHOULD 保留一条无需认证的验证路径。传输层凭据 MUST NOT 代替 controller 签名与权限检查。提交者不必是 subject、controller 或账户持有者。

任何知道凭证 ID 的人都可以读取该凭证。服务 MAY 隐去私密数据，但 MUST NOT 将不完整的证据呈现为可独立验证。缺少必要证据 MUST 导致验证失败关闭。ID 可能被猜到；宿主 SHOULD 避免在凭证中放入私密信息。

### 9.2 服务发现

`GET /.well-known/agent-delegation` SHOULD 返回 Agent Identity 发现文档，其端点名为 `delegations`（凭证与事件读取以及提交的基础 URL）与 `query`。本版本定义一个特性字符串 `enumeration`：服务应答经授权的枚举查询（第 9.5 节）。

```json
{
  "protocol": "agent-delegation/1.0",
  "service": "https://api.al.ink",
  "endpoints": {
    "delegations": "https://api.al.ink/v1/delegations",
    "query": "https://api.al.ink/v1/delegations/query"
  },
  "features": [
    "enumeration"
  ]
}
```

端点 URL MUST 使用 HTTPS。客户端 MAY 在主体权威 `delegation_query_url` 的源上读取发现文档，以定位其他端点。主体文档的 `delegation_query_url` 是查询的权威地址：该源上的发现文档 SHOULD 将同一 URL 列为 `query`，两者不同时客户端 MUST 使用主体给出的 URL。出示方提供的发现 URL 不构成权威。

### 9.3 凭证与事件读取

Delegation ID 取自 URL 非保留字符集，因此 `delegation_id` 在这些路径中原样出现。`GET /v1/delegations/{delegation_id}` 返回第 8 节的凭证，并带有最新的 `checked_at`。`GET /v1/delegations/{delegation_id}/events` 返回 Agent Identity 列表，其 `result` 按服务接受顺序包含已接受记录 `{ envelope, accepted_at }`。不同 controller 的 Nonce 相互独立；Nonce 顺序 MUST NOT 取代接受顺序。

### 9.4 提交

`POST /v1/delegations` 接受签名的 grant 或 revoke 信封，执行第 7 节的全部检查，并返回由此得到的第 8 节凭证。对已接受确切信封的重试遵循第 7 节的幂等查询规则。

### 9.5 查询

`POST /v1/delegations/query` 接受一个对象，包含可选的 `subject`、`principal_id`、`id`、`status`、`limit` 与 `cursor`。Agent ID 与主体 URL MUST 有效；`principal_id` MUST 为规范 ID。`limit` MUST 为正整数，默认 20，SHOULD 上限为 100。

公开的存在性查询 MUST 同时包含 `subject` 与 `principal_id`。省略任一方即为枚举查询。它 MUST 至少包含其中之一，并 MUST 携带以服务源为 `aud` 的 [Agent Identity 请求 JWT](../agent-identity/1.0.zh-CN.md#7-请求认证)，由被枚举的一方授权：

- subject 枚举自身的 delegation：查询包含 `subject`，且 JWT 的 `sub` 与之相等。
- controller 枚举某主体的凭证：查询包含 `principal_id`，且 JWT 的 `sub` 是该主体具有 `delegation` 权限的当前 Controller。结果遵循第 5 节的所有权规则：`"*"` 可见该主体的全部凭证，其他 controller 只能看到其谱系内拥有的凭证。没有 `delegation` 的 Controller 不能枚举。
- 主体所有者管理 MAY 通过服务商自定义的机制授权主体一方的枚举。

服务以 `permission_denied` 拒绝未经授权的枚举查询。服务 MAY 完全拒绝枚举；支持枚举的服务会声明 `enumeration` 特性。

响应为 Agent Identity 列表，其 `result` 包含第 8 节凭证，并适用第 9.1 节的隐去规则。无匹配时返回空 `result`；对于不存在的主体，服务 SHOULD 给出相同的空响应。

### 9.6 Agent Profile 提示

Agent Profile MAY 发布 `delegations` 数组，其中的提示项包含 `principal`、可选的 `id`、可选的 `relationship` 与可选的 `scopes`。它不证明任何权限。客户端 MUST 解析规范主体，以该 Profile 的 Agent ID 作为 `subject`（若提示含 delegation ID 则一并带上）查询其权威 `delegation_query_url`，并按第 8 节为自身 audience 验证凭证。提示不能指定受信任的状态服务。

### 9.7 错误

除 Agent Identity 错误码外，delegation 服务还使用：

| 错误码 | 含义 |
| --- | --- |
| `principal_unresolvable` | 无法以权威方式解析主体文档。 |
| `principal_not_canonical` | 签名的 `principal_id` 或查询的 `principal_id` 是别名或其他非规范形式。 |
| `controller_not_current` | `actor` 不是主体的当前 Controller，或时间超出其区间。 |
| `delegation_not_permitted` | 该 Controller 没有 `delegation` 权限。 |
| `delegation_ceiling_exceeded` | 授予的 scope 或 audience 超出 Controller 上限。 |
| `not_owner_controller` | 受限 Controller 未通过其谱系拥有该凭证。 |
| `credential_not_found` | 所引用的凭证不在该主体之下。 |
| `credential_identity_mismatch` | 替换改变了凭证的主体、subject 或协议。 |
| `grant_expired` | `expires_at` 不晚于事件时间、`not_before` 或接受时间。 |

## 10. 安全与隐私

主体 URL 仍是信任根，历史声明亦然。归档留存无法防止恶意或被攻破的主体宿主改写自身历史。离线或更强的历史声明需要独立锚定的证据。HTTPS 解析与重定向 SHOULD 执行本地网络访问策略以防止 SSRF。

每个应用使用独立密钥可以降低泄露影响。来源是公开元数据，可能暴露一个人使用了哪些应用；宿主 SHOULD 在登记前说明这一点，并避免在标签中使用设备序列号、账户标识或私有端点。默认托管密钥 SHOULD 有明显标识，完整通配权限 MUST 是所有者的显式选择，绝不能作为第三方登记的默认值。

泄露响应有三个相互独立的效果：停止接受新签名、重新评估已接受的 grant、保留历史密钥与权限证据。签名的数学有效性、历史授权与当前凭证可用性 MUST NOT 被合并为单一验证结果。权限变更只影响之后的签发；要收回已委托的权限，应撤销或暂停相关凭证。`supersedes` 让继承者管理其前任的凭证，因此登记继承者应与登记权限受到同等的所有者审查。

凭证的 subject 永不改变，因此以 delegation ID 为键的 Profile 提示或依赖方缓存无法被重定向到另一个智能体。公开的存在性查询并不意味着公开枚举。Source、Profile 提示与 controller 登记既不证明法律身份，也不证明 subject 的同意。未知的 scope 不授予任何能力。凭证与主体文档 MUST NOT 包含私钥或 Bearer 机密。

## 11. 一致性要求

除 Agent Identity 信封检查外，实现 MUST 执行以下结果。[`1.0.vectors.json`](1.0.vectors.json) 中的测试向量是规范性的，覆盖注册挑战格式与签名、主体文档、delegation ID、audience 以及 grant 与 revoke 的接受：

| 场景 | 要求的结果 |
| --- | --- |
| 注册在过期前回传挑战的字段与 `expires_at`，且密钥签名有效 | 通过绑定检查后发布获批的 Controller。 |
| 注册证明签署的是解码后的后缀、摘要或带尾部换行的挑战，或来自小阶密钥 | 拒绝。只按 Agent Identity 第 3.1 节签署完整挑战的精确 UTF-8 字节。 |
| 挑战请求缺少所有者授权，或注册回传了不同的主体、密钥、source、name、delegation 策略、`supersedes` 或 `expires_at`，或在 `expires_at` 当时或之后到达 | 拒绝。 |
| 已成功的注册证明被重放 | 拒绝：该密钥已注册或已淘汰。 |
| 没有 `delegation` 的密钥提交 grant、revoke 或枚举查询 | 拒绝。应用签名另行验证。 |
| dmsg 授予未列出的 scope，或 audience 为 `https://tokenlist.ing` | 拒绝。 |
| grant 在 controller 上限内指定 Agent ID 作为 audience | 接受；只有该依赖方智能体与之匹配。 |
| 枚举查询缺少被枚举一方的请求 JWT | 以 `permission_denied` 拒绝。 |
| 受限 controller 替换、撤销或枚举其谱系之外的凭证 | 拒绝，包括已撤销的凭证。 |
| 受限继承者撤销其所继承密钥签发的凭证 | 通过常规签名、时间与当前绑定检查后允许。 |
| 不受限 controller 撤销同一主体下其他密钥的凭证 | 通过常规签名、时间与当前绑定检查后允许。 |
| 替换 grant 在已有 ID 下更改 `subject` 或 `principal_id` | 拒绝。 |
| grant 使用别名而非规范主体 ID | 拒绝。 |
| 已淘汰密钥提交倒签事件 | 拒绝新的接受；对已接受信封的原样重试不能重新应用状态。 |
| 普通淘汰密钥此前签发的 grant 未过期且未撤销 | 若历史证据与全部操作检查通过，可继续使用。 |
| 泄露密钥声称旧时间戳，但没有截止时间之前的可信接受证据 | 暂停/撤销受影响凭证；历史授权无法验证。 |
| 同一密钥同时出现在当前与淘汰列表，或淘汰后再次登记 | 拒绝该文档。 |
| `supersedes` 指向未知密钥、记录自身或并不更早的记录 | 拒绝该文档。 |
| 某 Controller 携带 `delegation`，但文档没有 `delegation_query_url` | 拒绝该文档。 |
| 某 Controller 的 `valid_from` 或 `retired_at` 晚于文档的 `updated_at` | 拒绝该文档。 |
| 在同一密钥下修改已发布的权限 | 禁止；使用新密钥。旧事件不能继承新权限。 |
| 已淘汰 Controller 缺少 `retired_at`，或当前 Controller 含有该字段 | 拒绝该文档。 |
| 由不同 controller 撤销 grant | 保留 grant 字段与 `grant_event_id`；最新事件字段标识撤销方。 |
| 凭证的 `event_id` 不同于 `grant_event_id`，但状态不是 `revoked` | 验证失败。 |
| 别名副本注入当前或已淘汰 controller | 丢弃副本权限，解析规范 URL。 |
| `controllers` 中出现裸字符串、未知 delegation 策略、空对象或受限列表中的通配项 | 拒绝；绝不推断为不受限权限。 |
| Delegation ID 不符合 ID 语法 | 拒绝。 |
| 唯一的历史证据是自带不可信快照密钥的离线包 | 历史授权无法验证。 |

## 附录 A. 设计说明与备选方案

本附录为资料性内容。

仓库中的 Rust、TypeScript 与 Python 源码 SDK 提供了本文档的类型与校验辅助函数。服务实现仍负责经认证的历史证据、实时防重放检查、原子接受与当前状态；仅靠 SDK 物化并不构成验证。TokenList.ing 等外部应用必须匹配 `record.id`、source 与生命周期，同时保持其应用签名方案独立。

在字符串数组上加标签只能解决来源问题。单一的 `scopes` 字段仍然无法覆盖 audiences、跨 controller 替换、撤销、枚举与仅签名绑定。只归档密钥会丢失历史权限上限。完整文档快照或强制的公开透明日志可以提供额外证据，但普通的在线历史查询并不需要；保留的不可变 controller 记录是最小的存储模型。任何未签名的归档本身都无法防止倒签，也无法提供独立的离线证明。

独立历史证据留待未来版本。需要抵御服务被攻破或不诚实的依赖方，需要把确切事件 Hash 绑定到权限区间内、且在任何 `invalid_from` 之前的观测的证据：时间戳机构、透明日志、回执，或其自身的持久观测。已签名的主体快照在签发方密钥有独立信任链时可以证明签发方对历史绑定的声明，但不能为无关的 grant 提供时间戳。裸 JSON 快照、捆绑的不可信密钥以及签名方自选的事件时间都不足以作为证据。

依赖方只验证最新 grant（第 8 节），因为所有权与谱系管辖的是管理而不是使用。权威服务已在接受时执行这些规则；不信任该服务的依赖方，也无法靠重放同一服务提供的记录重新获得信任。

继承被建模为不可变的 `supersedes` 列表，而非可变的所有权。转移 `owner_controller` 会让所有权取决于对事件历史的解读；登记时确定的谱系则让每个所有权判断都成为当前主体文档与凭证的纯函数。
