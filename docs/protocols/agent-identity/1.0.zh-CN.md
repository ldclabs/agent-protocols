# Agent Identity Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-identity/1.0`
**状态**：草案
**日期**：2026-09-24
**主要算法**：Ed25519
**核心对象**：Agent ID

## 1. 概述

Agent Identity Protocol 为自治智能体定义了一种自验证（Self-certifying）身份格式。智能体身份直接由 Ed25519 公钥派生，私钥由智能体或其操作者独立保管，服务端通过验证签名确认智能体操作的合法性。

本协议保持最小核心设计，仅定义：

- 标准 Agent ID 格式。
- 通用编码规则。
- 供上层 Agent Protocols 复用的签名事件信封（Signed Event Envelope）。
- 签名、事件 Hash、时间戳、单调递增 Nonce 以及原样重提交（Exact Resubmission）的验证规则。
- 用于非签名事件类 HTTP 操作的请求认证方案。
- 上层协议共享的 HTTP 约定：错误、列表、已接受记录与发现文档。

Agent Identity 不涉及用户账户、OAuth 流程、计费账户或人类登录体系。这些机制可以存在于具体产品中，但不属于智能体的协议身份。

## 2. 规范用语

本文中的关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY`、`OPTIONAL` 仅在全大写出现时，按 BCP 14（RFC 2119、RFC 8174）的定义进行解释。

## 3. Agent ID

### 3.1 密钥算法

Agent Identity 1.0 采用 Ed25519。

- 公钥长度恰为 32 字节。
- 签名在 base64url 编码前恰为 64 字节：32 字节的点 `R` 编码，后接 32 字节小端序标量 `S`。
- 私钥 MUST 由智能体或其选定的操作者生成并保管。代其所有者持有密钥的托管方（例如 [Agent Delegation 第 4.1 节](../agent-delegation/1.0.zh-CN.md#41-统一的-controller-类型) 中主体的托管签名器）即为该密钥的操作者。
- 服务 MUST NOT 以上传私钥、助记词或等效机密作为使用服务的条件。

签名验证 MUST 遵循 RFC 8032，并附加以下规则，使所有合规验证方接受完全相同的签名集合：

1. 公钥 `A` 与点 `R` MUST 为规范编码：清除最高位后，255 位小端序 y 坐标 MUST 小于 `p = 2^255 - 19`。
2. `A` 与 `R` MUST NOT 为小阶点。当且仅当清除最高位后的 y 坐标为 `0`、`1`、`p - 1` 或附录 B 所列两个 8 阶取值之一时，该编码表示小阶点。
3. 标量 `S` MUST 完全约减：`S < L`，其中 `L = 2^252 + 27742317777372353535851937790883648493`。
4. 验证方 MUST 校验无余因子等式 `[S]B = R + [k]A`，MUST NOT 使用带余因子的验证；批量验证 MUST NOT 接受单签名验证会拒绝的签名。

RFC 8032 同时允许带余因子与无余因子两种等式，常见库在小阶点与非规范输入上的行为也各不相同。规则 1–4 消除了这一自由度：一个实现验证通过的归档，在所有其他实现中得到相同结果。请求 JWT 签名（第 7 节）适用相同规则。

### 3.2 标识符格式

标准 Agent ID 格式为：

```text
did:agent:<base64url-public-key>
```

其中 `<base64url-public-key>` 为原始 32 字节 Ed25519 公钥的无填充 base64url 编码。

示例：

```text
did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw
```

实现 MAY 在用户界面、日志或 URL 中展示截短的公钥，但协议对象中标识操作主体（actor）的字段 MUST 使用完整的 `did:agent:` 格式。

本草案采用 DID 风格的语法。未来可能追加正式的 DID Method 注册；除非通用 DID 解析器明确支持该方法，否则实现 MUST NOT 假定其能够解析 `did:agent:`。

### 3.3 解码

解码 Agent ID 时，实现 MUST：

1. 校验前缀严格为 `did:agent:`。
2. 将后缀按无填充 base64url 解码。
3. 校验解码后的字节长度为 32。
4. 校验后缀为规范编码：将 32 字节重新编码 MUST 精确还原输入后缀。
5. 将解码字节视为原始 Ed25519 公钥。

格式错误的 Agent ID MUST 被拒绝。规范性检查之所以重要，是因为宽松的 base64url 解码器会接受填充字符或非零尾部比特，使同一公钥对应多个不同的 `did:agent:` 字符串，进而破坏以字符串为键的比较、缓存与 Nonce 状态。点级检查（第 3.1 节）在使用密钥验证签名时执行；格式正确但其密钥无法通过点级检查的 Agent ID 永远无法产生有效签名。

### 3.4 非 Agent 主体的密钥

`did:agent:` 标识符命名的是 Ed25519 密钥持有者，并不一定是自治智能体。上层协议 MAY 将该密钥绑定到个人、组织或其他主体。[Agent Delegation](../agent-delegation/1.0.zh-CN.md) 在主体的规范 HTTPS URL 上以 Controller 记录发布此类绑定。匹配的 `Controller.id` 建立密钥绑定；只有其显式的 `delegation` 策略才授权委托操作，未携带 `delegation` 字段的密钥不具备此类权限。签名验证只证明由哪个密钥签名；主体绑定、权限检查与历史有效性属于上层协议。

此类绑定不改变信封验证。接收方照常执行本协议定义的 `actor`、事件 Hash、签名、时间戳与 Nonce 规则，再应用上层协议的绑定检查。

## 4. 编码规则

### 4.1 JSON 规范化

事件 JSON 对象在计算 Hash 前 MUST 使用 JSON 规范化方案（JCS，RFC 8785）进行规范化。

实现 MUST NOT 依赖普通 JSON 序列化器的键顺序。参与 Hash 的字节为 `JCS(event)`；参与签名的字节为 `event_hash = SHA3-256(JCS(event))` 的原始 32 字节。

JCS 仅对 I-JSON（RFC 7493）有定义。接收方 MUST 严格解析签名 JSON，并 MUST 拒绝 JSON 文本存在以下情形的信封：

- 任一层级的任一对象包含重复成员名；
- 包含非有效 Unicode 的字符串，例如未配对的代理项转义；
- 包含超出 `-(2^53 - 1)` 至 `2^53 - 1` 范围的整数。

重复成员名是经典的签名混淆手段：一个解析器基于最后一个值验证 Hash，而另一个组件却按第一个值执行。JCS 允许非整数数值，但其规范形式是跨实现 Hash 不一致最常见的来源；协议 SHOULD NOT 定义取值为非整数的签名字段，Agent Protocols 的注册 Schema 仅使用整数。

### 4.2 取值编码

| 取值                   | 编码                                       |
| ---------------------- | ------------------------------------------ |
| Agent ID 中的公钥      | 无填充 base64url                           |
| 签名                   | 无填充 base64url                           |
| SHA3-256 Hash          | 无填充 base64url                           |
| Nonce                  | 正的安全 JSON 整数，按 Agent ID 单调递增   |

Agent Protocols 中所有 base64url 取值均使用无填充的 URL 安全字母表，接收方 MUST 拒绝非规范编码：仅当解码后重新编码能精确还原输入字符串时，取值才有效。该规则同样适用于 Agent ID 后缀、Hash 与签名。

### 4.3 时间

签名事件对象中的所有协议时间戳均为 Unix 毫秒，编码为不大于 `2^53 - 1` 的非负 JSON 整数。

示例：

```json
{
  "created_at": 1779753600000
}
```

第 7 节请求认证所用的 JWT Claims 按 RFC 7519 要求使用以秒为单位的 JWT NumericDate。

## 5. 签名事件信封

上层 Agent Protocols 的写操作使用以下信封结构。

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
    "created_at": 1779753600000,
    "nonce": 1779753600000,
    "payload": {}
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

### 5.1 Event 字段

| 字段         | 必填 | 说明                                                                     |
| ------------ | ---- | ------------------------------------------------------------------------ |
| `protocol`   | 是   | 协议标识符，例如 `agent-profile/1.0` 或 `agent-discourse/1.0`。          |
| `type`       | 是   | 以点分隔命名的事件类型。                                                 |
| `actor`      | 是   | 签名智能体的 Agent ID。                                                  |
| `created_at` | 是   | Unix 毫秒。                                                              |
| `nonce`      | 是   | 由签名方维护、用于防重放的正整数（第 6.2 节）。                          |
| `payload`    | 是   | 事件专属的 JSON 载荷。                                                   |

Event 对象是封闭的：除上述六个字段外，仅可包含 `protocol` 所指协议显式定义的顶层字段，例如 Agent Discourse 的 `room_id`。接收方 MUST 拒绝携带任何其他顶层字段的事件。所有这类字段都位于 `JCS(event)` 之内，因而受签名覆盖；若验证方忽略未知字段，可能会悄然丢弃签名方有意设置的限制。`payload` 内的未知字段遵循上层协议的规则。

### 5.2 Event Hash

`hash` 由未签名的规范事件对象派生：

```text
event_bytes = JCS(event)
event_hash = SHA3-256(event_bytes)
hash = base64url(event_hash)
```

接收方 MUST 重新计算 `hash`，并在提供的 `hash` 不匹配时拒绝信封。上层协议将该值称为信封的**事件 ID**。

### 5.3 签名

签名覆盖 `event_hash` 的原始 32 字节，而非 `JCS(event)` 本身。此处 `event_hash` 指原始 SHA3-256 摘要，而非 base64url 形式的 `hash` 字符串：

```text
signature = base64url(Ed25519.sign(private_key, event_hash))
```

接收方 MUST 将 `actor` 解码为 Ed25519 公钥，重新计算 `event_hash`，并按第 3.1 节在该 32 字节 `event_hash` 上验证签名。

签名方 SHOULD 自行由完整事件计算 `event_hash`。在看不到摘要所承诺事件的情况下，对其他组件提供的摘要签名（盲签）是 NOT RECOMMENDED：由于 `actor` 与全部事件内容都在摘要之内，盲签方可能被诱导为归属其密钥的任意事件签名。签名服务等密钥托管方 SHOULD 在签名前自行规范化事件，并展示或校验其内容。

## 6. 验证规则

### 6.1 实时写入

处理实时写操作时，接收方 MUST：

1. 严格解析信封（第 4.1 节）并校验其结构，包括封闭的 Event 对象（第 5.1 节）。
2. 使用 JCS 规范化 `event`。
3. 重新计算 `hash`。
4. 将 `actor` 解码为 Ed25519 公钥。
5. 在重新计算的 32 字节 `event_hash` 上验证 `signature`（第 3.1 节）。
6. 处理原样重提交（第 6.3 节）；若该信封已被接受，至此结束。
7. 检查 `created_at` 是否处于允许的实时写入时间窗口内。
8. 检查 `nonce` 是否大于同一 `actor` 当前有效的已接受最大 Nonce。
9. 执行上层协议校验。

所有检查 MUST 全部通过方可接受。接收方 MAY 先执行信封结构、时间窗口等低开销检查，再进行签名验证，以降低拒绝垃圾流量的成本，前提是对已接受信封的原样重提交仍按第 6.3 节的要求作答。

实时写入时间窗口以接收方验证时的时钟为准：当 `|now - created_at|` 不超过窗口大小时，信封位于窗口之内；该规则同时覆盖过期信封与客户端时钟略微偏快的情况。实时写入的默认时间窗口 RECOMMENDED 为 300 秒（300000 毫秒）。历史导入、归档校验与显式跨宿主同步 MAY 采用不同的时间策略，但此类例外 MUST NOT 削弱实时写入的防重放保护。

### 6.2 Nonce

`nonce` 字段 MUST 为 `1` 至 `9007199254740991`（`2^53 - 1`）安全互操作范围内的正 JSON 整数。接收方 MUST 拒绝超出该范围的取值。

一个 Agent ID 签名的所有事件（跨所有协议、所有服务）共用同一个 Nonce 序列。客户端 SDK SHOULD 由时钟派生每个 Nonce：

```text
nonce = max(last_nonce + 1, created_at)
```

其中 `created_at` 为待签名事件的 Unix 毫秒时间戳。时钟派生的 Nonce 无需协调即可在重启、从备份恢复以及多设备共享密钥时保持单调。从 `1` 开始、每次加 `1` 的计数器同样有效，但它依赖持久化的本地状态。

服务 MUST 为每个 `actor` 缓存已接受的最大 Nonce 及其过期时间。缓存有效期 MUST 不短于实时写入时间窗口，并从该 actor 最近一次被接受信封的接受时刻起算；否则 `created_at` 仍在窗口内的信封可能在缓存过期后被重放。若该 actor 的缓存记录仍然有效且 `event.nonce` 不大于缓存的最大值，服务 MUST 拒绝该信封。上层协议 MAY 额外要求基于持久历史的比较；Agent Profile 对 `profile.update` 即有此要求。

因 Nonce 检查拒绝实时写入时，服务 MUST 在 `Max-Seen-Nonce` 响应头（十进制整数）中返回当前生效的最大 Nonce；接受实时写入时 SHOULD 同样返回。该响应头是丢失本地状态的客户端重新同步的途径。由于 Nonce 序列由智能体使用的所有服务共享，单个故障或恶意服务原本可以将其耗尽。因此，客户端 SDK MUST NOT 仅凭一个响应头就把下一个 Nonce 推进到超出 `max(next_nonce, now_ms)` 加 `2^32` 的位置；对于更大的取值，SHOULD 作为错误上报而非应用。在该界限内，当响应头取值大于或等于本地下一个 Nonce 时，客户端 SHOULD 将下一个 Nonce 推进为 `header_value + 1`。

### 6.3 原样重提交

响应丢失时客户端会重试。同一信封的重试所携带的 Nonce 服务已经见过，届时它也可能已经超出时间窗口；若无专门规则，客户端将永远无法得知写入是否成功。

当接收方在其持久的已接受历史中找到 `hash` 相同的信封，且提交的信封通过第 6.1 节第 1–5 步时，MUST 将本次提交视为幂等查询：返回携带原始接受结果的成功响应（例如同一条服务端记录，或协议为该信封定义的文档），不产生新的接受、不应用任何状态变更，并跳过时间戳与 Nonce 检查。已将该信封从历史中清理的接收方 MAY 按其他过期写入的方式作答。

## 7. 请求认证

需要证明对某个 Agent ID 的控制权、但本身不是签名事件的 HTTP 操作（鉴权读取、实时订阅、瞬态状态写入以及枚举查询）SHOULD 使用以 Ed25519 签名的短时效 JWT Bearer Token。RECOMMENDED 的 HTTP 授权方式为：

```text
Authorization: Bearer <compact-jwt>
```

JWT MUST 使用 JWS 紧凑序列化，并采用以下受保护头部：

```json
{
  "alg": "EdDSA",
  "typ": "JWT",
  "kid": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw"
}
```

JWT 载荷 MUST 包含以下 Claims：

| Claim | 必填 | 说明                                       |
| ----- | ---- | ------------------------------------------ |
| `iss` | 是   | 签名智能体的 Agent ID。                    |
| `sub` | 是   | 与 `iss` 相同的 Agent ID。                 |
| `aud` | 是   | 接收服务的源（Origin）。                   |
| `iat` | 是   | 签发时间，以秒为单位的 JWT NumericDate。   |
| `exp` | 是   | 过期时间，以秒为单位的 JWT NumericDate。   |

`aud` MUST 为接收服务的源，即协议、主机与非默认端口，不含路径，例如 `https://api.example.com`。同一源上的所有 Agent Protocols 端点共享这一受众值，不使用按端点区分的受众值。该统一规则使客户端仅凭请求 URL 即可推导出预期的 `aud`。

载荷示例：

```json
{
  "iss": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "sub": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "aud": "https://api.example.com",
  "iat": 1779753600,
  "exp": 1779753900
}
```

接收方 MUST：

1. 要求 `alg` 为 `EdDSA`。
2. 校验 `kid`、`iss` 与 `sub` 标识同一个 Agent ID。
3. 将该 Agent ID 解码为 Ed25519 公钥。
4. 按第 3.1 节验证 JWT 签名。
5. 校验 `aud` 等于接收服务自身的源。
6. 校验 `iat` 与 `exp` 有效且处于允许的时间窗口内。

接收方 MUST 拒绝 `exp` 小于或等于 `iat` 的请求 JWT。对于实时请求，服务 SHOULD 将 `exp - iat` 限制在 300 秒以内，并在对照本地时钟校验 `iat` 时 SHOULD 容忍少量时钟偏差（例如 60 秒）。请求 JWT 向目标服务证明对 Agent ID 的控制权，但除非服务显式签发会话，否则它本身不创建会话。

## 8. HTTP 约定

提供 HTTP API 的上层协议使用本节约定，使一个客户端库即可访问所有 Agent Protocols 服务。协议 MAY 增加字段与错误码，但 MUST NOT 重新定义下列内容。

### 8.1 错误

错误响应使用非 2xx 的 HTTP 状态码及以下 JSON 主体：

```json
{
  "error": {
    "code": "nonce_not_greater",
    "message": "Nonce must be greater than 1779753600000.",
    "data": {}
  }
}
```

`code` 为稳定的机器可读字符串；`message` 面向人类阅读，MAY 变化；`data` 为 OPTIONAL 对象，承载与错误码相关的细节。以下错误码由所有 Agent Protocols 服务共享：

| 错误码                    | 含义                                                                  |
| ------------------------- | --------------------------------------------------------------------- |
| `invalid_request`         | HTTP 请求、查询或主体格式错误，或违反端点的输入规则。                 |
| `invalid_event`           | 事件结构无效，包括未知事件字段或非 I-JSON 输入。                      |
| `invalid_event_hash`      | `hash` 与事件内容不匹配。                                             |
| `invalid_signature`       | 签名验证失败。                                                        |
| `invalid_actor`           | `actor` 对该操作而言不是有效的 Agent ID。                             |
| `timestamp_out_of_window` | `created_at` 超出实时写入窗口。                                       |
| `nonce_not_greater`       | `nonce` 不大于当前生效的最大值；响应携带 `Max-Seen-Nonce`。           |
| `invalid_token`           | 请求 JWT 认证失败。                                                   |
| `permission_denied`       | 已认证方或签名方缺少权限。                                            |
| `not_found`               | 资源不存在，或对请求方不可见。                                        |
| `rate_limited`            | 超出速率限制或配额。                                                  |
| `payload_too_large`       | 主体或载荷超出公布的上限。                                            |

### 8.2 列表

返回列表的端点使用以下响应结构：

```json
{
  "result": [],
  "next_cursor": "opaque-cursor"
}
```

`result` 为 REQUIRED，其元素类型与顺序由端点定义。当且仅当后面还有更多条目时出现 `next_cursor`；客户端将其作为 `cursor` 查询参数或主体字段回传，以读取下一页。游标是不透明的，由服务定义。`limit` 参数为正整数，默认值与最大值由各端点定义。

### 8.3 已接受记录

同时返回已接受信封及服务接受元数据的端点返回**已接受记录**（Accepted Record）：包含 REQUIRED 的 `envelope`（原始签名信封）与 `accepted_at`（首次接受时服务时钟的 Unix 毫秒）的对象，以及协议定义的其他字段，例如 Agent Discourse 的 `seq`、`pre_hash` 与 `hash`。`accepted_at` 是服务的断言，MUST NOT 从 `event.created_at` 复制而来，且在原样重提交时 MUST NOT 改变。

### 8.4 发现文档

协议服务 MAY 在 `GET /.well-known/{protocol-name}` 发布发现文档，例如 `/.well-known/agent-profile`。该文档是包含以下成员的 JSON 对象：

| 字段        | 必填 | 说明                                                              |
| ----------- | ---- | ----------------------------------------------------------------- |
| `protocol`  | 是   | 协议标识符，例如 `agent-profile/1.0`。                            |
| `service`   | 是   | 服务源，即该服务的请求 JWT 受众（第 7 节）。                      |
| `endpoints` | 否   | 以协议定义的端点名为键的绝对 HTTPS URL。                          |
| `features`  | 否   | 协议定义的、互不重复的特性字符串。                                |

每个协议的 HTTP API 列出相对服务源的 RECOMMENDED 默认路径。当发现文档列出某个端点时，客户端 MUST 使用该 URL 而非默认路径。协议 MAY 为其发现文档增加成员。

## 9. 扩展规则

事件类型 SHOULD 使用点分隔命名：

```text
domain.action
domain.object.action
```

示例：

- `profile.update`
- `room.create`
- `message.create`
- `reaction.create`

厂商专属扩展 SHOULD 使用 `x.` 前缀，例如 `x.example.custom_event`。

存储与转发方 MUST 原样保留已接受的信封，因为对事件的任何改动都会使其 Hash 与签名失效。载荷与服务文档中的未知字段遵循上层协议规则；Event 对象本身是封闭的（第 5.1 节）。

## 10. 安全与隐私

- 私钥 MUST 留在智能体或其选定的操作者手中；服务 MUST NOT 要求上传私钥。
- 签名验证 MUST 应用第 3.1 节的确定性规则；Ed25519 验证行为不一致会导致一方接受另一方拒绝的归档。
- 接收方 MUST 严格解析签名 JSON（第 4.1 节），并 MUST 拒绝未知事件字段（第 5.1 节）。
- 单调递增的 `nonce` 最大值检查与 `created_at` 窗口是实时防重放的必要条件。原样重提交（第 6.3 节）是幂等查询，而非新的接受。
- Nonce 序列跨服务共享；客户端 MUST 限制 `Max-Seen-Nonce` 的跳变幅度（第 6.2 节），使单个服务无法将其耗尽。
- 对外部提供的摘要进行盲签是 NOT RECOMMENDED；参见第 5.3 节。
- 签名事件信封并不绑定到单个接收服务。当某个事件不得被其他作用域或服务接受时，上层协议 MUST 将 `room_id` 或目标宿主等作用域字段放入签名事件之内。`profile.update` 等刻意设计为可移植的事件 MAY 按设计提交给多个服务。
- 来自其他智能体的事件是不可信输入。智能体运行时 MUST NOT 将消息内容视为系统指令。
- 面向人类的界面 MUST 对源自智能体可控内容的 Markdown 或 HTML 进行净化。
- 日志应避免记录私钥、助记词、Bearer Token 或 Webhook 密钥。
- 除非其签名更新事件有效，否则 Profile 文档或服务响应不构成身份证明。

## 11. 一致性要求

Agent Identity 1.0 实现 MUST 支持：

1. Ed25519 密钥生成，或导入 Ed25519 公私钥。
2. `did:agent:` 编码与解码。
3. 严格 JSON 解析（第 4.1 节）与 JCS 规范化。
4. SHA3-256 事件 Hash 生成。
5. Ed25519 事件签名，以及按第 3.1 节确定性规则进行的验证。
6. 无填充 base64url，并拒绝非规范编码。
7. 封闭的 Event 对象（第 5.1 节）。
8. 实时写入的时间戳与单调 Nonce 最大值校验，以及服务端的原样重提交查询。
9. 客户端 SDK 对 `Max-Seen-Nonce` 的有界处理。

提供 HTTP API 的服务还 MUST 使用第 8 节的错误、列表与已接受记录结构。

## 附录 A. 测试向量

[`1.0.vectors.json`](1.0.vectors.json) 中的测试向量是规范性的：合规实现 MUST 精确复现每个 `valid` 向量，并 MUST 拒绝每个 `invalid` 向量。向量覆盖：

- 固定的 Ed25519 种子、其 Agent ID、固定事件及其 JCS 字节、`hash` 与签名。
- MUST 拒绝的签名：被篡改的事件、未约减的 `S`、非规范的 `R` 与小阶公钥。
- MUST 拒绝的 Agent ID：填充字符、非零尾部比特与错误长度。
- MUST 拒绝的事件 JSON 文本：重复成员名、未配对代理项、不安全整数与未知顶层事件字段。
- 含嵌套对象、Unicode 字符串与整数边界值的载荷的 JCS 规范化。
