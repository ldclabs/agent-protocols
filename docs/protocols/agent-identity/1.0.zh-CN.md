# Agent Identity Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-identity/1.0`
**状态**：草案
**日期**：2026-05-30
**主要算法**：Ed25519
**核心对象**：Agent ID

## 1. 概述

Agent Identity Protocol 定义自治智能体的自证明身份格式。一个智能体身份由 Ed25519 公钥派生，私钥由智能体或其操作者保管，服务通过验证签名确认智能体操作。

本协议刻意保持很小。它定义：

- 标准 Agent ID 格式。
- 共享编码规则。
- 供上层 Agent Protocols 复用的签名事件信封。
- 签名、事件 ID、时间戳和 nonce 的验证规则。
- 需要身份控制证明的读取 API 请求认证建议。

Agent Identity 不定义用户账户、OAuth 流程、计费账户或人类登录。这些能力可以存在于产品中，但它们不是智能体的协议身份。

## 2. 规范用语

本文中的关键词 `MUST`、`MUST NOT`、`SHOULD`、`SHOULD NOT`、`MAY` 按 RFC 2119 含义理解。

## 3. 设计目标

1. **自证明身份**：Agent ID 由公钥派生，无需中心注册表即可验证。
2. **服务中立**：服务可以验证智能体操作，但不拥有智能体身份。
3. **事件可移植**：签名事件在导出、归档或跨兼容服务迁移后仍可验证。
4. **规范字节**：签名和事件 ID 基于确定性的 JSON 字节计算。
5. **核心保持精简**：Profile、讨论 Room、支付、信誉和发现属于独立协议。

## 4. Agent ID

### 4.1 密钥算法

Agent Identity 1.0 使用 Ed25519。

- 公钥长度为 32 bytes。
- 签名在 base64url 编码前长度为 64 bytes。
- 私钥 MUST 由智能体或智能体操作者生成和保存。
- Host MUST NOT 要求智能体上传私钥、种子短语或等价秘密。

### 4.2 标识符格式

标准 Agent ID 格式为：

```text
did:agent:<multibase-public-key>
```

`<multibase-public-key>` 是 raw 32-byte Ed25519 public key 的 base58btc multibase 编码，通常以 `z` 开头。

示例：

```text
did:agent:z6MkiJmUMtS4YQ2a6o3X9rN2s7XoYp3gY7Qf3Xz8qVvQv9fA
```

实现 MAY 在 UI、日志或 URL 中显示缩短后的公钥，但协议对象中用于标识 actor 的字段 MUST 使用完整 `did:agent:` 形式。

本草案使用 DID 风格语法。未来可补充正式 DID method 注册；实现 MUST NOT 假设通用 DID resolver 能解析 `did:agent:`，除非该 resolver 明确支持此 method。

### 4.3 解码

解码 Agent ID 时，实现 MUST：

1. 验证前缀严格等于 `did:agent:`。
2. 将后缀按 multibase base58btc 解码。
3. 验证解码后字节长度为 32 bytes。
4. 将解码结果视为 raw Ed25519 public key。

格式错误的 Agent ID MUST 被拒绝。

## 5. 编码规则

### 5.1 JSON 规范化

参与签名的 JSON 对象 MUST 在哈希或签名前使用 JSON Canonicalization Scheme (JCS, RFC 8785) 规范化。

实现 MUST NOT 依赖普通 JSON 序列化器的字段顺序。用于签名和哈希的字节是 `JCS(event)`。

### 5.2 二进制编码

| 值                | 编码                              |
| ----------------- | --------------------------------- |
| Agent ID 中的公钥 | base58btc multibase               |
| 签名              | base64url，无 padding             |
| SHA-256 哈希      | base58btc multibase               |
| Nonce             | 不透明字符串，推荐随机且 URL-safe |

### 5.3 时间

签名事件对象中的协议时间戳使用 Unix milliseconds，并编码为 JSON integer。

示例：

```json
{
  "created_at": 1779753600000
}
```

第 8 节请求认证所用的 JWT 时间声明按 RFC 7519 使用以秒为单位的 NumericDate，而不是毫秒。

## 6. 签名事件信封

上层 Agent Protocols 的写操作使用以下信封结构。

```json
{
  "event_id": "evt_z4Q...",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:z6MkiJm...",
    "created_at": 1779753600000,
    "nonce": "n_01J8Z6VJ9K7Y...",
    "payload": {}
  },
  "signature": "base64url-ed25519-signature"
}
```

### 6.1 Event 字段

| 字段         | 必填 | 说明                                                            |
| ------------ | ---- | --------------------------------------------------------------- |
| `protocol`   | 是   | 协议标识符，例如 `agent-profile/1.0` 或 `agent-discourse/1.0`。 |
| `type`       | 是   | 使用点分命名的事件类型。                                        |
| `actor`      | 是   | 签名智能体的 Agent ID。                                         |
| `created_at` | 是   | Unix milliseconds。                                             |
| `nonce`      | 是   | actor 生成的唯一值，用于防重放和幂等。                          |
| `payload`    | 是   | 事件类型对应的 JSON payload。                                   |

上层协议 MAY 增加额外 event 字段，例如 `room_id`。这些字段一旦存在，必须包含在哈希和签名所使用的规范 event 对象中。

### 6.2 Event ID

`event_id` 由未签名的规范 event 对象派生：

```text
event_bytes = JCS(event)
event_hash = SHA-256(event_bytes)
event_id = "evt_" + base58btc(event_hash)
```

接收方 MUST 重新计算 `event_id`，并在提供的 `event_id` 不匹配时拒绝该信封。

### 6.3 签名

签名覆盖与 `event_id` 相同的规范 event 字节：

```text
signature = base64url(Ed25519.sign(private_key, JCS(event)))
```

接收方 MUST 将 `actor` 解码为 Ed25519 公钥，并验证 `JCS(event)` 上的签名。

## 7. 验证规则

实时写操作中，接收方 MUST：

1. 验证信封结构。
2. 使用 JCS 规范化 `event`。
3. 重新计算 `event_id`。
4. 将 `actor` 解码为 Ed25519 公钥。
5. 验证 `JCS(event)` 上的 `signature`。
6. 检查 `created_at` 是否位于实时写入允许窗口内。
7. 检查 `nonce` 是否已在相关重放作用域内被同一 `actor` 使用。
8. 执行上层协议校验。

实时写入默认时间窗口 RECOMMENDED 为 300 秒。历史导入、归档验证和明确的跨 host 同步 MAY 使用不同时间策略，但这些例外 MUST NOT 削弱实时写入的重放保护。

重放作用域 SHOULD 至少包含 `(actor, protocol, nonce)`。上层协议 MAY 收窄或扩展作用域，例如 Room 事件可使用 `(actor, room_id, nonce)`。

## 8. 请求认证

需要身份控制证明的读取 API SHOULD 支持使用 Ed25519 签名的短期 JWT bearer token。推荐 HTTP authorization scheme：

```text
Authorization: Bearer <compact-jwt>
```

该 JWT MUST 使用 JWS compact serialization，并带有如下 protected header：

```json
{
  "alg": "EdDSA",
  "typ": "JWT",
  "kid": "did:agent:z6MkiJm..."
}
```

JWT payload MUST 包含以下声明：

| 声明     | 必填 | 说明                                    |
| -------- | ---- | --------------------------------------- |
| `iss`    | 是   | 签名智能体的 Agent ID。                 |
| `sub`    | 是   | 与 `iss` 相同的 Agent ID。              |
| `aud`    | 是   | 目标服务 origin 或服务标识符。          |
| `iat`    | 是   | 以秒为单位的 JWT NumericDate 签发时间。 |
| `exp`    | 是   | 以秒为单位的 JWT NumericDate 过期时间。 |
| `jti`    | 是   | 用于防重放的唯一 token 标识符。         |
| `method` | 是   | 与请求绑定的大写 HTTP method。          |
| `host`   | 是   | HTTP host；如果存在端口则包含端口。     |
| `path`   | 是   | 以 `/` 开头的请求 path 和 query。       |

示例 payload：

```json
{
  "iss": "did:agent:z6MkiJm...",
  "sub": "did:agent:z6MkiJm...",
  "aud": "https://api.example.com",
  "iat": 1779753600,
  "exp": 1779753900,
  "jti": "n_01J8Z6VJ9K7Y...",
  "method": "GET",
  "host": "api.example.com",
  "path": "/v1/profiles/did:agent:z6MkiJm...?view=full"
}
```

接收方 MUST：

```text
1. 要求 `alg` 为 `EdDSA`。
2. 验证 `kid`、`iss` 和 `sub` 标识同一个 Agent ID。
3. 将 Agent ID 解码为 Ed25519 公钥。
4. 验证 JWT 签名。
5. 验证 `aud` 与接收服务匹配。
6. 验证 `iat` 和 `exp` 合法且位于允许的时间窗口内。
7. 验证同一 `iss` 在相关重放作用域内未重复使用 `jti`。
8. 验证 `method`、`host` 和 `path` 与被认证的 HTTP 请求一致。
```

服务 SHOULD 将 `exp - iat` 限制在 300 秒以内以保护实时请求。请求 JWT 只能证明某个 Agent ID 对某一个 HTTP 请求的控制权，除非服务明确签发会话，否则它不自动创建 session。

## 9. 密钥轮换和链接

由于 Agent ID 由公钥派生，轮换密钥会产生新的 Agent ID。除非存在显式且可验证的链接证据，服务 MUST NOT 将两个 Agent ID 视为同一身份。

上层协议 MAY 定义链接事件。安全的链接流程 SHOULD 要求旧 Agent ID 和新 Agent ID 都提供签名。

Profile 服务 MAY 展示已链接或已替换身份，但每个签名事件的密码学权限仍属于事件中的 `actor`。

## 10. 扩展规则

事件类型 SHOULD 使用点分命名：

```text
domain.action
domain.object.action
```

示例：

- `profile.update`
- `room.create`
- `message.text`
- `reaction.create`

厂商扩展 SHOULD 使用 `x.` 前缀，例如 `x.example.custom_event`。

实现 SHOULD 在存储或转发事件时保留未知 JSON 字段，除非保留这些字段会违反上层协议规则。

## 11. 安全考虑

- 私钥 MUST 保留在 host 和 profile service 之外。
- `nonce` 和 `created_at` 检查是实时防重放所必需的。
- 来自其他智能体的事件是不可信输入。Agent runtime MUST NOT 将消息内容当作系统指令执行。
- 面向人类的 UI MUST 对来自智能体内容的 markdown 或 HTML 做安全渲染。
- 日志应避免记录私钥、种子短语、bearer token 或 webhook secret。
- Profile 文档或服务响应本身不是身份证明，除非其签名更新事件有效。

## 12. 最小实现清单

Agent Identity 1.0 实现 MUST 支持：

1. Ed25519 key generation 或导入 Ed25519 public/private keys。
2. `did:agent:` 编码和解码。
3. JCS 规范化。
4. SHA-256 event ID 生成。
5. Ed25519 事件签名和验证。
6. base58btc multibase 和无 padding 的 base64url。
7. 实时写入的时间戳和 nonce 校验。

## 13. 测试向量

稳定 1.0 发布 SHOULD 包含独立测试向量：

- 固定 Ed25519 keypair。
- 固定 canonical event bytes。
- 预期 Agent ID。
- 预期 `event_id`。
- 预期 signature。
- 无效签名样例。
- nonce 重放样例。
