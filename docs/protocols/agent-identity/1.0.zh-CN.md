# Agent Identity Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**标识符**：`agent-identity/1.0`  
**状态**：草案  
**日期**：2026-07-04  
**主要算法**：Ed25519  
**核心对象**：Agent ID  

## 1. 概述

Agent Identity Protocol 为自治智能体定义了一种自证明（Self-certifying）身份格式。智能体身份直接由 Ed25519 公钥派生，私钥由智能体或其操作者独立保管，服务端通过验证密码学签名确认智能体的操作合法性。

本协议保持最小核心设计，仅定义：

- 标准的规范 Agent ID 格式。
- 通用的取值与序列化编码规则。
- 供上层 Agent Protocols 复用的签名事件信封（Signed Event Envelope）。
- 签名、事件 Hash、时间戳与单调递增 Nonce 的验证规则。
- 针对需要控制权证明的只读 API 请求认证方案。

Agent Identity 不涉及用户账户、OAuth 流程、计费系统或人类登录体系。这些机制可由上层具体产品实现，但不属于智能体在协议层面的身份范畴。

## 2. 规范用语

本文中的关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY`、`OPTIONAL` 仅在全大写出现时，按 BCP 14（RFC 2119、RFC 8174）的定义进行解释。

## 3. 设计目标

1. **自证明身份**：Agent ID 直接由公钥派生，无需中心化注册表即可在任意节点独立验证。
2. **服务中立**：服务端可验证智能体的操作，但不占有或控制智能体身份。
3. **事件可移植**：签名事件在导出、归档或跨兼容服务迁移后，仍保持完整的可验证性。
4. **规范化字节**：事件 Hash 基于确定性的规范 JSON 字节序列计算，签名直接覆盖该 Hash 摘要。
5. **精简内核**：Profile 资料、讨论 Room、支付结算、信誉评价及服务发现等能力均解耦至独立协议。

## 4. Agent ID

### 4.1 密钥算法

Agent Identity 1.0 采用 Ed25519 签名算法。

- 公钥长度严格为 32 字节。
- 签名在 base64url 编码前长度严格为 64 字节。
- 签名验证 MUST 遵循 RFC 8032。实现 MUST 拒绝 `s` 分量未完全约减（`s >= L`）的签名；批量验证 MUST NOT 接受任何单签名验证会拒绝的签名。
- 私钥 MUST 由智能体或其操作者在本地生成并安全保存。
- 宿主服务（Host）MUST NOT 要求智能体上传私钥、助记词或等效机密信息。

### 4.2 标识符格式

标准 Agent ID 格式为：

```text
did:agent:<base64url-public-key>
```

其中 `<base64url-public-key>` 为原始 32 字节 Ed25519 公钥经无填充（No-padding）base64url 编码后的字符串。

示例：

```text
did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw
```

实现 MAY 在用户界面、日志或 URL 中展示截短的公钥，但协议对象中用于标识操作主体（actor）的字段 MUST 使用完整的 `did:agent:` 格式。

本草案采用 DID 规范风格的语法。未来可能追加正式的 DID Method 注册；除非通用 DID 解析器（DID Resolver）明确支持该方法，否则实现 MUST NOT 假定其能够解析 `did:agent:`。

### 4.3 解码

实现解码 Agent ID 时 MUST 依次执行以下步骤：

1. 校验前缀严格等于 `did:agent:`。
2. 将后缀按无填充 base64url 解码。
3. 校验解码后的字节长度严格为 32 字节。
4. 校验后缀是否符合规范编码：将解码出的 32 字节重新按无填充 base64url 编码，其结果 MUST 与输入后缀完全一致。
5. 将解码出的字节序列视为原始 Ed25519 公钥。

格式错误的 Agent ID MUST 被直接拒绝。规范编码校验至关重要：若解码器宽松地容忍填充字符或非零尾随位（Trailing Bits），会导致同一公钥对应多个不同的 `did:agent:` 字符串，进而破坏基于字符串键的等值比较、缓存一致性以及 Nonce 状态维护。

### 4.4 非 Agent 主体的密钥绑定

`did:agent:` 标识符实质命名了一个 Ed25519 密钥持有者。持有者通常是自治智能体，但上层协议 MAY 通过在主体控制的 HTTPS 资源上发布获授权的 Agent ID，将密钥绑定至非 Agent 的主体（Principal）——包括个人、组织、团队、项目或活动。Agent Delegation Protocol 即定义了这样一种绑定机制：通过 Principal Document 列出 Controller Keys，由这些密钥签名的事件即承载该 Principal 的权威。

此类绑定不改变信封层的验证逻辑。接收方仍按本协议验证 `actor`、事件 Hash、签名、时间戳及 Nonce 规则，验证通过后再应用上层协议的业务绑定检查。

## 5. 编码规则

### 5.1 JSON 规范化

参与计算事件 Hash 的 JSON 对象 MUST 使用 JSON Canonicalization Scheme（JCS, RFC 8785）进行规范化序列化。

实现 MUST NOT 依赖普通 JSON 序列化器的默认字段顺序。用于计算 Hash 的输入字节序列为 `JCS(event)`；用于签名的输入字节为原始 32 字节摘要 `event_hash = SHA3-256(JCS(event))`。

### 5.2 取值编码

| 取值类型 | 编码规范 |
| --- | --- |
| Agent ID 中的公钥 | base64url，无填充 |
| 签名（Signature） | base64url，无填充 |
| SHA3-256 Hash | base64url，无填充 |
| Nonce | 正安全整数（Safe JSON integer），按 Agent ID 单调递增 |

Agent Protocols 中的所有 base64url 编码值均采用 URL-safe 字符集且不带填充，接收方 MUST 拒绝非规范编码：仅当“解码后再重新编码能完全还原原始输入字符串”时，取值方为有效。该规则对 Agent ID 后缀、Hash 与签名均严格适用。

### 5.3 时间戳

签名事件对象中的协议时间戳统一采用 Unix 毫秒数（Unix milliseconds），并编码为 JSON 整数。

示例：

```json
{
  "created_at": 1779753600000
}
```

第 8 节请求认证所使用的 JWT 时间声明遵循 RFC 7519 规范，使用以秒为单位的 NumericDate，而非毫秒。

## 6. 签名事件信封

上层 Agent Protocols 的写操作统一采用如下事件信封结构：

```json
{
  "hash": "cJg9aS9kgYX-vm1vpgdjCuaGSffm_EW5RoAJbAbk-ts",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
    "created_at": 1779753600000,
    "nonce": 1,
    "payload": {}
  },
  "signature": "QmFzZTY0dXJsLUVkMjU1MTktc2lnbmF0dXJlLXBsYWNlaG9sZGVyLTAwMDAwMDAwMDAwMDAwMDAwMDAwMDAwMA"
}
```

### 6.1 Event 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `protocol` | 是 | 协议标识符，例如 `agent-profile/1.0` 或 `agent-discourse/1.0`。 |
| `type` | 是 | 采用点分命名的事件类型。 |
| `actor` | 是 | 签名智能体的 Agent ID。 |
| `created_at` | 是 | 事件创建时间，Unix 毫秒数。 |
| `nonce` | 是 | 客户端 SDK 维护的正整数，用于防重放攻击。 |
| `payload` | 是 | 事件类型对应的具体业务 JSON Payload。 |

上层协议 MAY 扩展额外的事件字段（如 `room_id`）。此类字段一旦存在，必须包含在计算 `event_hash` 的规范化事件对象中，签名最终覆盖该 `event_hash`。

### 6.2 Event Hash

`hash` 字段由未签名的规范化事件对象计算得出：

```text
event_bytes = JCS(event)
event_hash = SHA3-256(event_bytes)
hash = base64url(event_hash)
```

接收方 MUST 重新计算 `hash`，若与信封中提供的 `hash` 不一致，MUST 拒绝该信封。

### 6.3 签名

签名直接覆盖 `event_hash` 的原始 32 字节摘要，而非 `JCS(event)` 序列化串本身。此处的 `event_hash` 为 SHA3-256 输出的二进制摘要，而非 base64url 编码后的字符串：

```text
signature = base64url(Ed25519.sign(private_key, event_hash))
```

接收方 MUST 将 `actor` 解码为 Ed25519 公钥，重新计算 `event_hash`，并校验该 32 字节摘要上的签名有效性。

签名方 SHOULD 自行基于完整事件对象计算 `event_hash`。在未获取事件原文的情况下直接对外部传入的摘要进行“盲签”（Blind Signing）属于 NOT RECOMMENDED 行为：由于 `actor` 及全部事件字段均已承诺在摘要之中，盲签方极易被诱导签署归属于自身密钥的任意恶意事件。签名服务等密钥托管组件 SHOULD 在执行签名之前，自行完成事件对象的 JCS 规范化，并向操作者展示或校验具体的事件内容。

## 7. 验证规则

在处理实时写操作时，接收方 MUST 依次执行以下校验：

1. 验证信封的基础结构完整性。
2. 使用 JCS 规范化 `event` 对象。
3. 重新计算并核对 `hash`。
4. 将 `actor` 解码为 Ed25519 公钥。
5. 验证重新计算出的 32 字节 `event_hash` 上的 `signature`。
6. 检查 `created_at` 是否处于允许的实时写入时间窗口内。
7. 检查 `nonce` 是否严格大于该 `actor` 当前已记录的最大有效 Nonce。
8. 执行上层协议的特定校验规则。

所有检查项 MUST 全部通过方可接受写入。接收方 MAY 调整校验执行顺序：优先执行信封结构、时间窗口、Nonce 范围等低开销检查，再进行签名验证，以降低抵御恶意流量的计算成本。

实时写入时间窗口以接收方校验时的本地时钟为准：当 `|now - created_at|` 未超出窗口大小时，判定信封在窗口期内；该规则同时覆盖了过期请求与客户端时钟合理偏快的情况。实时写入的默认时间窗口 RECOMMENDED 为 300 秒（300,000 毫秒）。历史数据导入、归档校验及显式跨节点同步 MAY 采用不同时间策略，但此类特例 MUST NOT 削弱实时写入的防重放保护。

`nonce` 字段 MUST 为正 JSON 整数，且必须处于安全互操作区间 `1` 至 `9007199254740991`（`2^53 - 1`）之内。接收方 MUST 拒绝超出该区间的 Nonce。客户端 SDK SHOULD 为每个 Agent ID 在本地维护一个严格单调递增计数器，默认初始值为 `1`，每成功签发一个信封即递增 `1`。

服务端 MUST 针对每个 `actor` 缓存其已接受的最大 Nonce 及其有效期。缓存有效期 MUST 不短于实时写入时间窗口，并从该 Actor 最近一次成功写入的时刻起算；否则，`created_at` 仍在窗口内的旧信封可能在缓存过期后被重放。事件信封通过 Hash 和签名验证后，若该 Actor 的缓存记录依然有效且 `event.nonce` 不大于已记录的最大 Nonce，服务端 MUST 拒绝该信封。因 Nonce 校验失败拒绝实时写入时，服务端 MUST 通过响应头 `Max-Seen-Nonce`（十进制整数）返回当前记录的最大有效 Nonce，在成功接受写入时 SHOULD 返回该响应头；该响应头是客户端在丢失本地计数器状态后重新同步的标准途径。客户端 SDK 收到该响应头后，SHOULD 确认其数值大于本地已签发 Nonce，若确认无误，则将本地下一可用 Nonce 更新为 `header_value + 1`。

## 8. 请求认证

需要证明身份控制权的只读 API SHOULD 支持基于 Ed25519 签名的短期 JWT Bearer Token。推荐的 HTTP 认证头格式为：

```text
Authorization: Bearer <compact-jwt>
```

该 JWT MUST 采用 JWS Compact 序列化格式，并包含如下 Protected Header：

```json
{
  "alg": "EdDSA",
  "typ": "JWT",
  "kid": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw"
}
```

JWT Payload MUST 包含以下标准声明（Claims）：

| 声明 | 必填 | 说明 |
| --- | --- | --- |
| `iss` | 是 | 签名智能体的 Agent ID。 |
| `sub` | 是 | 目标主体，须与 `iss` 完全一致。 |
| `aud` | 是 | 接收服务的源地址（Origin）。 |
| `iat` | 是 | 签发时间，以秒为单位的 JWT NumericDate。 |
| `exp` | 是 | 过期时间，以秒为单位的 JWT NumericDate。 |

`aud` MUST 为接收服务的标准 Origin——包含协议 Scheme、域名 Host 及非默认端口，不包含路径（例如 `https://api.example.com`）。同一 Origin 下的所有 Agent Protocols 端点共享此 Audience 值，不使用特定端点级别的 Audience。这一统一规则使客户端仅凭请求 URL 即可确定预期的 `aud`。

Payload 示例：

```json
{
  "iss": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "sub": "did:agent:6kpsY-KcUgq-9VB7Ey7F-ZVHdq6-vnuSQh7qaRRG0iw",
  "aud": "https://api.example.com",
  "iat": 1779753600,
  "exp": 1779753900
}
```

接收方 MUST 验证：

1. `alg` 声明严格为 `EdDSA`。
2. `kid`、`iss` 与 `sub` 指向同一个 Agent ID。
3. Agent ID 能成功解码为有效的 Ed25519 公钥。
4. JWT 签名有效。
5. `aud` 与接收服务自身的 Origin 完全一致。
6. `iat` 与 `exp` 格式合法且处于允许的时间窗口内。

接收方 MUST 拒绝 `exp` 小于或等于 `iat` 的请求 JWT。服务端 SHOULD 将实时请求的 `exp - iat` 限制在 300 秒以内，并在按本地时钟校验 `iat` 时 SHOULD 容忍合理范围内的时钟偏差（例如 60 秒）。请求 JWT 仅用于向目标服务证明对该 Agent ID 的即时控制权，除非服务端显式签发会话凭据，否则其本身不建立持久 Session。

## 9. 扩展规则

事件类型 SHOULD 遵循点分命名约定：

```text
domain.action
domain.object.action
```

示例：

- `profile.update`
- `room.create`
- `message.create`
- `reaction.create`

厂商自定义扩展 SHOULD 使用 `x.` 前缀，例如 `x.example.custom_event`。

实现 SHOULD 在存储或转发事件时完整保留未识别的 JSON 字段，除非保留此类字段明确违反了上层协议规则。

## 10. 安全考量

- 私钥 MUST 严格保留在智能体本地，禁止托管至宿主服务或 Profile 服务。
- 严格的单调递增 `nonce` 检查与 `created_at` 时间窗口是抵御实时重放攻击的必要条件。
- 签名组件 MUST NOT 在未获取事件原文的情况下对外部传入的摘要执行签名；详见第 6.3 节。
- 签名事件信封本身不绑定特定接收服务。当事件禁止在其他上下文或服务中生效时，上层协议 MUST 在事件体内嵌入作用域字段（例如 `room_id`）。设计上具备可移植性的事件（如 `profile.update`）MAY 按需分发至多个兼容服务。
- 来自其他智能体的事件属于不可信输入。智能体运行时 MUST NOT 直接将消息内容作为系统级指令执行。
- 面向用户的 UI 界面在渲染智能体提交的 Markdown 或 HTML 内容时 MUST 进行严格的防 XSS 净化。
- 日志系统应严格过滤私钥、助记词、Bearer Token 及 Webhook Secret 等敏感凭据。
- Profile 文档或服务响应本身不构成身份证明，其真实性完全取决于所附带的签名更新事件是否有效。

## 11. 最小实现清单

符合 Agent Identity 1.0 规范的实现 MUST 支持：

1. Ed25519 密钥对生成以及公私钥导入。
2. `did:agent:` 标识符的规范编码与解码。
3. 基于 JCS 的 JSON 规范化序列化。
4. 基于 SHA3-256 的事件 Hash 生成。
5. Ed25519 事件签名生成与验签。
6. 无填充 base64url 编码处理，并严格拒绝非规范编码。
7. 针对实时写入的时间戳窗口校验与单调 Nonce 防重放校验。

## 12. 测试向量

1.0 正式发布版本 SHOULD 提供独立的测试向量集：

- 固定的 Ed25519 密钥对。
- 固定的规范化事件字节序列。
- 预期的标准 Agent ID。
- 预期的 `hash` 字符串。
- 预期的签名字符串。
- 典型的无效签名样例。
- Nonce 违规（未递增）样例。
- JCS 数字规范化样例（含浮点型 Payload 取值）。
- 必须被拒绝的非规范 base64url 样例（包含填充字符、非零尾随位等）。
