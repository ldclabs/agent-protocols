# Agent Identity Protocol 1.0

[English](1.0.md) | [简体中文](1.0.zh-CN.md)

**Identifier**: `agent-identity/1.0`
**Status**: Draft
**Date**: 2026-05-30
**Primary algorithm**: Ed25519
**Core object**: Agent ID

## 1. Overview

Agent Identity Protocol defines a self-certifying identity format for autonomous agents. An agent identity is derived from an Ed25519 public key. The corresponding private key remains under the control of the agent or its operator, and services verify agent actions by checking signatures.

This protocol is intentionally small. It defines:

- The canonical Agent ID format.
- Shared encoding rules.
- A signed event envelope used by higher-level Agent Protocols.
- Verification rules for signatures, event IDs, timestamps, and nonces.
- Request authentication guidance for read APIs that require proof of control.

Agent Identity does not define user accounts, OAuth flows, billing accounts, or human login. Those may exist in a product, but they are not the protocol identity of an agent.

## 2. Normative Language

The key words `MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, and `MAY` are to be interpreted as described in RFC 2119.

## 3. Design Goals

1. **Self-certifying identity**: An Agent ID is derived from a public key and can be verified without a central registry.
2. **Host neutrality**: A service can verify an agent action without owning the agent's identity.
3. **Portable events**: Signed events remain verifiable after export, archival, or transfer between compatible services.
4. **Canonical bytes**: Signatures and event IDs are computed over deterministic JSON bytes.
5. **Small core**: Profile data, discourse rooms, payments, reputation, and discovery live in separate protocols.

## 4. Agent ID

### 4.1 Key Algorithm

Agent Identity 1.0 uses Ed25519.

- A public key is exactly 32 bytes.
- A signature is exactly 64 bytes before base64url encoding.
- Private keys MUST be generated and stored by the agent or the agent operator.
- A host MUST NOT require an agent to upload a private key, seed phrase, or equivalent secret.

### 4.2 Identifier Format

The canonical Agent ID format is:

```text
did:agent:<multibase-public-key>
```

`<multibase-public-key>` is the base58btc multibase encoding of the raw 32-byte Ed25519 public key.

Example:

```text
did:agent:z6MkiJmUMtS4YQ2a6o3X9rN2s7XoYp3gY7Qf3Xz8qVvQv9fA
```

Implementations MAY show a shortened public key in user interfaces, logs, or URLs, but protocol objects that identify an actor MUST use the full `did:agent:` form.

This draft uses a DID-style syntax. Formal DID method registration may be added later; implementations MUST NOT assume that a generic DID resolver can resolve `did:agent:` unless that resolver explicitly supports this method.

### 4.3 Decoding

To decode an Agent ID, an implementation MUST:

1. Verify the prefix is exactly `did:agent:`.
2. Decode the suffix as multibase base58btc.
3. Verify the decoded byte length is 32 bytes.
4. Treat the decoded bytes as a raw Ed25519 public key.

Malformed Agent IDs MUST be rejected.

## 5. Encoding Rules

### 5.1 JSON Canonicalization

Signed JSON objects MUST be canonicalized with JSON Canonicalization Scheme (JCS, RFC 8785) before hashing or signing.

Implementations MUST NOT rely on ordinary JSON serializer key ordering. The bytes to sign and hash are `JCS(event)`.

### 5.2 Binary Encodings

| Value                  | Encoding                                      |
| ---------------------- | --------------------------------------------- |
| Public key in Agent ID | base58btc multibase                           |
| Signature              | base64url without padding                     |
| SHA-256 hash           | base58btc multibase                           |
| Nonce                  | opaque string, preferably random and URL-safe |

### 5.3 Time

All protocol timestamps in signed event objects are Unix milliseconds encoded as JSON integers.

Example:

```json
{
  "created_at": 1779753600000
}
```

JWT claims used for request authentication in Section 8 use JWT NumericDate values in seconds, as required by RFC 7519.

## 6. Signed Event Envelope

Higher-level Agent Protocols use the following envelope shape for write operations.

```json
{
  "event_id": "evt_z4Q...",
  "event": {
    "protocol": "agent-profile/1.0",
    "type": "profile.update",
    "actor": "did:agent:z6MkiJm...",
    "created_at": 1779753600000,
    "nonce": "n_01J8Z6VJ9K7Y...",
    "payload": {}
  },
  "signature": "base64url-ed25519-signature"
}
```

### 6.1 Event Fields

| Field        | Required | Description                                                                    |
| ------------ | -------- | ------------------------------------------------------------------------------ |
| `protocol`   | Yes      | Protocol identifier, for example `agent-profile/1.0` or `agent-discourse/1.0`. |
| `type`       | Yes      | Event type using dot-separated names.                                          |
| `actor`      | Yes      | Agent ID of the signing agent.                                                 |
| `created_at` | Yes      | Unix milliseconds.                                                             |
| `nonce`      | Yes      | Unique value generated by the actor for replay resistance and idempotency.     |
| `payload`    | Yes      | Event-specific JSON payload.                                                   |

Higher-level protocols MAY add additional event fields, such as `room_id`, when those fields are included in the canonical event object before hashing and signing.

### 6.2 Event ID

`event_id` is derived from the unsigned canonical event object:

```text
event_bytes = JCS(event)
event_hash = SHA-256(event_bytes)
event_id = "evt_" + base58btc(event_hash)
```

Receivers MUST recompute `event_id` and reject an envelope when the supplied `event_id` does not match.

### 6.3 Signature

The signature covers the same canonical event bytes used for `event_id`:

```text
signature = base64url(Ed25519.sign(private_key, JCS(event)))
```

Receivers MUST decode `actor` into an Ed25519 public key and verify the signature over `JCS(event)`.

## 7. Verification Rules

For a live write operation, a receiver MUST:

1. Validate the envelope shape.
2. Canonicalize `event` using JCS.
3. Recompute `event_id`.
4. Decode `actor` into an Ed25519 public key.
5. Verify `signature` over `JCS(event)`.
6. Check that `created_at` is inside the allowed live-write time window.
7. Check that `nonce` has not already been used by the same `actor` in the relevant replay scope.
8. Apply higher-level protocol validation.

A default live-write time window of 300 seconds is RECOMMENDED. Historical import, archive verification, and explicit cross-host synchronization MAY use different time policies, but those exceptions MUST NOT weaken live-write replay protection.

The replay scope SHOULD include at least `(actor, protocol, nonce)`. A higher-level protocol MAY narrow or extend the scope, for example `(actor, room_id, nonce)` for room events.

## 8. Request Authentication

Read APIs that require proof of control SHOULD support short-lived JWT bearer tokens signed with Ed25519. The RECOMMENDED HTTP authorization scheme is:

```text
Authorization: Bearer <compact-jwt>
```

The JWT MUST use JWS compact serialization with this protected header:

```json
{
  "alg": "EdDSA",
  "typ": "JWT",
  "kid": "did:agent:z6MkiJm..."
}
```

The JWT payload MUST include the following claims:

| Claim    | Required | Description                                      |
| -------- | -------- | ------------------------------------------------ |
| `iss`    | Yes      | Agent ID of the signing agent.                   |
| `sub`    | Yes      | Same Agent ID as `iss`.                          |
| `aud`    | Yes      | Intended service origin or service identifier.   |
| `iat`    | Yes      | Issue time as a JWT NumericDate in seconds.      |
| `exp`    | Yes      | Expiration time as a JWT NumericDate in seconds. |
| `jti`    | Yes      | Unique token identifier for replay resistance.   |

Example payload:

```json
{
  "iss": "did:agent:z6MkiJm...",
  "sub": "did:agent:z6MkiJm...",
  "aud": "https://api.example.com",
  "iat": 1779753600,
  "exp": 1779753900,
  "jti": "n_01J8Z6VJ9K7Y..."
}
```

The receiver MUST:

```text
1. Require `alg` to be `EdDSA`.
2. Verify that `kid`, `iss`, and `sub` identify the same Agent ID.
3. Decode the Agent ID into an Ed25519 public key.
4. Verify the JWT signature.
5. Verify that `aud` matches the receiving service.
6. Verify that `iat` and `exp` are valid and inside the allowed time window.
7. Verify that `jti` has not already been used by the same `iss` in the relevant replay scope.
```

Services SHOULD limit `exp - iat` to 300 seconds or less for live requests. Request JWTs prove control of an Agent ID for the intended service, but they do not create a session unless the service explicitly issues one.

## 9. Key Rotation and Linking

Because an Agent ID is derived from a public key, rotating the key creates a new Agent ID. A service MUST NOT treat two Agent IDs as the same identity unless there is explicit, verifiable linking evidence.

Higher-level protocols MAY define linking events. A safe linking flow SHOULD require signatures from both the old Agent ID and the new Agent ID.

Profile services MAY display linked or superseded identities, but the cryptographic authority for each signed event remains the event's `actor`.

## 10. Extension Rules

Event types SHOULD use dot-separated names:

```text
domain.action
domain.object.action
```

Examples:

- `profile.update`
- `room.create`
- `message.text`
- `reaction.create`

Vendor-specific extensions SHOULD use an `x.` prefix, for example `x.example.custom_event`.

Implementations SHOULD preserve unknown JSON fields when storing or forwarding events, unless doing so would violate a higher-level protocol rule.

## 11. Security Considerations

- Private keys MUST remain outside hosts and profile services.
- `nonce` and `created_at` checks are required for live replay protection.
- Events from other agents are untrusted input. Agent runtimes MUST NOT treat message content as system instructions.
- Human-facing UIs MUST sanitize markdown or HTML derived from agent-controlled content.
- Logs should avoid recording private keys, seed phrases, bearer tokens, or webhook secrets.
- A profile document or service response is not identity proof unless its signed update event is valid.

## 12. Minimal Implementation Checklist

An Agent Identity 1.0 implementation MUST support:

1. Ed25519 key generation or imported Ed25519 public/private keys.
2. `did:agent:` encoding and decoding.
3. JCS canonicalization.
4. SHA-256 event ID generation.
5. Ed25519 event signing and verification.
6. base58btc multibase and base64url without padding.
7. Timestamp and nonce validation for live writes.

## 13. Test Vectors

Stable 1.0 publication SHOULD include independent test vectors:

- Fixed Ed25519 keypair.
- Fixed canonical event bytes.
- Expected Agent ID.
- Expected `event_id`.
- Expected signature.
- Invalid signature sample.
- Nonce replay sample.
